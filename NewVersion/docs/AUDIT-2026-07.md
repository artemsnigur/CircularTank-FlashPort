# Full-project audit — July 2026

A read-only audit of every unit in the port, run across all 13 `PROGRESS.md`
categories. Written down because it took seven parallel sweeps plus independent
re-verification to produce, and none of it is re-derivable from a green test run.

**Status of this document:** findings are as of commit `d390ce0`. Items marked
**[FIXED]** have been addressed since; everything else stands. Nothing here was
observed in a running game — see [Verification status](#verification-status).

## Method

Seven read-only agents, split by `PROGRESS.md` category, each establishing four
flags per unit with a `file:line` citation for every claim:

- **exists** — the module is there
- **tested** — it has tests that assert real behaviour
- **wired** — it has a call site outside its own test file, *and* that caller is
  reachable from a runtime entry point, *and* the export is actually called
  rather than merely imported
- **verified** — it has been seen working in the running game

`verified` is never assignable from reading code — only play can set it — and it
was unknown for every unit here when this was written. Three items have since
been observed and are recorded in
[Verification status](#verification-status), each naming the commit it was seen
against; that requirement exists because a `verified` granted against a stale
dev server is indistinguishable from a real one. It remains unknown for the
large majority of modules.

"Wired" was established by following aliases and renamed destructures to a
runtime entry point, not by name-grep — per the rule in `CLAUDE.md` about
`enemyModel` column 1, which was wrongly declared dead because its only read
went through a renamed working copy.

Baseline at time of audit: `npm run typecheck` clean, `npm run lint` clean,
`npm run data:check` green, `npm test` 62 files / 1327 tests passing. Every
defect below was present underneath that green suite.

## Critical — breaks play

### 1. All 45 Boss levels auto-win without spawning anything **[FIXED — 8001772]**

> Fixed by deriving `bossAmount` from the level composition (`bossCountFor`, the
> port of `getBossCount`) and making it `createWaveState`'s default, so a caller
> cannot omit a value it never has to pass. Wiring-seam tests added and confirmed
> failing against the old default. **Verified on screen** — the reviewer reached
> 1-9, saw the boss spawn, damaged it, killed it, and the level ended. Observed
> against >= d3c02cd, which postdates this fix; see the stale-server section.

The first Boss level is **1-9**, the ninth level of the game, and `LevelSelectScene`
pins world 1. This is not an edge case.

- `GameplayScene.ts:606` calls `createWaveState(spec)` and omits the second argument
- `waveState.ts:65` — `createWaveState(spec: LevelSpec, bossAmount = 0)` defaults to **0**
- `waveState.ts:269` — `bossAmountKilled >= bossAmount` → `0 >= 0` → **complete on frame 1**
- `waveState.ts:108` — `bossAmount <= bossAmountKilled` → `canSpawn` false forever, **nothing spawns**
- Nothing anywhere in `src/` computes a boss count

The AS3 derives it in `ScreenGame.as:703-716` (`getBossCount`), summing `count` for
every composition entry whose level is `"B"`. That data survives the extraction —
level 1-9 carries `{ type: "Basic", level: "B", count: 1 }` — and is never read.

**Why the suite was blind:** every Boss test passes `bossAmount` explicitly
(`flag.test.ts:144`, `flag.test.ts:185`, `waveState.test.ts:83`). The module was
correct; the scene fed it wrong. This is `CLAUDE.md`'s documented failure mode
verbatim.

Mode counts across the 405 levels: `Normal 90, Flag 90, Tower 90, Defense 90, Boss 45`.
World 1 Boss levels: 9, 18, 27, 36, 45.

### 2. Music can never play **[FIXED — db708b9, VERIFIED on screen]**

> All five defects fixed as one unit. Menu music confirmed playing by the
> reviewer against current code, after the stale server was killed — the first
> observation in this document made against a provably current server.

`SoundManager`'s SFX path is genuinely wired — 17 runtime call sites covering weapon
fire, impacts, enemy death, coin pickup, flag capture, contact damage, weapon change
and purchases. Music is not.

- `PreloadScene.ts:140` — `installSoundManager(this)` binds `PhaserAudioBackend` to
  **PreloadScene**
- `PreloadScene.ts:147` — `this.scene.start(SceneKeys.MainMenu)`, seven lines later,
  shuts that scene down
- `PhaserAudioBackend.requestLoad` (`:33-44`) reaches for `this.loaderScene.load` —
  a torn-down scene's loader
- Its `loadInFlight` guard is cleared only by listeners registered on that same dead
  loader, so every subsequent request early-returns
- `SoundManager.startCrossfade` deliberately retries "next frame" — a retry that can
  never succeed

Near-miss worth knowing: `112_MusicMenu.mp3` **is** decoded during preload, under key
`music-menu` (`manifest.ts:83`), while the manager looks for `snd:112_MusicMenu.mp3`.
Two naming schemes for one file in one cache.

Also: 5 of 8 tracks (`Normal`, `Flag`, `Tower`, `Defense`, `Boss`) have no call site
at all. Per-level-mode music is not wired.

### 3. Every level plays at the wrong size **[FIXED — 9a25f25]**

> Fixed by resolving the level spec at the top of `create()` and taking
> `roomWidth`/`roomHeight` from it. This also revived the off-camera spawn
> search on **195 of 405** levels; `spawnPlacement.ts` needed no change, as its
> guard was already a faithful port of `PartGameArea.as:7245` and only its input
> was wrong. **Verified on screen** — room sizes visibly differ between levels.
> Observed against >= d3c02cd, which postdates this fix.

`LevelSpec.roomWidth` / `roomHeight` are extracted for all 405 levels and asserted in

never runs, and **every enemy in the game enters from a wall**.

## E1. Every entity size was invented — corrected 4 August 2026

**Every difficulty judgement anyone made while playing this build before 4 August
2026 was made against wrong collision numbers.** That is the headline, and it is
why this sits here rather than inside the art commit that fixed it.

The AS3 sets `enemy.radius = enemy.width / 2` (`PartGameArea.as:3318`) — the authored
sprite width *is* the hitbox, per type. The port drew every enemy as a tinted circle at
one invented diameter, 26 for all normal types and 46 for all bosses, and took the
radius from that. The tank used 58.

| | AS3 | port before | ratio |
|---|---|---|---|
| Normal enemy radius | 4.5 – 13.5, per type | 13, flat | 0.35x – 1.04x |
| Boss radius | 20.5 – 65.5, per type | 23, flat | 0.89x – 2.85x |
| Tank radius | 14 (`Tank.as:23`) | 29 | 2.07x |

Contact damage sums the two radii, so a `Basic` reaching the tank triggered at
`29 + 13 = 42` units where the original triggers at `14 + 8.5 = 22.5` — **1.87x the
intended range, on every level, for the whole project**. `DamageAddictBoss` was drawn
and collided at a third of its intended size; `Tiny` at nearly three times.

**Three separate constants, three separate causes.** They are worth keeping apart,
because only one of them is the kind of mistake a citation would have caught:

1. **`TANK_DIAMETER = 58`** — a diameter/radius conflation, confirmed arithmetically
   rather than assumed. The authored `TankBody` is 29 wide. 29 read as a *radius* and
   doubled gives exactly 58; no other reading produces it. The port then took
   `58 / 2 = 29` back out as the radius, so both the sprite and the hitbox carried the
   doubling.
2. **The enemy diameters** — not a conflation, simply invented. 26 and 46 reconcile
   with no authored width. They were placeholders that outlived the placeholder art.
3. **`TANK_ROT_SPEED_MAX = 10`** — a transcription error against `Tank.as:25`'s 20,
   found while deriving expected values for the rotation tests. It carried a correct
   citation to the line that contradicts it, and `tankMovement.test.ts` asserted the
   step size by copying the same wrong literal, so the test could not tell a correct
   step from a halved one.

**`TANK_RADIUS = 14` was already in the tree, ported and tested, and reached by
nothing.** `player/tankDamage.ts:29` carries the correct AS3 value with the right
citation; production read `PlayerTank`'s locally derived 29 instead. This is the
"exists + tested but not wired" pattern again, and the most uncomfortable instance so
far, because the correct number was sitting beside the wrong one the entire time.

**The full suite stayed green across the change.** 2445 tests, and not one of the 112
`radius` consumers pinned a value. That is the finding behind the finding: the numbers
were unpinned, which is why they could be invented and stay invented.

### What was checked afterwards

Every post-swap radius was reconciled against `width / 2` read back out of the
exported SVG — not against the new table, which would only prove self-consistency.
All 40 reconcile exactly; none needed rounding. `enemyArt.test.ts` drives that
reconciliation on every run, so a transcription slip in the table fails rather than
becoming the new truth.

The tank is the exception and is deliberately *not* derived: `Tank.as:23` hard-codes
14 against a 29-wide body, i.e. half the width less the 0.5-unit stroke. Deriving it
would give 14.5 and silently diverge, so the constant is imported from `tankDamage.ts`
and the test asserts both readings — that it is 14, and that the body is not 58.

### Knowing the rule does not prevent breaking it

Worth recording because it is the strongest evidence for the section above.
Three corrections in a single round were each one of the patterns catalogued
here, reappearing **inside the fix for that pattern**, with the rule freshly
written and in context:

- A **substituted denominator** — "4% → 100%" for the filename check, where 100%
  required redefining the total from "every extracted file" to "every named
  file". Committed in the change addressing partial enforcement.
- An **unverified assertion** — "this retires three knip entries", stated without
  running knip, and false. Committed in the change addressing unverified
  guarantees.
- A **self-check on the weak gate only** — `pre-commit` verified itself,
  `pre-push` did not, leaving the gate that carries lint, the full suite and
  `data:check` as the unprotected one.

None was caught by the rule existing. All three were caught by a reviewer asking
a direct question. The conclusion is not "be more careful": it is that every
entry in the enforced column was built after a defect *because* knowing a rule
does not prevent breaking it. **Where a rule matters, it needs a mechanism even
when the person applying it wrote the rule down minutes earlier.**

Which points at the obvious gap: **this sweep itself has no mechanism.** Nothing
re-runs it, nothing greps for new present-indicative claims, and nothing fails
when one is added. The next asserted guarantee someone writes goes uncaught until
a human happens to look — exactly as the previous three did, months apart.

### The hooks are accident protection, not enforcement

`pre-commit` (main guard, `SWFimported` guard, typecheck) and `pre-push` (lint,
tests, `data:check`) are real and were each verified by triggering them. But
**`--no-verify` bypasses every local hook**, and so does any tool that commits
through a library rather than the CLI. They stop mistakes; they cannot stop
intent, and they are not a control.

The hooks now self-check: `pre-commit` compares the installed copy against
`NewVersion/.husky/pre-commit` in the working tree and refuses to run a stale
gate. That closes the drift the copy-install introduced — `prepare` covers
`npm install` but not a branch switch or a pull.

**The only real guarantee for `main` is server-side.** A GitHub ruleset blocking
direct pushes and requiring a PR is the one layer `--no-verify` cannot reach. It
was requested at the start of the project and never set up — the same gap as the
hooks, one layer further out, and it is account-level so it cannot be scripted
from here.

## Every viewport-dependent gameplay difference, in one place

Individually each entry below is documented and defensible. **Together they mean the
game plays materially differently on a phone than on a desktop**, and that aggregate
had never been looked at as a set. The project rule is that where the AS3 froze a
screen dimension into a constant, this port uses the live value (`CLAUDE.md`) — this
section is the standing cost of that rule.

The variable behind all of it is `logicalHeight` = `renderHeight / zoom`, clamped to
`[400, 1440]`. Width is always the 640 design width. A wide desktop window sits near
the 400 floor — which is the AS3's own stage height, so **desktop happens to
approximate the original and phones do not**.

| # | Mechanic | Desktop (~400) | Phone (~1385) | Status |
|---|---|---|---|---|
| 1 | **Weapon reach** — laser hits, magic retargeting gate on `worldView` | 640×400 | up to 640×960, room-limited | Deliberate. A faithful 640×400 rect would leave ~44% of the visible area unreachable on 375/405 levels. |
| 2 | **Off-camera spawn acceptance** | 60.5% of candidates | 28.9% | Deliberate. A taller window genuinely shows more room, so fewer positions are off screen. |
| 3 | **Off-camera search enabled at all** | 195 of 405 levels | 195 | Stable now. Was 0 on phones for one commit under a `<=` disqualifier. |
| 4 | **Height-equality disqualifier** | a level property | measure-zero | Faithful rule, effectively dead. A one-pixel resize flips it. |
| 5 | **Warning visibility / reaction time** | AS3-like | much longer | Emergent, unquantified. A taller view shows spawn warnings earlier. |
| 6 | **Enemies visible at once** | AS3-like | up to 2.4× the vertical band | Emergent, unquantified. |
| 8 | **Food-round border bounce** — Gummy Bear and Crazy Cheese reflect off the camera rect, not the room walls (`:1906`) | bounce box ≈640×400, close to the original | bounce box up to 640×1385 | Deliberate, and **faithful**. `:1906`'s `roomWidth` terms cancel exactly, leaving the visible window inset by the radius. On the AS3's fixed stage this was indistinguishable from a room-wall rule; here it is not. See C1 below. |
| 7 | **Grenade throw distance** — speed and friction both derive from the distance to the cursor | reach ≈755 (the 640×400 diagonal), speed ≈81 | reach ≈1570, speed ≈168 | Deliberate. See below. |

### 7, in more detail — added with the Grenade secondary

`PartGameArea.as:4042-4047` derives both launch speed and friction from
`shootDistance`, the world-space gap between the muzzle and the cursor. Nothing
about that is camera-relative, so **the distance itself needs no correction** —
it is measured between two world points and camera zoom never enters it.

What *is* viewport-dependent is how far the cursor can be. The AS3 could not
point beyond its 640×400 view, capping the throw at that diagonal; a tall
portrait viewport here roughly doubles it, and speed and friction rise together
with it. A grenade thrown across a phone screen is genuinely faster and
decelerates harder than any the original could produce.

This is the same trade as rows 1 and 2 and is accepted on the same grounds: you
can throw as far as you can point, and a fixed 755-unit cap would put a hard
ceiling in the middle of a view the player can see into. Recorded here rather
than argued at the call site, per the standing rule.

**Separately, one AS3 correction is deliberately not ported at all.**
`:4032-4038` shortens a throw aimed below `400 - cameraPosY` — the world Y of
the bottom edge of the play area, because the Flash stage is 640×480 with an
80-pixel HUD strip below the game view. It exists so aiming *into the HUD* lands
the grenade at the bottom of what you can see. The port's HUD is DOM floating
over the canvas, and `pointerWorldPoint` is always inside `worldView`, so the
condition is unreachable. Reproducing it would leave a branch no player can
enter. Reasoning is at `weapons/grenade.ts`'s `throwGrenade`; this is the only
place so far where "use the live value" would have produced a permanently false
test rather than the right answer.

**Not yet examined:** 5 and 6 are consequences of the same variable but have not been
measured. Difficulty is currently hardcoded to Easy, so no balance work has been done
against either.

**Nothing in this table has been observed on a phone.** The port targets iOS/Android
via Capacitor and has never been opened on one. Two of the six entries were defects
found by accident; a desktop-only pass is structurally unable to find the rest,
because desktop sits at the one viewport height where the port matches the original.

## Fixed-camera assumptions in a dynamic-camera port

A recurring class, worth its own heading because it has now caused one shipped
bug and one shipped regression, and both looked faithful when read.

The AS3's camera was **a fixed 640×400 Flash stage**. This port's is
**640 × `logicalHeight`**, where `logicalHeight` is `renderHeight / zoom` clamped
to `[400, 1440]` (`config/viewport.ts`). Any AS3 expression involving the camera
is therefore a *constant* there and a *variable* here, and porting it term for
term preserves the arithmetic while silently changing what it means.

Two instances so far:

1. **The off-camera spawn search compared against 640×400.** Faithful predicate,
   wrong operand — the protected rectangle was up to 320 units shorter than the
   real viewport, so >20% of "off-camera" placements were on screen. Fixed by
   requiring the live viewport on `PlacementContext`; omitting it is now a
   compile error.
2. **The `roomWidth == cameraWidth || roomHeight == cameraHeight` disqualifier
   was widened to `<=`**, justified as "identical on every room size the AS3
   could produce". That justification reasons in the AS3's world about a change
   that only matters in this one. It disabled the search on **all 405 levels at
   any logical height ≥ 720** — i.e. everywhere on a phone. Reverted to `==`.
   The two axes are independent: a 900-wide room in a 640-wide camera keeps
   28.9% of candidates valid at any height, and the "camera covers this
   dimension" case needs no guard because a negative margin widens that band
   past the room and the test falls through to the other axis on its own.

**Known divergence, deliberate.** With `==` restored the structure is faithful,
but two properties are now viewport-dependent where the original's were fixed:

- **The acceptance rate varies.** In a 900×720 room, 60.5% of candidates are
  accepted at a 640×400 viewport and 28.9% at 640×720 or taller. A taller window
  genuinely shows more of the room, so fewer positions are off screen. This is
  the honest physical consequence, not a defect.
- **The height-equality disqualifier is effectively dead.** It fires only when
  `logicalHeight` exactly equals a room height — a measure-zero coincidence with
  a continuous viewport, where in the AS3 it was a static property of a level. A
  one-pixel resize flips it. Pinned in `offCameraSpawn.test.ts` so the behaviour
  is recorded rather than discovered.

**Before porting any other camera-derived expression, ask whether the AS3 value
was constant.** If it was, the port needs the live value and probably needs it
to be non-optional.

## One rule, two copies — the tested one unused

**Read this before the dead-module list below.** It is a worse failure than dead
code, and it is easy to mistake for it.

In each case a helper exists, is exported, and has real tests. The caller does not
call it — it reimplements the same rule inline. So there are two copies of one
rule, a green test guards the copy that never runs, and the copy that *does* run
is unguarded. Dead code is inert and honest. This actively misleads: the suite
reports the behaviour as covered, and the two copies can drift apart silently, at
which point the tests keep passing while the game does something else.

| Rule | Tested copy | Live copy |
|---|---|---|
| Crowd count within a flame radius | `weapons/flames.ts:120` `countCrowd`, 3 tests | `GameplayScene.ts:938-943`, same `Math.hypot(...) < FLAME_CROWD_RADIUS` loop written out |
| Whether the player can afford an upgrade | `upgrades/upgradeState.ts:86` `canAfford` | `UpgradesScene.ts:101`, `cost !== null && state.money >= cost` |
| Flag payout | `waves/flag.ts:155` `flagReward` | `GameplayScene.ts:1386`, `spec.flagMoney` inlined |

None is currently divergent — checked at the time of the audit. That is the point:
they agree *now*, nothing enforces that they keep agreeing, and the mechanism that
would normally catch it (a failing test) is pointed at the wrong instance.

`npm run knip` surfaces these as unused exports, which reads as "safe to delete" —
the opposite of the correct action. Deleting the tested copy leaves the live copy
untested; the fix is to call it.

## The knip canary has now fired five times, always correctly

Worth naming as a pattern rather than five incidents, because a future session that
hits it should recognise it as the mechanism working rather than an obstacle.

`scripts/knip-canary.test.mjs` asserts that a named set of exports — and, until D1, one
whole *file* — remain unreachable. It exists because a misconfiguration once made knip
blind to exactly the ported-but-unwired functions it was added to find. Its assertions
are deliberately the kind that go stale: each one is true only until the thing it names
gets wired.

It has fired on `discoverEnemies`, on `countMaxedPrimary`/`getAchievementTiers`, on
`applyFreeze`, and most recently on `PM_PRNG.ts` when `backgroundProps.ts` imported it.
**Every one was a genuine wiring event, not a tooling failure.** Each time the assertion
was *inverted* rather than deleted, so the reverse regression — an importer removed and
the module going quiet again — still fails.

If it fires: check whether the named thing acquired a real consumer. If it did, invert
the assertion and note why. Deleting it is only correct if the symbol itself is gone.

## Deliberate content divergences

Distinct from the viewport divergences above, which are consequences of a
different camera. These are places where the port **plays something the
original did not**, by decision.

### Spawn placement is deterministic; the AS3's is not

`spawnWarnings` draws every placement value from **unseeded `Math.random()`** —
`randomNum`, `randX`, `randY`, `warning.wall`, `warning.x`, `warning.y`. The same level
played twice in the original spawns enemies in different places.

The port seeds `spawnRng` from a string key per level (`GameplayScene.ts:1075`), so a
level's spawn pattern is fixed and repeats exactly.

**Why accepted:** reproducibility. A spawn-related bug is otherwise unreproducible, and
"did my change move the spawns" is unanswerable. It was a deliberate departure taken for
debuggability, not an attempt at fidelity.

**The cost, stated:** the original's run-to-run variety is gone. A level plays the same
way every time, which is a different feel over a long session even though no single run
looks wrong. **If faithful spawn behaviour ever becomes a goal, this is one of the two
places to revisit** — and note that "make it faithful" here means making it *random
again*, not seeding it from `LevelSpec.seed`, which would swap one invented determinism
for another (see D1's correspondence finding).

### `spawnPickups` was added content — **removed**

`GameplayScene.spawnPickups` laid a fixed board of eight decorative coins at level
start. **The original had no counterpart.** `spawnMoney` is called only on enemy death
(`:6844`, `:6848`) and on flag pickup (`:2589`) — money exists in the AS3 only as a
drop, never as scenery.

**Deleted**, along with `Pickup.ts`, `collectPickups`, `collect` and the physics group.
It was recorded here as an accepted divergence for one pass; that standing did not
survive contact with its own history. It had already caused a real defect — `levelOutcome`
was fed `moneyOnFloor: this.pickups.countActive(true)`, counting decorative coins rather
than enemy drops, so **no level could hand over at all**. Added content that has already
produced a total failure is not a divergence with a stated cost; it is scaffolding that
outlived its purpose.

Nothing depended on it: no achievement (the two that once keyed off it, `first-coins`
and `clear-board`, were invented demo scaffolding and were removed earlier), no test
asserting coin-board behaviour, and `currency:earned` has five other producers so the
event path it was demonstrating survives.

**One real consequence, stated:** the board was worth 8 x 5 = 40 currency per level of
free income. That income is gone. Enemy drops pay out directly in `removeEnemy`, so the
economy still works, but every level is 40 poorer than it was.

**Not retired with it:** `moneyOnFloor: 0` in the level-outcome call. That hardcoded
zero is correct because **`ItemMoney` is unported**, not because the coin board existed
— deleting the board does not discharge it. It comes out when enemy money drops become
collectable objects rather than a direct payout.

*(Both of these were nearly filed under "Faithful, and easy to mistake for a defect".
That would have been wrong in the way that section is most dangerous: it tells a
reviewer "we checked, this matches the original" — and neither of these matches the
original. They are departures, and they belong here with their costs written down.)*

### World 1 Normal/Flag rooms standardised to 800x600 (27 July 2026)

World 1's nine Normal and nine Flag levels shipped at three sizes — 640x400,
800x600 and 900x720. All eighteen now play at 800x600, which is 1-4's room and
was already the size of six of them. Tower, Boss and Defense (27 of world 1's
45) are untouched: their sizes are tied to how those modes play.

Twelve levels actually change. Two accepted consequences:

- **Density moves, and enemy counts do not.** The nine shrinking from 900x720
  lose 26% of their area and get ~35% denser; the three growing from 640x400
  gain 87% and get ~47% sparser. Signed off explicitly as a balance change.
- **Off-camera spawning switches on for 1-1, 1-3 and 1-30.** The disqualifier
  fires when `roomHeight === cameraHeight`, and nominal camera height is
  clamped to exactly 400 — so every 640x400 room had the search disabled and
  its enemies entered at the visible edge. At 800x600 they arrive from off
  screen. This is the most visible behavioural effect.

**A third consequence, found only when props were drawn (T14).** Anything the AS3 scales
by *room area* is scaled up with the room, and nobody had looked at that class as a class.

Background prop count is the demonstrated case. `createBackground` derives `amount` from
`tileCountX * tileCountY` where a tile is 256 units (`:1135`, `:1244`), so 640x400 gives
`3 x 2 = 6` tiles and 800x600 gives `4 x 3 = 12`. **World 1's standardised levels place
exactly twice the props the extraction's dimensions would.** The formula is faithful; the
operand is the standardised room.

**This is not being patched, deliberately.** Scaling `minAmount`/`maxAmount` down would
fix a symptom of the room decision by putting a compensating error inside
`createBackground`'s arithmetic — the prop count would then match neither the source nor
the room, for a reason recorded in a different file from the thing that caused it, and
every future comparison against the AS3 gets harder. If the density is wrong in play, the
honest fix is revisiting 800x600, not the formula.

**What else is area-proportional has not been surveyed.** Prop count is simply the first
one that became visible. Any AS3 quantity derived from `roomWidth`/`roomHeight` — spawn
counts, terrain features, anything tiled or per-unit-area — is affected on the same
twelve levels by the same factor, and none of it has been checked. That unexamined set is
the real cost of the standardisation, and it is recorded here rather than in each
subsystem so the cost is visible in one place.

**The fidelity check was strengthened, not relaxed.** `LEVELS` remains a pure
transcription of `ScreenGame.as` and is still asserted to match it exactly;
the overrides are applied in `getLevel`, so what the game plays is checked too.
An override must name the source value it replaces, so it excuses only the
divergence it predicted — a re-extraction that changed 1-2 away from 900x720
would fail rather than be masked. Four further tests stop the table rotting: no
no-op entries, no stale entries, nothing outside world 1 Normal/Flag, and an
exact count of twelve.

Table: `src/game/levels/levelSizeOverrides.ts`. Tests:
`src/game/levels/roomSizeSource.test.ts`.

## Open decisions

Distinct from *Held, not fixed*. A hold is "we will do this later"; an open
decision is **two incompatible options where picking neither is itself a

### D1 — Which RNG lineage owns level layout?

**Status:** **DECIDED — Option A**, after being deferred twice (most recently 27 July
2026). See *The decision, and what it actually costs* at the foot of this entry, which
also records why A is not the separable RNG change it was described as.

**The situation.** The port runs two random number generators with no boundary
between them.

- `core/PM_PRNG.ts` is a faithful Lehmer port of the original's generator,
  tested against BigInt over 35k draws on 7 real level seeds. It has **zero
  non-test importers**.
- `GameplayScene` (`:1075`, `:3324` — the entry originally cited `:607`/`:1789`,
  which T1-T7 moved) uses `Phaser.Math.RandomDataGenerator` seeded from **string
  keys**, not from the level table.
- `LevelSpec.seed` is extracted from `levelDataModel[...][9]` and **read by
  nothing**.

So the reproducibility-critical module is unreachable, the value it exists to
consume is unused, and a different generator has already been chosen at the
sites that place things in the world. That is a decision that has been made in
practice without being made on purpose.

**Option A — restore the original lineage.** Wire `PM_PRNG` to `LevelSpec.seed`
and route layout randomness through it.

- Gets: the original's exact background-prop placement, per level, reproducibly.
  Bug reports become replayable, and a screenshot of the SWF can be compared
  against the port directly.
- Costs: every site that currently draws from `RandomDataGenerator` for
  *placement* has to move. The two known sites are in `GameplayScene`; more may
  appear as props land. `PM_PRNG`'s arithmetic is fragile by nature — its
  product reaches ~7.2e13 and `Math.imul`, `| 0` and `>>> 0` all destroy it —
  so anything touching it inherits that constraint permanently.

**Option B — drop `PM_PRNG` and standardise on Phaser's generator.**

- Gets: one generator, one seeding story, ~200 lines and a differential test
  deleted. Phaser's is seedable, so levels can still be deterministic — just not
  *identical to the SWF*.
- Costs: the original's layouts become unreproducible for good. Any future
  "does this match the Flash version" comparison of prop placement is off the
  table, and `LevelSpec.seed` should then be dropped from the extraction with a
  note saying why, rather than left as a column nothing reads.

**What makes this decidable:** whether faithful background-prop placement is a
goal of the port or not. It is not a technical question and does not get easier
with more tracing — both options are a day's work and neither is blocked.

**Do not "keep both."** That is the current state, and it is the one option with
the costs of A and the benefits of neither: a fragile module nobody runs, a
level column nobody reads, and layout that already diverges.

### The decision, and what it actually costs

**Option A**, decided rather than deferred a third time. The reason is the project's
own standing rule: the AS3 source is the spec, and seven consecutive porting tasks paid
that price deliberately. B is the honest choice in a port where faithful behaviour is
not a goal; that is not this port. The cost asymmetry settles the timing — A is two
call sites now and more as placement sites land.

**A is not a separable RNG change. It is the background-prop port.** That was
established by reading the source before wiring anything, and it is the finding that
matters most here, because the scope it replaced would have manufactured a reader and
called it fidelity.

#### The correspondence finding — the two live sites have no AS3 counterpart

`PM_PRNG` appears in **exactly three places in the entire AS3 tree**, all of them the
background-object subsystem:

| Line | Site |
|---|---|
| `:711` | `getRandomPointWithinCircle(randGenerator:PM_PRNG, …)` — helper |
| `:1184` | the **only** instantiation, inside `createBackground` (`:1102`) |
| `:2603` | `removeBackgroundObjectsColliding(randGenerator:PM_PRNG)` |

`randGenerator` is a **local** at `:1184`, so the lineage cannot leave
`createBackground`. Its one helper call is `:1408`, also inside it.

Against that, the two generators the port actually runs:

- **`spawnRng` (`GameplayScene.ts:1075`) — spawn placement.** The AS3 counterpart is
  `spawnWarnings`, which uses **unseeded `Math.random()` throughout** — `randomNum`,
  `randX`, `randY`, `warning.wall`, `warning.x`, `warning.y`. AS3 spawn placement is
  non-deterministic run to run. There is no PM_PRNG draw to be faithful to.
- **`spawnPickups` (`GameplayScene.ts:3324`) — decorative coins.** No AS3 counterpart
  at all. `spawnMoney` fires only on enemy death (`:6844`, `:6848`) and flag pickup
  (`:2589`); the original has no fixed coin board.

**So moving those two sites onto the PM_PRNG lineage would be wrong, not merely
unnecessary.** It would attach the faithful lineage to sites with no faithful
counterpart — the exact conflation D1 exists to resolve — and would manufacture a
"production reader" for `LevelSpec.seed` that reflects nothing in the original.
`LevelSpec.seed`'s only faithful consumer is `createBackground`, which is unported.

This is a negative result, and it cost a full pass to derive. It is recorded at length
so it does not cost another one.

#### The draw order the prop port must satisfy

One generator, seeded once per level, consumed in a fixed sequence:

```
:1184-1185  seed  ← levelDataModel[...][9]   (LevelSpec.seed)
:1246       amount = minAmount + round(nextDouble() * (maxAmount - minAmount))

per prop, in exactly this order — :1281-1288
  scale      = nextDouble()
  posX       = round(nextDouble() * roomWidth)
  posY       = round(nextDouble() * roomHeight)
  rotation   = round(nextDouble() * 360)
  stopAt     = nextDouble()
  typeNumber = floor(nextDouble() * (objectList.length / 2))   // only if randomOrder
```

`removeBackgroundObjectsColliding` (`:2603`) draws from the **same** generator and is
therefore **inside this sequence**, not beside it.

**Any divergence in draw order makes every position after it wrong.** A Lehmer
generator has no resynchronisation: one extra or missing `nextDouble()` shifts the
whole remaining stream, so a prop layer that is correct in every formula and wrong by
one draw produces a layout that matches nothing. That is the fragile part, and the
reason the order is written down before anyone starts rather than discovered by
comparing screenshots.

#### What this decision does *not* disturb

- **T1-T7 removed no blocker, because none existed.** The entry has always said both
  options were unblocked; the harness, the hazard-sweep extraction and the kill site
  are all irrelevant to it. The deferral was never technical.
- **Nothing is pinned against the current generator.** No test anywhere references
  `spawnRng` or `RandomDataGenerator`, so deciding this moves no test. The one reader
  of `LevelSpec.seed` is `levelProgress.test.ts`, asserting the 405 seeds are unique —
  a data-integrity claim that holds under either option.
- The generator itself needs nothing: `PM_PRNG.test.ts` asserts MINSTD's canonical
  opening terms and **Park & Miller's published check value** (the 10000th term from
  seed 1 is `1043618065`), which is ground truth independent of this repo *and* of the
  SWF. Earlier reports grouped this with `B1` as "needs a running SWF" — that was
  wrong. The generator is verified and the consumption order is readable.

**Landed (step 2 of 3):** `levels/backgroundProps.ts` — the layout maths, seeded from
`LevelSpec.seed`, which finally has the production reader D1 was decided to give it. No
rendering and no collision pass.

#### Visual fidelity is unverifiable here — same shape as B1

Stated before the work rather than discovered after. **Positions are provable; how it
looks is not.** The generator is verified against Park & Miller, the formulas are
readable, and the draw sequence is pinned against a hand-derived stream — so the port
can prove it places props *where the original would*. Nobody can put the port and the
SWF side by side to confirm the result, and no assertion in this repository can close
that. Treat "the layout is correct" as proven and "the layout looks right" as untested.

**Placeholder art is in place with the real frame counts** (1-16, read from the sprite
definitions in `assets.swf`), so the `stopAt` draw is exercised rather than collapsing
to a constant. A reviewer should not read the variant logic as untested — it is; only
the pictures are missing.

**One number disagrees with the art already.** `addBackgroundObject` declares
`maxFrames = 3` for `RedBloodCell`, but symbol 1465 has **1** frame. Flash clamps
`gotoAndStop` past the end, so it always showed frame 1 in the original. The port keeps
the AS3's 3 because that is what the arithmetic uses; it only matters once rendering
lands, and step 3 must clamp rather than trust the table.

#### Two findings from the step-2 read

- **`randomOrder` is dead, and that removes a draw.** `:1188` declares it `false` and
  nothing assigns it again — a function-local, so exhaustive rather than a name-grep
  floor. `typeNumber` is therefore always 0, the draw at `:1288` never executes, and the
  per-prop sequence is **five draws, not six**. Reading `:1281-1288` as the spec
  consumes one draw too many per prop and diverges from the second prop onward. The type
  still changes — by exhaustion, when index 0's count hits zero and the pair is spliced.
- **A ruleless type still burns the group roll.** `groupChance *= 1 / ((max - min) / 2)`
  is `0 * (1 / 0)` = NaN for a type with no group rule, so the comparison is false and it
  never clusters — but the draw at `:1370` happens regardless. Moving that roll inside
  the rule check would shorten the stream by one draw per prop.

**Still owed, and what discharges it:** the collision pass (`:2603`) draws one
`nextDouble() < 0.5` per colliding pair (`:2646`), so it is inside this sequence and its
draw count is data-dependent — **it must be pinned as "one draw per collision resolved",
never as a stream offset.** And the art: the 21 `BGObject*` clips embedded in
`assets.swf`, roughly 100 frames, needing an extraction step that is scoped but not
built. Order is deliberately step 2 -> 3 -> 1, so that when the art lands any wrongness
is unambiguously the art, the positions having already been pinned.

#### Step 1 landed — via a correction to a check, not to the repository

An earlier pass concluded the prop shapes were absent from the tree and that step 1 was
blocked on running JPEXS against `assets.swf`. **That was wrong, and the cause was a bug
in the check.** The list of required shape ids was written by a Python script on
Windows, so it carried CRLF line endings, and the shell loop testing
`[ -f "$id.svg" ]` was asking for `1483.svg` on every iteration. All 108 reported
missing. Re-run with line endings stripped: **all 108 present, zero missing.** The
inference built on it — that `shapes/` held only main-SWF art and the two files had
disjoint id spaces — was wrong for the same reason.

Recorded rather than quietly fixed, because the shape of the mistake is the useful part:
**a check that returns "not found" for every single input is far more likely to be
broken than informative.** It read as a clean, decisive negative result and was reported
as one. A single spot-check with `find` caught it one pass later.

(That pass also *claimed* to record the blocked status here and did not: the edit used a
string replace whose anchor had drifted, with no assertion on the result, so it silently
did nothing while reporting success. Same class of error — an unchecked operation
reported as done.)

**What landed.** All 21 clips resolve: every `DefineSprite` frame places exactly one
`DefineShape`, giving 109 distinct shapes, generated into `levels/propArt.ts` rather
than hand-listed. Frames that place nothing hold the previous shape — `Skeleton` has 16
frames from 12 placements. The shapes went into the **curated sync set**, not
`assets-authored/`: they are extracted art, and `assets-authored/` is for assets we
made. They load as `prop-<shapeId>`.

**The neutrality assertion did its job.** `the art cannot move a prop` passed unchanged
across the swap — the derived positions for seed 610309764 are identical and the
survivors are still an unmoved subset. Nothing reached past the collision pass. It was
written before the art existed precisely so the swap would be guarded rather than
reviewed, and it is the first thing in this port pinned ahead of the change it protects.

**`RedBloodCell` still disagrees with itself**, as predicted: the clip has one frame
where `addBackgroundObject` declares three. The extraction did not reconcile them and
must not. Now asserted against the generated map as well as the hand-read table, which
is the independent check that the table was read correctly.

**What real art does not close:** the visual-fidelity gap. Having the original shapes is
not having confirmed the result, and nobody can compare against a running SWF. That
entry stands.

#### The first bug found by looking, in a subsystem that was fully green

The props were rendered and looked wrong in three ways: they drifted over the terrain as
the camera moved, they overlapped constantly, and they read as roughly twice the size and
twice the number. **Three symptoms, four causes, and the suite was green throughout.**

- **Drift — an invented parallax.** The ground tile position was offset by
  `scrollX * 0.06` as a depth cue. `createBackground` puts the ground tiles *and* every
  prop in the same `bg` container (`:1145`, `:3551`), so nothing in the original moves at
  a different rate. Props were correct; the ground was wrong. Removed.
- **Size — a flat rasterisation.** Every prop SVG was rasterised at 96x96. They range
  from **10.8 to 107 units wide** and are not square, so a rock authored at 13.95x12.95
  drew at nearly seven times its size with its aspect destroyed. Now rasterised at 3x each
  shape's own authored size and drawn at that size.
- **Size again — the raw scale draw.** `scale` is never used raw: `:3529` onward maps it
  per type through eleven different affine transforms, most landing *near one* rather than
  near zero (`Rock` 0.60-1.10, `Dirt` 1.20-1.40, `Seastuff` 0.20-0.325). The port applied
  the 0-1 draw directly, flattening all eleven. `FuturisticLines` is `4 + scale * 0` — a
  constant 4, with the draw consumed and discarded, the same dead arithmetic as the Laser
  Cannon's spread.
- **Overlap — a collision pass reading invented numbers.** `:2617` takes the radius off
  the *rendered* sprite. The port computed it from a hand-invented `PLACEHOLDER_SIZE`
  table and the raw scale, so it ran and under-removed. Both operands now come from the
  art and the mapped scale.

**Density is the one that is not a bug.** The port's world-1 rooms are 800x600 where the
extraction says 640x400, so tiles go from 3x2=6 to 4x3=12 and `amount` doubles with them.
That is the room-standardisation divergence already recorded under *Deliberate content
divergences*, with a consequence nobody had seen until the props were drawn. Halving it
would mean either unwinding that decision or diverging from `createBackground`'s own
arithmetic — a design call, not a correction.

**Why this belongs next to the seam finding.** Every one of these is a rendering-layer
fault in a subsystem whose *maths* is pinned to a hand-derived stream and whose unit tests
number in the dozens. The layout was correct the whole time and stayed correct through the
fix — the neutrality assertion passed unchanged before and after, which is how we know
this was the right layer. What no test could see was what any human saw in seconds. The
seam survey found eight subsystems pinned at the unit and unpinned at the seam; this is
the same lesson arriving from the other direction, and it is the argument for looking at
the running game as a routine step rather than an occasional one.

**The visual-fidelity entry above is now half false and stays.** Nobody can compare
against a running SWF — that is unchanged. But the port itself can be looked at, and the
first time anyone did, it produced four findings.

### The third direction: unpinned numbers (T34, 4 August 2026)

The same lesson again, and the most uncomfortable version. **T34 changed every entity's
collision radius — up to 2.85x, across 112 consumers — and the full suite stayed green.**
2445 tests, and not one of them pinned a value.

The seam survey found subsystems pinned at the unit and unpinned at the seam. The visual
survey found subsystems pinned in maths and unpinned in rendering. This is the third:
**pinned in behaviour and unpinned in magnitude.** A rule can be correct, tested, reached,
and rendering correctly while operating on a number nobody ever checked — which is how
`26`, `46` and `58` survived from placeholder art to the present.

**The mechanism worth carrying, because it generalises past this project:** a test that
copies a constant out of the code it is testing cannot detect a wrong constant.
`tankMovement.test.ts` asserted the hull's per-frame turn was at most `10` — a literal
copied from `TANK_ROT_SPEED_MAX`, which was itself wrong against `Tank.as:25`'s 20. The
test passed for exactly as long as the bug existed and would have failed the moment
anyone fixed it. It now reads the constant, and a separate assertion pins the constant
against the AS3 value. **The assertion has to come from the source, not from the code.**

A citation is not a check either. All three wrong constants carried correct-looking
references to the AS3 lines that contradict them.

**And inert exports can hide correct values, not just absent subsystems.**
`TANK_RADIUS = 14` was in the tree, correctly ported, correctly cited, covered by its own
test — and reached by nothing, while production used a locally derived 29. This is the
`PM_PRNG` shape at value scale: the right answer present and unwired. When the knip
canary reports an unused export, "ported but not yet needed" is one reading; "the correct
value, sitting beside the wrong one in use" is another, and nothing distinguishes them
without looking.

There is exactly one save in this project with real play history, and it now

## The stale-server window, and what it costs the `verified` status

A dev server (PID 24316) started **23:41:56** and held port 5173 until **02:05**.

## Frame-order and timing divergences

Added with the ground-hazard weapons (T1–T6, `5b009e0`..`31602ab` — 8 commits of the
85 between `origin/main` and `31602ab`). Distinct from the viewport section above:
nothing here depends on screen size. These are places where the AS3's *ordering within
a frame* is either not reproduced, or not knowable from the extraction.

### A2. The results screen opens on the score, not the reveal — deliberate

**A divergence requested by the user, not a fix.** Recorded so nobody restores
the original ordering thinking it was a bug.

**What the AS3 does.** `ScreenStatus` builds one page stack —
`pagesArray = ["Standard", ...achievements, ...enemies]` (`:226`, `:408`,
`:427`) — and opens on the **last** page (`pageCurrent = pagesTotal`, `:431`).
The exits live on the Standard page only (`:939-960`), so a reveal cannot be
skipped, only walked back past. Its exits are **Play Again** and **Next Level**
(suppressed on the final level of the final world, or a medal-less defeat).
There is **no menu button and no level chooser** on that screen at all.

**What this port does now.** Opens on the results. The reveals are a pop-up
above the panel, dismissed with Continue, and a `Unlocked: …` line on the
results records what they said so the information survives dismissal — in the
original it could not be missed, because it was a page you walked through. A
**Level select** button is added beside Next Level and Replay.

**Why.** The original's order is coherent for a game where the reveal *is* the
reward. This port surfaces the score as primary feedback instead. It also
misread as a bug twice during development: a first clear shows "NEW ENEMY"
where a score is expected, and it cost two harness misdiagnoses.

**What did not change.** The reveal content, its order, and the page stack
itself are untouched — `buildStatusPages` is unchanged and still returns
results → achievements → enemies. Only where the reveal appears in the sequence
moved. `initialPageIndex` is kept as a named function rather than inlining `0`,
so the divergence has one place to be read and reverted, and
`statusPages.test.ts` asserts the new rule **against** the AS3's, so restoring
the original ordering fails loudly rather than silently.

**Found by looking.** The first attempt centred the pop-up, which covered the
title and the stats — defeating the entire reason for the change. The frame
said so; no test could have.

### A0. RESOLVED (T35, 4 August 2026) — the level-done gate

**Retired, not downgraded.** The port now reproduces the AS3's `levelDone` partition,
and the frame that proves it exists: `.look/p-06-after-level-00.png` shows the tank's
death blast throwing debris radially while every enemy sits at pixel-identical
coordinates across the next two frames. Under the old behaviour that debris would have
been frozen in the same place in all three.

**What the original actually does, which is not what the entry originally assumed.**
`levelDone` is set the instant a level resolves (`:2774`), and the loop keeps running —
but roughly half the frame is inside `if(!levelDone)` at `:2806`:

| stops | keeps running |
|---|---|
| `handleMines` `:2812`, `handleGround` `:2813` | `handleBullets` `:2804` |
| `moveTank` `:2816`, `tankAttack` `:2818`, `handleTankShield` `:2819` | enemy-bullet *flight* `:1492` |

The split is coherent: **everything that can act on the player stops, everything already

the naive-unpause hazard this entry warned about does not exist once the gate is right.

**The original never draws its results screen over a live scene.** `levelDoneFunction`
(`:667`) waits for the loose money to be collected, counts a 15-frame timer down, then
sets `Main.changeScreen = "Status"` — it leaves the gameplay screen entirely. So there
are *two* stages, and the port already models both: `outcome.result` is the AS3's
`levelDone`, and `outcome.finished` is the screen change.

**The `scene.pause()` at `:3121` was therefore in the right place all along** and is
kept. It stands in for the screen change. The defect was the window *before* it, where
the port ran everything and the AS3 runs about half — roughly 500ms, which is why it
took a 60ms capture to photograph.

**On defeat the tank is removed outright** (`:2781`) with a 150-radius blast queued, and
the shield with it. The port already did this. Driven specifically, since a destroyed
tank under an overlay was the state most likely to produce something absurd: enemies
freeze, enemy fire keeps flying and fades out without being able to connect, the death
blast resolves, and the overlay arrives on schedule.

**Implementation note.** The partition lives in `waves/levelDoneGate.ts` as a named
table with a line cite per entry, and the scene calls `shouldRun(system, levelDone)`
rather than repeating `!levelDone` at each site. `levelDoneGate.test.ts` drives that
function against a second independent transcription of `:2804-2842` — asserting the
table against itself would only prove self-consistency, and the pairing of system to
side is the thing that has to be right.

### A1. The laser's half-frame skew is not reproduced

`PartGameArea.update` runs `handleBullets` → `handleGround` → `tankAttack` →

The port runs one sweep (`hazardSweep.ts`) and both reads see the same beam. The

Accepted. Recorded at `hazardSweep.ts:23`.

### B1. `:7083` does not fire — resolved by testimony, unconfirmed by measurement

`:7083` would destroy any ice patch the laser beam crosses. **The port no longer feeds
it a beam**, so the laser leaves ice trails alone.

**Status: resolved, and the manner matters.** The port was wired *reachable* on a static
reading of the source. It was unwired on the **player's direct recollection of playing
the original**, where lasers do not destroy ice patches.

That is real evidence, and better than anything derivable from this repository — nobody
can read Flash's playhead timing out of an extraction. **It is not a measurement.** A
future reader must not upgrade it to one: no log was taken, no frame was inspected, and
the experiment below has still never been run.

**The reading that put a beam there, recorded because it will be rediscovered.**
`:7083` gates only on `currentFrame == 1`, where the enemy-collision site at `:5560`
checks `canDamage && currentFrame == 1`. `canDamage` is cleared in `handleBullets`
before `handleGround` runs, so including it at `:7083` would guarantee the branch never
fired — and omitting it reads as an author writing a branch he expected to fire. That
argument is why the port shipped it wired for two commits. **It was known, and it is
outweighed by someone having played the game. Do not re-wire on the strength of it
alone.**

Against it: `handleGround` only ever sees beams spawned on an earlier frame (A1), and
`BulletLaser` is a 4-frame auto-playing `MovieClip` (`assets.swf` character 259,
frameCount 4). If Flash advances a runtime-added clip's playhead before dispatching
`enterFrame`, every beam it sees is already at `currentFrame >= 2` and the gate never
passes. That is consistent with what the player remembers.

**The experiment that would confirm it — still specified, still unrun.** With a working
SWF and a debugger, in `handleGround` at `:7069`, log `theBullet.currentFrame` for every
`BulletLaser` in `bulletArray` on a frame **after** one was fired. Fire once and hold; do
not fire again. Every value `>= 2` across several shots confirms the branch is dead. Any
value of `1` means it is reachable — and then the port is wrong, not the recollection
necessarily, since a reachable branch could still be one a player never noticed.

**What to change if it ever comes back the other way.** In
`NewVersion/src/game/scenes/GameplayScene.ts`, in `updateHazards`, pass the live beam
instead of `null`. That needs an `activeBeam` field restored on the scene, assigned in
`fireLaser` and cleared at both of `updateHazards`' exits — it was removed when this
landed because typecheck flagged it as dead. `sweepHazards` needs nothing: the rule is
still implemented and still tested.

**What this change cost, and what it exposed.** Unwiring removed a real behaviour from
the game and **moved no test whatsoever** — 2275 passing before and after. `sweepHazards`
was thoroughly pinned; nothing pinned whether the scene ever *fed* it a beam. The T6
assertions read stronger than they were, and the gap is the same unit-versus-seam one
this document keeps recording. A narrow wiring assertion was added with this change.

**A1 is dormant while this stands.** It described the patch sweep and the freeze gate
reading beams from different frames; with only one read left there is no skew. It
becomes live again if `:7083` is ever re-wired.

## A survey pass got three things wrong, and the corrections matter more than it did

A call-graph survey reported that **enemies never shoot**, that **defeat is therefore
unreachable**, and that **nothing is saved**. The player, who runs this build, says all
three are wrong. They are, and the way each went wrong is the reusable part.

**"Enemies never shoot" — a truncated grep read as a whole result.** The search was
`grep -rn "enemyBullet\|EnemyBullet" src/game/ | head -4`, and the first four hits were
all `difficultyMultipliers.ts` because `config/` sorts before `scenes/`. Enemy firing is
fully ported and wired: `enemies/enemyFiring.ts` with its own tests,
`advanceEnemyBullets` called at `GameplayScene.ts:2770`, bullets classed
`EnemyBulletBasic` / `EnemyBulletTrap`. **`head` is not a filter, it is a truncation**,
and reading one as the other produced a confident absence claim about a subsystem with
its own test file.

**"Defeat is unreachable" — deduced from the above, and contradicted by this document.**
The *Doc contradictions* section already recorded that `GameplayScene.ts:548-551`'s
"losing is arithmetically impossible until shooting enemies are ported" is a **stale
comment**, and that `:1315` applies enemy bullet damage to the tank. The survey
contradicted a correct record that was already written down, in the same file it was
writing to. The same pass also observed contact damage dropping the tank to 65/100, which
makes defeat reachable regardless of bullets.

**"Nothing is saved" — settled: it saves. The claim was wrong, and so was a second one
drawn from the same read.**

Driven end to end: win a level, **wait past the hand-over delay**, reload.
`CircularTankSave1` is written, survives the reload, and the menu comes back reading
**"Continue — Level 2"**. Both claims below were produced by one premature dump —
storage read at the instant the last enemy died, while `outcome.finished` was still
counting down the post-win timer that gates `bankLevelOutcome`. Two seconds later the
write is there.

- ~~Nothing is saved.~~ It saves.
- ~~There is no route from a win to the next level.~~ There is: the menu's **Continue**
  button, which that check never got far enough to see.

**The third purely-timing failure of seven.** A sub-frame tap, a screenshot taken after
a radial burst had left the frame, and now a storage read taken before the thing that
writes it had run. All three shared a shape: *a fixed delay chosen without reference to
what the game was actually waiting on.* `npm run look` now captures a burst rather than a
single frame, and its `--save` mode reports storage at three points rather than one.

The original diagnosis is kept below, because the reasoning it used was sound and the
conclusion still wrong — which is the useful part.

**"Nothing is saved" — an instrument reporting a clean negative, for the fifth time.**
`localStorage` read empty after a win. The mechanism is right — `SaveStore` writes
`saveString` to `window.localStorage`, and `levelBanking.ts:167` calls `profile.save()`.
The most likely artefact is that the level was never properly exited: the only route out
is a `Menu` button that **`diagnostics` overlaps**, and the harness needed `force: true`
to click it, so the click may have landed on the wrong control. Not diagnosed further,
because the player reports saving works and that outranks the instrument.

**`enemyBulletSpeed` has a consumer.** The survey called it "a tuned stat for a system
that does not exist", drawing a parallel to `LevelSpec.seed` before D1. That parallel
dissolves entirely — enemy firing exists, so the stat is read.

**The pattern, now at five instances.** A CRLF-poisoned file list, a drifted string
replace, a sub-frame key tap, an unowned weapon, and now a truncated grep. Every one
produced a clean, decisive, wrong result from a tool that reported success. **A survey
built from searches is evidence about the searches.** Where a claim matters, drive it and
watch it, or read the code path end to end — and check whether this document already
answers it before asserting the opposite.

## How to read a DefineSprite's frames — method, not incident

**A frame is the accumulated display list, not the shapes placed on that frame.** Flash
keeps objects across frames: a `PlaceObject2` without `HasCharacter` is a *move* of
whatever already sits at that depth, and a frame that replaces one of two layers changes
only that layer. The first parser used for `propArt` and `particleArt` recorded "shapes
placed on this frame", which is a different thing and is wrong.

**It was latent in two subsystems before anything showed it.** Props and particles each
replace a single shape per frame, so "placed" and "displayed" happen to coincide there,
and both tables are correct. `ItemMoney` is the first clip whose frames layer a shared
body under a changing numeral, and the wrong model produced a coin ladder with a
4.2-unit Money5 against a 7-unit Money1.

**The tell was monotonicity.** A derived table that is not ordered the way the source
obviously intends is a *parser* question before it is a *data* question. Coin values
ascend, so their discs cannot shrink; enemy tiers ascend, so bosses cannot be smaller
than their base form. Whenever an extracted table has an obvious intended order, assert
it — `money.test.ts` and `enemyArt.test.ts` both do, and in the coin case that assertion
is the one that would have caught the parser rather than the data.

**The correct method**, for any future extraction:

1. Track `depth -> characterId`. Apply `PlaceObject2`/`PlaceObject3` (set when
   `HasCharacter`, otherwise leave the depth alone) and `RemoveObject`/`RemoveObject2`.
2. Snapshot the whole depth map at each `ShowFrame`.
3. Flatten nested sprites to `DefineShape` ids afterwards, not during.

`propArt` and `particleArt` were re-checked against the corrected parser and are
unaffected. **One latent finding survives**: `TankBody` frame 2 is `[4, 3]`, not `[4]` —
Tower mode adds a shape *over* the frame-1 body rather than replacing it. Nothing reads
it today because the port has no Tower-mode body switch; the warning is written at
`entities/tankArt.ts` beside `TANK_BODY_FRAMES`, which is where whoever wires one will
be standing.

## Unsourced polish — an open category

Invented presentation with no AS3 counterpart, added for feel and never recorded as
added. **It reads as faithful to anyone who did not write it**, which is what makes it a
category rather than a list of small choices.

The category exists because one instance caused a real bug hunt: a `scrollX * 0.06`
parallax on the ground tile made props appear to drift, and the complaint arrived as
"props are broken" while the props were correct and the ground was the invention. A
future session debugging a symptom near any of these should suspect the polish before the
mechanic.

Known instances — **not hunted, so treat this as a floor**:

- **Ground margin dimming.** The out-of-arena border is darkened because "with no border
  art in the extraction, the change in brightness is the only thing marking where the
  arena ends". Self-declared invention, still present.
- **Bullet render inflation.** `setDisplaySize(radius * 4)` — bullets are drawn at four
  times their collision radius so they "read at speed". Also self-declared. See the
  placeholder-art note below for why this one is a trap.
- **Ground parallax.** Removed in `b51c059`. Recorded here because it was invented,
  survived months looking faithful, and cost a diagnosis pass.
- **Prop variant brightness step.** Gone — superseded when real art landed in `c5bd4bf`,
  where the variant frame became an actual sprite frame instead of an opacity cue. Noted
  so a future reader looking for it knows why it is absent rather than assuming it was
  lost.

## Placeholder art is not a bug, and must not be compensated for

Two rows of the first visual survey are **consequences of placeholder art**, recorded so
nobody "fixes" them in the rendering layer:

- **Enemies and the player tank are near-identical bright green.** Both are tinted
  circles; the tank differs only by size and a blue centre. At a glance they are hard to
  tell apart. The fix is enemy art, not a different tint.
- **Bullets are nearly invisible** — radius 2, pale tint, easy to miss entirely in a
  frame while firing.

**Do not make bullets bigger.** They already carry a 4x inflation over their collision
radius (see unsourced polish above), so enlarging them further stacks invented polish on
invented polish — and the second layer hides the first, which is exactly how the parallax
survived. The honest fix is real art; until then the discrepancy between what is drawn
and what collides stays recorded rather than tuned away.

## Two ways this port can be misread, and both bit within one pass

`npm run look` drives the running game; **the two traps in operating it are findings
about the port, not about the tool**, and the next person to conclude "this weapon does
not fire" needs them. Full detail sits next to the command in `CLAUDE.md`:

- **A sub-frame key tap can be lost.** Input flags are read once per frame, so a
  down+up inside ~10 ms is never observed. This is **faithful** — see the entry below.
- **A secondary can fire invisibly.** Mine drops at the tank's own centre, under an
  opaque sprite. A frame taken on the press cannot distinguish "did not fire" from
  "fired underneath".

Both were reported as game findings before being diagnosed as observation artefacts.

## Code that looks wrong, is load-bearing, and invites the tidy-up that breaks it

Three instances found so far, months apart, in unrelated subsystems. Each looks like a
mistake, each is faithful, and **each is tempting to tidy in exactly the way that breaks
it**. A fourth should be recognisable in one line rather than re-derived.

**Broadened 4 August 2026.** The heading was "arithmetic that discards its own result",
which covered three instances that were all literally dead arithmetic. A fourth arrived
that is not arithmetic at all and belongs to the same family, so the category is now the
*hazard* rather than the syntax: **code a careful reader would improve, where the
improvement is the defect.**

### The coin magnet has no range limit, and must not acquire one

`handleMoney` (`:2155`) adds `2.5` toward the tank to every coin's velocity **every
frame, from anywhere on the map**. No proximity check, no acquisition radius. It reads
like a missing guard, and adding one is the obvious tidy-up.

It is load-bearing. `levelDoneFunction` (`:667`) holds the results screen while loose
money is on the floor, and the unlimited magnet is what guarantees every coin eventually
reaches the tank — i.e. that the wait *terminates*. A range-gated magnet looks more
sensible and hangs the results screen permanently on any coin that came to rest out of
reach. The level would simply never hand over, and it would happen only on drops that
scattered far, which is the worst possible failure distribution.

Pinned in `items/money.test.ts` by driving a corner coin 400 frames and requiring it to
arrive, with the reason stated at the assertion.

**The shape (original three):** an expression whose result is discarded, thrown away by a multiply by
zero, or rendered inert by NaN — *while still consuming a random draw or occupying a
branch*. The behaviour is correct as written. The tidy version is correct too, right up
until it changes how many draws were taken or which branch ran.

| Where | The arithmetic | Why it must stay |
|---|---|---|
| **Laser Cannon spread** (`:3938`) | `tower.rotation - spread/2 + random() * spread` with `spread = 0` | Evaluates to the turret rotation exactly. Once recorded as a reason the weapon "needed its own spread rule" — it is a no-op, and reading it as a mechanic cost a scoping pass. |
| **Prop group roll** (`:1370`) | `groupChance *= 1 / ((max - min) / 2)` = `0 * (1/0)` = **NaN** for a ruleless type | The NaN gives the right answer (never clusters) *and* consumes the right draw. Hoisting the roll inside the rule check keeps the behaviour and shifts every prop after the first ruleless one. **Verified: hoisting it fails six tests.** |
| **`FuturisticLines` scale** (`:3529` region) | `4 + scale * 0` | A constant 4. The `scale` draw is taken and thrown away. Simplifying to `4` is correct in isolation and wrong in sequence — the draw is part of the stream. |

**What to do when you meet the fourth.** Do not simplify it. Establish first whether the
discarded expression *consumes* anything — a `nextDouble()`, a branch that advances
state, a side effect in an argument. If it does, the arithmetic is load-bearing despite
producing nothing, and it goes in the table above with a comment at the site saying so.
If it genuinely consumes nothing, it is dead and can go — but say which you established
and how, because the two are indistinguishable by reading the expression alone.

The tell is a term that is provably zero, provably constant, or provably NaN, sitting in
an expression nobody would write that way on purpose. In this source that is a signal it
was left over from something, not that it is inert.

## Faithful, and easy to mistake for a defect

Seven places where the port looks wrong and is not. Each was verified against the AS3

- **C1. Food rounds bounce off the camera, not the room.** `:1906`. The `roomWidth`
  terms cancel exactly; `cameraPosX` is a negative container offset (`:707`), so the
  pair is the visible window inset by the radius. A round bounces with a thousand units
  of empty room beside it.
- **C2. Lava patches *grow* as they die.** `:7062`, scale `0.75` → `1.25`, and a patch
  drops from its spawn radius of 18 to 15 on its very first tick because `:1800` sets 18
  and `:7065` overwrites it.
- **C3. Ice bites for its full stat; lava for fifteen frames less.** One gate at
  `lifeTime > 15` (`:6200`), and only ice is spawned with `+15` (`:1789`, `:1795`).
- **C4. The Ice Ball deals no contact damage at all.** `explosion = false` (`:4187`)
  keeps it off the automatic blast path and `:5917` names it in the exclusion list of
  the direct-damage path that flag selects. Its hand-queued blast (`:5895`) is its only
  route to an enemy — including the one it just hit.
- **C5. A new Ice Ball throw re-arms every patch on the floor**, including the previous
  throw's. `:6208` compares the enemy's stamp against the scene counter's **live**
  value, and no patch carries an id. Diverges from a per-patch model only when a second
  ball is in flight over the first one's trail, which is why the wrong model survived
  review.
- **C6. Gummy Bear's 4× damage was unreachable for the entire port until `fad4cba`.**
  A bear escalates on bounce — `×3` into stage 2, `×4/3` into stage 3 (`:1951`) — and
  the port culled every bullet at the room edge, so it never bounced. **The weapon ran
  at a quarter of its intended damage, indefinitely, with no test failing and nothing
  visibly broken.** This is the strongest case in the repository for pinning ported
  rules against the source rather than against observed behaviour: no amount of playing
  the port would have revealed it, because the port was self-consistent.
- **C8. Kill Reload does not reload anything.** `:6849`. Every kill takes 2-11 frames
  off the **secondary** cooldown; the primary is untouched. It also does not bank — a
  kill with the secondary already off cooldown is worth nothing — so it shortens a wait
  rather than charging a weapon, which is not what the name promises.
- **C9. A contact suicide pays no money but still buys cooldown.** `:6849` sits outside
  the `noMoney` gate at `:6842`, so the one death that deliberately pays nothing is
  still worth 2-11 frames. Reads like a missing guard; is faithful.
- **C10. A lava-trail kill credits the player.** `:6282` sets the same `dead` flag a
  bullet does, from the ground-contact loop, so an enemy that dies to a patch thrown
  seconds earlier triggers everything a shot would — Kill Reload included. Ice trails
  never do, because they freeze and never damage.
- **C11. A prop that can never cluster still rolls for it.** `:1370` computes
  `groupChance *= 1 / ((max - min) / 2)`, which for a type with no group rule is
  `0 * (1 / 0)` = **NaN** — so `nextDouble() <= NaN` is false and it never clusters, but
  the draw happens. The NaN is load-bearing: it gives the right behaviour *and* consumes
  the right draw. Hoisting the roll inside the rule check keeps the behaviour and shifts
  every position after the first ruleless prop. Verified: hoisting it fails six tests.
- **C12. `RedBloodCell` asks for a frame it does not have.** `addBackgroundObject`
  declares `maxFrames = 3` (`:3596`); symbol 1465 has one frame, and Flash clamps
  `gotoAndStop` past the end. The port keeps 3 in the arithmetic — that is what the draw
  consumes — and clamps only at display. Reconciling the two tables either changes the
  stream or renders a frame that does not exist.
- **C13. Cracks collide with everything, despite a branch that says otherwise.** `:2633`
  excludes `BGObjectCrack` against non-Crack in both directions, and **no class of that
  name exists**. Confirmed two ways rather than on one reading:

  1. *Exhaustive search.* No file, and no `class BGObjectCrack` declaration, anywhere in
     `scripts/`. The three clips are `BGObjectCrackDesert`, `BGObjectCrackBlueDirt` and
     `BGObjectCrackConcrete`, and none of them extends a shared `BGObjectCrack` — each
     extends `MovieClip` directly, so there was no base class to test against either.
     The literal `"[object BGObjectCrack]"` occurs nowhere but `:2633`.
  2. *A control on the same line.* The idiom resolves through
     `Object.prototype.toString`, giving `[object ClassName]`. `BGObjectCrackDesert` and
     `BGObjectFuturisticSquare` are structurally identical — same top-level package, both
     `public dynamic class … extends MovieClip`, neither overriding `toString` — and the
     **FuturisticSquare test on the same line matches**, which is why that exclusion is
     live. So the mechanism works; only the name is wrong.

  The author appears to have meant "any Crack variant" and written a name that never
  existed. Cracks are removed by collision like anything else. Reproduced as written.
- **C14. The game can drop a very fast key tap — and so did the original.** Input is a
  latched flag set on keydown and cleared on keyup, polled once per frame, so a press and
  release that both land between two frames is never observed. That looks like a defect
  and is faithful: `Main.as:711` sets `space = true` on keydown, `:771` clears it on
  keyup, and `PartGameArea.as:3981` polls `if(Main.space)` once per frame inside
  `tankAttack`. Identical structure, identical vulnerability — and at the AS3's 30 fps the
  window is 33 ms, *wider* than the port's. **Not a fidelity bug, and not to be "fixed"
  by latching the event**, which would make the port accept inputs the original refused.
  Established by comparing both handlers, after a 10 ms scripted tap was mistaken for a
  weapon that would not fire.
- **C7. Fire drain stacks per flame; lava damage does not.** Both in the same file. The
  drain sits in the bullet loop with no dedup (`:7078`), so two flames on one patch
  drain it twice; `onLava` (`:6250`) is deduped per frame. Opposite rules, both faithful.
