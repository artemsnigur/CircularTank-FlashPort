# Full-project audit — July 2026

A read-only audit of every unit in the port, run across all 13 `PROGRESS.md`
categories. Written down because it took seven parallel sweeps plus independent
re-verification to produce, and none of it is re-derivable from a green test run.

**Status of this document:** findings are as of commit `d390ce0`. Items marked
**[FIXED]** have been addressed since; everything else stands. Nothing here was
observed in a running game — see [Verification status](#verification-status).

## Method

Seven read-only agents, split by `PROGRESS.md` category, each establishing four
flags per unit with a `file:line` citation for every claim:

- **exists** — the module is there
- **tested** — it has tests that assert real behaviour
- **wired** — it has a call site outside its own test file, *and* that caller is
  reachable from a runtime entry point, *and* the export is actually called
  rather than merely imported
- **verified** — it has been seen working in the running game

`verified` is never assignable from reading code — only play can set it — and it
was unknown for every unit here when this was written. Three items have since
been observed and are recorded in
[Verification status](#verification-status), each naming the commit it was seen
against; that requirement exists because a `verified` granted against a stale
dev server is indistinguishable from a real one. It remains unknown for the
large majority of modules.

"Wired" was established by following aliases and renamed destructures to a
runtime entry point, not by name-grep — per the rule in `CLAUDE.md` about
`enemyModel` column 1, which was wrongly declared dead because its only read
went through a renamed working copy.

Baseline at time of audit: `npm run typecheck` clean, `npm run lint` clean,
`npm run data:check` green, `npm test` 62 files / 1327 tests passing. Every
defect below was present underneath that green suite.

## Critical — breaks play

### 1. All 45 Boss levels auto-win without spawning anything **[FIXED — 8001772]**

> Fixed by deriving `bossAmount` from the level composition (`bossCountFor`, the
> port of `getBossCount`) and making it `createWaveState`'s default, so a caller
> cannot omit a value it never has to pass. Wiring-seam tests added and confirmed
> failing against the old default. **Verified on screen** — the reviewer reached
> 1-9, saw the boss spawn, damaged it, killed it, and the level ended. Observed
> against >= d3c02cd, which postdates this fix; see the stale-server section.

The first Boss level is **1-9**, the ninth level of the game, and `LevelSelectScene`
pins world 1. This is not an edge case.

- `GameplayScene.ts:606` calls `createWaveState(spec)` and omits the second argument
- `waveState.ts:65` — `createWaveState(spec: LevelSpec, bossAmount = 0)` defaults to **0**
- `waveState.ts:269` — `bossAmountKilled >= bossAmount` → `0 >= 0` → **complete on frame 1**
- `waveState.ts:108` — `bossAmount <= bossAmountKilled` → `canSpawn` false forever, **nothing spawns**
- Nothing anywhere in `src/` computes a boss count

The AS3 derives it in `ScreenGame.as:703-716` (`getBossCount`), summing `count` for
every composition entry whose level is `"B"`. That data survives the extraction —
level 1-9 carries `{ type: "Basic", level: "B", count: 1 }` — and is never read.

**Why the suite was blind:** every Boss test passes `bossAmount` explicitly
(`flag.test.ts:144`, `flag.test.ts:185`, `waveState.test.ts:83`). The module was
correct; the scene fed it wrong. This is `CLAUDE.md`'s documented failure mode
verbatim.

Mode counts across the 405 levels: `Normal 90, Flag 90, Tower 90, Defense 90, Boss 45`.
World 1 Boss levels: 9, 18, 27, 36, 45.

### 2. Music can never play **[FIXED — db708b9, VERIFIED on screen]**

> All five defects fixed as one unit. Menu music confirmed playing by the
> reviewer against current code, after the stale server was killed — the first
> observation in this document made against a provably current server.

`SoundManager`'s SFX path is genuinely wired — 17 runtime call sites covering weapon
fire, impacts, enemy death, coin pickup, flag capture, contact damage, weapon change
and purchases. Music is not.

- `PreloadScene.ts:140` — `installSoundManager(this)` binds `PhaserAudioBackend` to
  **PreloadScene**
- `PreloadScene.ts:147` — `this.scene.start(SceneKeys.MainMenu)`, seven lines later,
  shuts that scene down
- `PhaserAudioBackend.requestLoad` (`:33-44`) reaches for `this.loaderScene.load` —
  a torn-down scene's loader
- Its `loadInFlight` guard is cleared only by listeners registered on that same dead
  loader, so every subsequent request early-returns
- `SoundManager.startCrossfade` deliberately retries "next frame" — a retry that can
  never succeed

Near-miss worth knowing: `112_MusicMenu.mp3` **is** decoded during preload, under key
`music-menu` (`manifest.ts:83`), while the manager looks for `snd:112_MusicMenu.mp3`.
Two naming schemes for one file in one cache.

Also: 5 of 8 tracks (`Normal`, `Flag`, `Tower`, `Defense`, `Boss`) have no call site
at all. Per-level-mode music is not wired.

### 3. Every level plays at the wrong size **[FIXED — 9a25f25]**

> Fixed by resolving the level spec at the top of `create()` and taking
> `roomWidth`/`roomHeight` from it. This also revived the off-camera spawn
> search on **195 of 405** levels; `spawnPlacement.ts` needed no change, as its
> guard was already a faithful port of `PartGameArea.as:7245` and only its input
> was wrong. **Verified on screen** — room sizes visibly differ between levels.
> Observed against >= d3c02cd, which postdates this fix.

`LevelSpec.roomWidth` / `roomHeight` are extracted for all 405 levels and asserted in
`levelProgress.test.ts:67-72` — and read by **no runtime code**. `GameplayScene.ts:113-114`
hardcodes 640×960. Level 1-1 should be 640×400; level 1-2 should be 900×720.

This is also the root cause of a dead subsystem: `spawnPlacement.ts:70` disables the
off-camera spawn search when `roomWidth === cameraWidth`, and `CAMERA_WIDTH = 640`
(`spawnPlacement.ts:24`) equals the hardcoded `ROOM_WIDTH = 640` for every level. So
`canSearchOffCamera` returns false unconditionally, the 25-attempt search at `:146-155`
never runs, and **every enemy in the game enters from a wall**.

## E1. Every entity size was invented — corrected 4 August 2026

**Every difficulty judgement anyone made while playing this build before 4 August
2026 was made against wrong collision numbers.** That is the headline, and it is
why this sits here rather than inside the art commit that fixed it.

The AS3 sets `enemy.radius = enemy.width / 2` (`PartGameArea.as:3318`) — the authored
sprite width *is* the hitbox, per type. The port drew every enemy as a tinted circle at
one invented diameter, 26 for all normal types and 46 for all bosses, and took the
radius from that. The tank used 58.

| | AS3 | port before | ratio |
|---|---|---|---|
| Normal enemy radius | 4.5 – 13.5, per type | 13, flat | 0.35x – 1.04x |
| Boss radius | 20.5 – 65.5, per type | 23, flat | 0.89x – 2.85x |
| Tank radius | 14 (`Tank.as:23`) | 29 | 2.07x |

Contact damage sums the two radii, so a `Basic` reaching the tank triggered at
`29 + 13 = 42` units where the original triggers at `14 + 8.5 = 22.5` — **1.87x the
intended range, on every level, for the whole project**. `DamageAddictBoss` was drawn
and collided at a third of its intended size; `Tiny` at nearly three times.

**Three separate constants, three separate causes.** They are worth keeping apart,
because only one of them is the kind of mistake a citation would have caught:

1. **`TANK_DIAMETER = 58`** — a diameter/radius conflation, confirmed arithmetically
   rather than assumed. The authored `TankBody` is 29 wide. 29 read as a *radius* and
   doubled gives exactly 58; no other reading produces it. The port then took
   `58 / 2 = 29` back out as the radius, so both the sprite and the hitbox carried the
   doubling.
2. **The enemy diameters** — not a conflation, simply invented. 26 and 46 reconcile
   with no authored width. They were placeholders that outlived the placeholder art.
3. **`TANK_ROT_SPEED_MAX = 10`** — a transcription error against `Tank.as:25`'s 20,
   found while deriving expected values for the rotation tests. It carried a correct
   citation to the line that contradicts it, and `tankMovement.test.ts` asserted the
   step size by copying the same wrong literal, so the test could not tell a correct
   step from a halved one.

**`TANK_RADIUS = 14` was already in the tree, ported and tested, and reached by
nothing.** `player/tankDamage.ts:29` carries the correct AS3 value with the right
citation; production read `PlayerTank`'s locally derived 29 instead. This is the
"exists + tested but not wired" pattern again, and the most uncomfortable instance so
far, because the correct number was sitting beside the wrong one the entire time.

**The full suite stayed green across the change.** 2445 tests, and not one of the 112
`radius` consumers pinned a value. That is the finding behind the finding: the numbers
were unpinned, which is why they could be invented and stay invented.

### What was checked afterwards

Every post-swap radius was reconciled against `width / 2` read back out of the
exported SVG — not against the new table, which would only prove self-consistency.
All 40 reconcile exactly; none needed rounding. `enemyArt.test.ts` drives that
reconciliation on every run, so a transcription slip in the table fails rather than
becoming the new truth.

The tank is the exception and is deliberately *not* derived: `Tank.as:23` hard-codes
14 against a 29-wide body, i.e. half the width less the 0.5-unit stroke. Deriving it
would give 14.5 and silently diverge, so the constant is imported from `tankDamage.ts`
and the test asserts both readings — that it is 14, and that the body is not 58.

## E2. Half the deaths in the game were silent — corrected 7 August 2026

**A behaviour fix, not a sound-coverage entry**, which is why it sits here beside E1
rather than in the trigger bookkeeping. It changes *which deaths produce a death
sound*, and it was wrong for every contact suicide in the port's history.

**What the AS3 does.** `PartGameArea.as:6861-6868`, inside `if(dead == true)`:

```
if(!bottomCollision) { push("EnemySquish") }
else                 { push("BottomCollision") }
```

Two facts in that shape, and the port had both wrong:

1. **It is an either/or**, so a death sounds exactly one of two names.
2. **It sits *below* the `noMoney` gate at `:6842`** and below the KillReload block
   at `:6850` — so it is **not conditional on the death paying out**. Every death
   sounds, including the contact suicides that deliberately pay nothing.
   (Same structural point as **C9**: `:6849` also sits outside that gate, which is
   why a suicide still buys secondary cooldown. Two rules, one boundary.)

**What the port did.** `GameplayScene.removeEnemy` queued `EnemySquish` *inside*
`if (payMoney)`, alongside the kill count. Contact deaths pass `payMoney: false`
— a suicide attack is not a kill and pays nothing — so **they died in silence**.

On level 1-1 that is most of the level: the T37 baseline records "two kills, ten
enemies. The other eight reached the tank and died on contact." Eight of ten
deaths made no sound, and nothing looked broken, because the two that did sound
were the two the player shot.

**And it made a second name unreachable.** `BottomCollision` is the `else` branch
— the sound for exactly the deaths that pay nothing. Gated behind `payMoney` it
could never fire, on any level, ever. It had been filed as "scenario reach: the
sweep never visits Defense", which was wrong twice over: driving Defense would
not have produced it either.

**The fix.** The queue moved out of the `payMoney` block and became the either/or
the source has, with `removeEnemy` taking a `bottomCollision` flag that the
Defense line-breach site passes `true`. `this.kills += 1` stays inside `payMoney`
— that part was always right, and conflating the two is how this happened.

**Why it survived.** The sound was correct for every death anyone was *watching* —
you hear the enemies you shoot. The silent ones are the ones that reach you, where
the tank-damage flash and the health bar are what the player is reading. No test
covered it: the suite pins `removeEnemy`'s counting and money behaviour, and
nothing asserted that a death makes a noise.

**Pinned** in `audio/deathAndStatusSounds.test.ts` as a pair — `EnemySquish` and
`BottomCollision` are asserted to be an either/or over one death, never both and
never neither, because a port that queued both would satisfy either assertion
alone.

this codebase has been enforced pre-emptively. That makes the *asserted* column a
ranked prediction of the next bugs rather than a documentation backlog — it is the

### Knowing the rule does not prevent breaking it

Worth recording because it is the strongest evidence for the section above.
Three corrections in a single round were each one of the patterns catalogued
here, reappearing **inside the fix for that pattern**, with the rule freshly
written and in context:

- A **substituted denominator** — "4% → 100%" for the filename check, where 100%
  required redefining the total from "every extracted file" to "every named
  file". Committed in the change addressing partial enforcement.
- An **unverified assertion** — "this retires three knip entries", stated without
  running knip, and false. Committed in the change addressing unverified
  guarantees.
- A **self-check on the weak gate only** — `pre-commit` verified itself,
  `pre-push` did not, leaving the gate that carries lint, the full suite and
  `data:check` as the unprotected one.

None was caught by the rule existing. All three were caught by a reviewer asking
a direct question. The conclusion is not "be more careful": it is that every
entry in the enforced column was built after a defect *because* knowing a rule
does not prevent breaking it. **Where a rule matters, it needs a mechanism even
when the person applying it wrote the rule down minutes earlier.**

Which points at the obvious gap: **this sweep itself has no mechanism.** Nothing
re-runs it, nothing greps for new present-indicative claims, and nothing fails
when one is added. The next asserted guarantee someone writes goes uncaught until
a human happens to look — exactly as the previous three did, months apart.

### The hooks are accident protection, not enforcement

`pre-commit` (main guard, `SWFimported` guard, typecheck) and `pre-push` (lint,
tests, `data:check`) are real and were each verified by triggering them. But
**`--no-verify` bypasses every local hook**, and so does any tool that commits
through a library rather than the CLI. They stop mistakes; they cannot stop
intent, and they are not a control.

The hooks now self-check: `pre-commit` compares the installed copy against
`NewVersion/.husky/pre-commit` in the working tree and refuses to run a stale
gate. That closes the drift the copy-install introduced — `prepare` covers
`npm install` but not a branch switch or a pull.

**The only real guarantee for `main` is server-side.** A GitHub ruleset blocking
direct pushes and requiring a PR is the one layer `--no-verify` cannot reach. It
was requested at the start of the project and never set up — the same gap as the
hooks, one layer further out, and it is account-level so it cannot be scripted
from here.

## Every viewport-dependent gameplay difference, in one place

Individually each entry below is documented and defensible. **Together they mean the
game plays materially differently on a phone than on a desktop**, and that aggregate
had never been looked at as a set. The project rule is that where the AS3 froze a
screen dimension into a constant, this port uses the live value (`CLAUDE.md`) — this
section is the standing cost of that rule.

The variable behind all of it is `logicalHeight` = `renderHeight / zoom`, clamped to
`[400, 1440]`. Width is always the 640 design width. A wide desktop window sits near
the 400 floor — which is the AS3's own stage height, so **desktop happens to
approximate the original and phones do not**.

| # | Mechanic | Desktop (~400) | Phone (~1385) | Status |
|---|---|---|---|---|
| 1 | **Weapon reach** — laser hits, magic retargeting gate on `worldView` | 640×400 | up to 640×960, room-limited | Deliberate. A faithful 640×400 rect would leave ~44% of the visible area unreachable on 375/405 levels. |
| 2 | **Off-camera spawn acceptance** | 60.5% of candidates | 28.9% | Deliberate. A taller window genuinely shows more room, so fewer positions are off screen. |
| 3 | **Off-camera search enabled at all** | 195 of 405 levels | 195 | Stable now. Was 0 on phones for one commit under a `<=` disqualifier. |
| 4 | **Height-equality disqualifier** | a level property | measure-zero | Faithful rule, effectively dead. A one-pixel resize flips it. |
| 5 | **Warning visibility / reaction time** | AS3-like | much longer | Emergent, unquantified. A taller view shows spawn warnings earlier. |
| 6 | **Enemies visible at once** | AS3-like | up to 2.4× the vertical band | Emergent, unquantified. |
| 8 | **Food-round border bounce** — Gummy Bear and Crazy Cheese reflect off the camera rect, not the room walls (`:1906`) | bounce box ≈640×400, close to the original | bounce box up to 640×1385 | Deliberate, and **faithful**. `:1906`'s `roomWidth` terms cancel exactly, leaving the visible window inset by the radius. On the AS3's fixed stage this was indistinguishable from a room-wall rule; here it is not. See C1 below. |
| 7 | **Grenade throw distance** — speed and friction both derive from the distance to the cursor | reach ≈755 (the 640×400 diagonal), speed ≈81 | reach ≈1570, speed ≈168 | Deliberate. See below. |

### 7, in more detail — added with the Grenade secondary

`PartGameArea.as:4042-4047` derives both launch speed and friction from
`shootDistance`, the world-space gap between the muzzle and the cursor. Nothing
about that is camera-relative, so **the distance itself needs no correction** —
it is measured between two world points and camera zoom never enters it.

What *is* viewport-dependent is how far the cursor can be. The AS3 could not
point beyond its 640×400 view, capping the throw at that diagonal; a tall
portrait viewport here roughly doubles it, and speed and friction rise together
with it. A grenade thrown across a phone screen is genuinely faster and
decelerates harder than any the original could produce.

This is the same trade as rows 1 and 2 and is accepted on the same grounds: you
can throw as far as you can point, and a fixed 755-unit cap would put a hard
ceiling in the middle of a view the player can see into. Recorded here rather
than argued at the call site, per the standing rule.

**Separately, one AS3 correction is deliberately not ported at all.**
`:4032-4038` shortens a throw aimed below `400 - cameraPosY` — the world Y of
the bottom edge of the play area, because the Flash stage is 640×480 with an
80-pixel HUD strip below the game view. It exists so aiming *into the HUD* lands
the grenade at the bottom of what you can see. The port's HUD is DOM floating
over the canvas, and `pointerWorldPoint` is always inside `worldView`, so the
condition is unreachable. Reproducing it would leave a branch no player can
enter. Reasoning is at `weapons/grenade.ts`'s `throwGrenade`; this is the only
place so far where "use the live value" would have produced a permanently false
test rather than the right answer.

**Not yet examined:** 5 and 6 are consequences of the same variable but have not been
measured. Difficulty is currently hardcoded to Easy, so no balance work has been done
against either.

**Nothing in this table has been observed on a phone.** The port targets iOS/Android
via Capacitor and has never been opened on one. Two of the six entries were defects

## Fixed-camera assumptions in a dynamic-camera port

### The tutorial panel's `480` — the AS3's *stage*, not its camera

`PartTutorial.as:341` places the `Objective` panel with
`theYPos = 480 - tutorialObjective.height - 8`.

**480 is the stage height, not the camera height (400).** That distinction is
the whole trap: a reader who knows this section exists will recognise 400 as
the frozen camera and might leave 480 alone as "some other constant". It is the
same class — a compile-time screen dimension that is a runtime variable here —
and it is the third member of this category after the spawn search and the
food-round bounce.

Ported as the live viewport bottom in `tutorial/tutorialArt.ts`'s
`panelPosition`. Transcribing the literal would pin the panel 480 units from
the top of a viewport that is 400 units tall on a wide desktop window (off the
bottom) and 1385 on a portrait phone (floating in mid-air, two thirds up).

The other eleven panels are at a literal `(16, 16)` and need no such treatment,
which is why this is one site rather than twelve.

A recurring class, worth its own heading because it has now caused one shipped
bug and one shipped regression, and both looked faithful when read.

The AS3's camera was **a fixed 640×400 Flash stage**. This port's is
**640 × `logicalHeight`**, where `logicalHeight` is `renderHeight / zoom` clamped
to `[400, 1440]` (`config/viewport.ts`). Any AS3 expression involving the camera
is therefore a *constant* there and a *variable* here, and porting it term for
term preserves the arithmetic while silently changing what it means.

Two instances so far:

1. **The off-camera spawn search compared against 640×400.** Faithful predicate,
   wrong operand — the protected rectangle was up to 320 units shorter than the
   real viewport, so >20% of "off-camera" placements were on screen. Fixed by
   requiring the live viewport on `PlacementContext`; omitting it is now a
   compile error.
2. **The `roomWidth == cameraWidth || roomHeight == cameraHeight` disqualifier
   was widened to `<=`**, justified as "identical on every room size the AS3
   could produce". That justification reasons in the AS3's world about a change
   that only matters in this one. It disabled the search on **all 405 levels at
   any logical height ≥ 720** — i.e. everywhere on a phone. Reverted to `==`.
   The two axes are independent: a 900-wide room in a 640-wide camera keeps
   28.9% of candidates valid at any height, and the "camera covers this
   dimension" case needs no guard because a negative margin widens that band
   past the room and the test falls through to the other axis on its own.

**Known divergence, deliberate.** With `==` restored the structure is faithful,
but two properties are now viewport-dependent where the original's were fixed:

- **The acceptance rate varies.** In a 900×720 room, 60.5% of candidates are
  accepted at a 640×400 viewport and 28.9% at 640×720 or taller. A taller window
  genuinely shows more of the room, so fewer positions are off screen. This is
  the honest physical consequence, not a defect.
- **The height-equality disqualifier is effectively dead.** It fires only when
  `logicalHeight` exactly equals a room height — a measure-zero coincidence with
  a continuous viewport, where in the AS3 it was a static property of a level. A
  one-pixel resize flips it. Pinned in `offCameraSpawn.test.ts` so the behaviour
  is recorded rather than discovered.

**Before porting any other camera-derived expression, ask whether the AS3 value
was constant.** If it was, the port needs the live value and probably needs it
to be non-optional.

## One rule, two copies — the tested one unused

**Read this before the dead-module list below.** It is a worse failure than dead
code, and it is easy to mistake for it.

In each case a helper exists, is exported, and has real tests. The caller does not
call it — it reimplements the same rule inline. So there are two copies of one
rule, a green test guards the copy that never runs, and the copy that *does* run
is unguarded. Dead code is inert and honest. This actively misleads: the suite
reports the behaviour as covered, and the two copies can drift apart silently, at
which point the tests keep passing while the game does something else.

|---|---|---|
| Crowd count within a flame radius | `weapons/flames.ts:120` `countCrowd`, 3 tests | `GameplayScene.ts:938-943`, same `Math.hypot(...) < FLAME_CROWD_RADIUS` loop written out |

## A registration point is not a centre — 13 August 2026

**Flash positions a clip by its registration point; Phaser positions a sprite by
its origin, which defaults to the centre.** Where a piece of art's registration
*is* its centre the two agree and nothing is owed, which is why this survived
120 tasks: **33 of the 44 particle shapes are centred**, as are six of the twelve
turrets.

The exceptions were wrong the whole time, and both were reported as something
else:

- **The muzzle flare "appears in the middle of the tank."** Shapes 1108, 1114
  and 1119 — the three flares' first frames — have their registration at local
  x = 0, the flare's flat base. Drawn centred, half of every flare sat *behind*
  the muzzle, inside the hull. The reported symptom was real and the obvious
  reading of it was wrong: the flare's **position** was very nearly right all
  along, and its **anchor** was not.
- **The turret was drawn `setDisplaySize(21, 21)`** — a square, centred. Five
  of the twelve turret shapes are not square (19x17, 20x19, 20.9x20.85, 20x23,
  26.4x17) and were being stretched to fit; the Magic Cannon was also swung
  about a point 4.7 units from its real hinge.

**Why this class is hard to see.** Every symptom it produces looks like a
different bug. A stretched turret reads as "the art is a bit off". A flare
anchored at its centre reads as "the flare is in the wrong place" — and the
natural fix, moving the flare, makes it worse while appearing to address the
complaint. T120 did exactly that: moved the spawn point out to the hull edge,
measured that it had moved, and shipped it green. The measurement it never took
was where the barrel actually ends.

**What now enforces it.** `src/assets/spriteGeometry.ts` is generated from the
SVG bounds — `npm run sprite-geometry:data`, checked in `data:check` — and
carries the registration point of every turret plus every particle clip whose
registration is *not* its centre. The table is deliberately sparse: an entry
means "this art is not centred". `spriteGeometry.test.ts` re-derives the numbers
from the SVGs rather than reading the generated file back, so a generator that
computes the wrong thing fails rather than shipping a confident table.

One clip is excluded by name, with its reason recorded at the exclusion:
`Lock` places shape 843 at a translation of (-65, -47), and the generated
placement data keeps only the *scale* half of the SWF's matrix — so an anchor
derived from registration alone would move it by the amount that translation
exists to cancel. It stays centred, exactly as it draws today.

**Owed, and not done here:** the same question has not been asked of enemy art,
projectile art or prop art. The tool exists now; the sweep does not.

## Deliberate content divergences

Distinct from the viewport divergences above, which are consequences of a
different camera. These are places where the port **plays something the
original did not**, by decision.

### Spawn placement is deterministic; the AS3's is not

`spawnWarnings` draws every placement value from **unseeded `Math.random()`** —
`randomNum`, `randX`, `randY`, `warning.wall`, `warning.x`, `warning.y`. The same level
played twice in the original spawns enemies in different places.

The port seeds `spawnRng` from a string key per level (`GameplayScene.ts:1075`), so a
level's spawn pattern is fixed and repeats exactly.

**Why accepted:** reproducibility. A spawn-related bug is otherwise unreproducible, and
"did my change move the spawns" is unanswerable. It was a deliberate departure taken for
debuggability, not an attempt at fidelity.

**The cost, stated:** the original's run-to-run variety is gone. A level plays the same
way every time, which is a different feel over a long session even though no single run
looks wrong. **If faithful spawn behaviour ever becomes a goal, this is one of the two
places to revisit** — and note that "make it faithful" here means making it *random
again*, not seeding it from `LevelSpec.seed`, which would swap one invented determinism
for another (see D1's correspondence finding).

### `spawnPickups` was added content — **removed**

`GameplayScene.spawnPickups` laid a fixed board of eight decorative coins at level
start. **The original had no counterpart.** `spawnMoney` is called only on enemy death
(`:6844`, `:6848`) and on flag pickup (`:2589`) — money exists in the AS3 only as a
drop, never as scenery.

**Deleted**, along with `Pickup.ts`, `collectPickups`, `collect` and the physics group.
It was recorded here as an accepted divergence for one pass; that standing did not
survive contact with its own history. It had already caused a real defect — `levelOutcome`
was fed `moneyOnFloor: this.pickups.countActive(true)`, counting decorative coins rather
than enemy drops, so **no level could hand over at all**. Added content that has already
produced a total failure is not a divergence with a stated cost; it is scaffolding that
outlived its purpose.

Nothing depended on it: no achievement (the two that once keyed off it, `first-coins`
and `clear-board`, were invented demo scaffolding and were removed earlier), no test
asserting coin-board behaviour, and `currency:earned` has five other producers so the
event path it was demonstrating survives.

**One real consequence, stated:** the board was worth 8 x 5 = 40 currency per level of
free income. That income is gone. Enemy drops pay out directly in `removeEnemy`, so the
economy still works, but every level is 40 poorer than it was.

**Not retired with it:** `moneyOnFloor: 0` in the level-outcome call. That hardcoded
zero is correct because **`ItemMoney` is unported**, not because the coin board existed
— deleting the board does not discharge it. It comes out when enemy money drops become
collectable objects rather than a direct payout.

*(Both of these were nearly filed under "Faithful, and easy to mistake for a defect".
That would have been wrong in the way that section is most dangerous: it tells a
reviewer "we checked, this matches the original" — and neither of these matches the
original. They are departures, and they belong here with their costs written down.)*

### World 1 Normal/Flag rooms standardised to 800x600 (27 July 2026)

World 1's nine Normal and nine Flag levels shipped at three sizes — 640x400,
800x600 and 900x720. All eighteen now play at 800x600, which is 1-4's room and
was already the size of six of them. Tower, Boss and Defense (27 of world 1's
45) are untouched: their sizes are tied to how those modes play.

Twelve levels actually change. Two accepted consequences:

- **Density moves, and enemy counts do not.** The nine shrinking from 900x720
  lose 26% of their area and get ~35% denser; the three growing from 640x400
  gain 87% and get ~47% sparser. Signed off explicitly as a balance change.
- **Off-camera spawning switches on for 1-1, 1-3 and 1-30.** The disqualifier
  fires when `roomHeight === cameraHeight`, and nominal camera height is
  clamped to exactly 400 — so every 640x400 room had the search disabled and
  its enemies entered at the visible edge. At 800x600 they arrive from off
  screen. This is the most visible behavioural effect.

**A third consequence, found only when props were drawn (T14).** Anything the AS3 scales
by *room area* is scaled up with the room, and nobody had looked at that class as a class.

Background prop count is the demonstrated case. `createBackground` derives `amount` from
`tileCountX * tileCountY` where a tile is 256 units (`:1135`, `:1244`), so 640x400 gives
`3 x 2 = 6` tiles and 800x600 gives `4 x 3 = 12`. **World 1's standardised levels place
exactly twice the props the extraction's dimensions would.** The formula is faithful; the
operand is the standardised room.

**This is not being patched, deliberately.** Scaling `minAmount`/`maxAmount` down would
fix a symptom of the room decision by putting a compensating error inside
`createBackground`'s arithmetic — the prop count would then match neither the source nor
the room, for a reason recorded in a different file from the thing that caused it, and
every future comparison against the AS3 gets harder. If the density is wrong in play, the
honest fix is revisiting 800x600, not the formula.

**What else is area-proportional has not been surveyed.** Prop count is simply the first
one that became visible. Any AS3 quantity derived from `roomWidth`/`roomHeight` — spawn
counts, terrain features, anything tiled or per-unit-area — is affected on the same
twelve levels by the same factor, and none of it has been checked. That unexamined set is
the real cost of the standardisation, and it is recorded here rather than in each
subsystem so the cost is visible in one place.

**The fidelity check was strengthened, not relaxed.** `LEVELS` remains a pure
transcription of `ScreenGame.as` and is still asserted to match it exactly;
the overrides are applied in `getLevel`, so what the game plays is checked too.
An override must name the source value it replaces, so it excuses only the
divergence it predicted — a re-extraction that changed 1-2 away from 900x720
would fail rather than be masked. Four further tests stop the table rotting: no
no-op entries, no stale entries, nothing outside world 1 Normal/Flag, and an
exact count of twelve.

Table: `src/game/levels/levelSizeOverrides.ts`. Tests:
`src/game/levels/roomSizeSource.test.ts`.

## Open decisions

Distinct from *Held, not fixed*. A hold is "we will do this later"; an open
decision is **two incompatible options where picking neither is itself a
choice**, and one that gets made by default if it stays unwritten.

### D1 — Which RNG lineage owns level layout?

**Status:** **DECIDED — Option A**, after being deferred twice (most recently 27 July
2026). See *The decision, and what it actually costs* at the foot of this entry, which
also records why A is not the separable RNG change it was described as.

**The situation.** The port runs two random number generators with no boundary
between them.

- `core/PM_PRNG.ts` is a faithful Lehmer port of the original's generator,
  tested against BigInt over 35k draws on 7 real level seeds. It has **zero
  non-test importers**.
- `GameplayScene` (`:1075`, `:3324` — the entry originally cited `:607`/`:1789`,
  which T1-T7 moved) uses `Phaser.Math.RandomDataGenerator` seeded from **string
  keys**, not from the level table.
- `LevelSpec.seed` is extracted from `levelDataModel[...][9]` and **read by
  nothing**.

So the reproducibility-critical module is unreachable, the value it exists to
consume is unused, and a different generator has already been chosen at the
sites that place things in the world. That is a decision that has been made in
practice without being made on purpose.

**Option A — restore the original lineage.** Wire `PM_PRNG` to `LevelSpec.seed`
and route layout randomness through it.

- Gets: the original's exact background-prop placement, per level, reproducibly.
  Bug reports become replayable, and a screenshot of the SWF can be compared
  against the port directly.
- Costs: every site that currently draws from `RandomDataGenerator` for
  *placement* has to move. The two known sites are in `GameplayScene`; more may
  appear as props land. `PM_PRNG`'s arithmetic is fragile by nature — its
  product reaches ~7.2e13 and `Math.imul`, `| 0` and `>>> 0` all destroy it —
  so anything touching it inherits that constraint permanently.

**Option B — drop `PM_PRNG` and standardise on Phaser's generator.**

- Gets: one generator, one seeding story, ~200 lines and a differential test
  deleted. Phaser's is seedable, so levels can still be deterministic — just not
  *identical to the SWF*.
- Costs: the original's layouts become unreproducible for good. Any future
  "does this match the Flash version" comparison of prop placement is off the
  table, and `LevelSpec.seed` should then be dropped from the extraction with a
  note saying why, rather than left as a column nothing reads.

**What makes this decidable:** whether faithful background-prop placement is a
goal of the port or not. It is not a technical question and does not get easier
with more tracing — both options are a day's work and neither is blocked.

**Do not "keep both."** That is the current state, and it is the one option with
the costs of A and the benefits of neither: a fragile module nobody runs, a
level column nobody reads, and layout that already diverges.

### The decision, and what it actually costs

**Option A**, decided rather than deferred a third time. The reason is the project's
own standing rule: the AS3 source is the spec, and seven consecutive porting tasks paid
that price deliberately. B is the honest choice in a port where faithful behaviour is
not a goal; that is not this port. The cost asymmetry settles the timing — A is two
call sites now and more as placement sites land.

**A is not a separable RNG change. It is the background-prop port.** That was
established by reading the source before wiring anything, and it is the finding that
matters most here, because the scope it replaced would have manufactured a reader and
called it fidelity.

#### The correspondence finding — the two live sites have no AS3 counterpart

`PM_PRNG` appears in **exactly three places in the entire AS3 tree**, all of them the
background-object subsystem:

| Line | Site |
|---|---|
| `:711` | `getRandomPointWithinCircle(randGenerator:PM_PRNG, …)` — helper |
| `:1184` | the **only** instantiation, inside `createBackground` (`:1102`) |
| `:2603` | `removeBackgroundObjectsColliding(randGenerator:PM_PRNG)` |

`randGenerator` is a **local** at `:1184`, so the lineage cannot leave
`createBackground`. Its one helper call is `:1408`, also inside it.

Against that, the two generators the port actually runs:

- **`spawnRng` (`GameplayScene.ts:1075`) — spawn placement.** The AS3 counterpart is
  `spawnWarnings`, which uses **unseeded `Math.random()` throughout** — `randomNum`,
  `randX`, `randY`, `warning.wall`, `warning.x`, `warning.y`. AS3 spawn placement is
  non-deterministic run to run. There is no PM_PRNG draw to be faithful to.
- **`spawnPickups` (`GameplayScene.ts:3324`) — decorative coins.** No AS3 counterpart
  at all. `spawnMoney` fires only on enemy death (`:6844`, `:6848`) and flag pickup
  (`:2589`); the original has no fixed coin board.

**So moving those two sites onto the PM_PRNG lineage would be wrong, not merely
unnecessary.** It would attach the faithful lineage to sites with no faithful
counterpart — the exact conflation D1 exists to resolve — and would manufacture a
"production reader" for `LevelSpec.seed` that reflects nothing in the original.
`LevelSpec.seed`'s only faithful consumer is `createBackground`, which is unported.

This is a negative result, and it cost a full pass to derive. It is recorded at length
so it does not cost another one.

#### The draw order the prop port must satisfy

One generator, seeded once per level, consumed in a fixed sequence:

```
:1184-1185  seed  ← levelDataModel[...][9]   (LevelSpec.seed)
:1246       amount = minAmount + round(nextDouble() * (maxAmount - minAmount))

per prop, in exactly this order — :1281-1288
  scale      = nextDouble()
  posX       = round(nextDouble() * roomWidth)
  posY       = round(nextDouble() * roomHeight)
  rotation   = round(nextDouble() * 360)
  stopAt     = nextDouble()
  typeNumber = floor(nextDouble() * (objectList.length / 2))   // only if randomOrder
```

`removeBackgroundObjectsColliding` (`:2603`) draws from the **same** generator and is
therefore **inside this sequence**, not beside it.

**Any divergence in draw order makes every position after it wrong.** A Lehmer
generator has no resynchronisation: one extra or missing `nextDouble()` shifts the
whole remaining stream, so a prop layer that is correct in every formula and wrong by
one draw produces a layout that matches nothing. That is the fragile part, and the
reason the order is written down before anyone starts rather than discovered by
comparing screenshots.

#### What this decision does *not* disturb

- **T1-T7 removed no blocker, because none existed.** The entry has always said both
  options were unblocked; the harness, the hazard-sweep extraction and the kill site
  are all irrelevant to it. The deferral was never technical.
- **Nothing is pinned against the current generator.** No test anywhere references
  `spawnRng` or `RandomDataGenerator`, so deciding this moves no test. The one reader
  of `LevelSpec.seed` is `levelProgress.test.ts`, asserting the 405 seeds are unique —
  a data-integrity claim that holds under either option.
- The generator itself needs nothing: `PM_PRNG.test.ts` asserts MINSTD's canonical
  opening terms and **Park & Miller's published check value** (the 10000th term from
  seed 1 is `1043618065`), which is ground truth independent of this repo *and* of the
  SWF. Earlier reports grouped this with `B1` as "needs a running SWF" — that was
  wrong. The generator is verified and the consumption order is readable.

**Landed (step 2 of 3):** `levels/backgroundProps.ts` — the layout maths, seeded from
`LevelSpec.seed`, which finally has the production reader D1 was decided to give it. No
rendering and no collision pass.

#### Visual fidelity is unverifiable here — same shape as B1

Stated before the work rather than discovered after. **Positions are provable; how it
looks is not.** The generator is verified against Park & Miller, the formulas are
readable, and the draw sequence is pinned against a hand-derived stream — so the port
can prove it places props *where the original would*. Nobody can put the port and the
SWF side by side to confirm the result, and no assertion in this repository can close
that. Treat "the layout is correct" as proven and "the layout looks right" as untested.

**Placeholder art is in place with the real frame counts** (1-16, read from the sprite
definitions in `assets.swf`), so the `stopAt` draw is exercised rather than collapsing
to a constant. A reviewer should not read the variant logic as untested — it is; only
the pictures are missing.

**One number disagrees with the art already.** `addBackgroundObject` declares
`maxFrames = 3` for `RedBloodCell`, but symbol 1465 has **1** frame. Flash clamps
`gotoAndStop` past the end, so it always showed frame 1 in the original. The port keeps
the AS3's 3 because that is what the arithmetic uses; it only matters once rendering
lands, and step 3 must clamp rather than trust the table.

#### Two findings from the step-2 read

- **`randomOrder` is dead, and that removes a draw.** `:1188` declares it `false` and
  nothing assigns it again — a function-local, so exhaustive rather than a name-grep
  floor. `typeNumber` is therefore always 0, the draw at `:1288` never executes, and the
  per-prop sequence is **five draws, not six**. Reading `:1281-1288` as the spec
  consumes one draw too many per prop and diverges from the second prop onward. The type
  still changes — by exhaustion, when index 0's count hits zero and the pair is spliced.
- **A ruleless type still burns the group roll.** `groupChance *= 1 / ((max - min) / 2)`
  is `0 * (1 / 0)` = NaN for a type with no group rule, so the comparison is false and it
  never clusters — but the draw at `:1370` happens regardless. Moving that roll inside
  the rule check would shorten the stream by one draw per prop.

**Still owed, and what discharges it:** the collision pass (`:2603`) draws one
`nextDouble() < 0.5` per colliding pair (`:2646`), so it is inside this sequence and its
draw count is data-dependent — **it must be pinned as "one draw per collision resolved",
never as a stream offset.** And the art: the 21 `BGObject*` clips embedded in
`assets.swf`, roughly 100 frames, needing an extraction step that is scoped but not
built. Order is deliberately step 2 -> 3 -> 1, so that when the art lands any wrongness
is unambiguously the art, the positions having already been pinned.

#### Step 1 landed — via a correction to a check, not to the repository

An earlier pass concluded the prop shapes were absent from the tree and that step 1 was
blocked on running JPEXS against `assets.swf`. **That was wrong, and the cause was a bug
in the check.** The list of required shape ids was written by a Python script on
Windows, so it carried CRLF line endings, and the shell loop testing
`[ -f "$id.svg" ]` was asking for `1483
.svg` on every iteration. All 108 reported
missing. Re-run with line endings stripped: **all 108 present, zero missing.** The
inference built on it — that `shapes/` held only main-SWF art and the two files had
disjoint id spaces — was wrong for the same reason.

Recorded rather than quietly fixed, because the shape of the mistake is the useful part:
**a check that returns "not found" for every single input is far more likely to be
broken than informative.** It read as a clean, decisive negative result and was reported
as one. A single spot-check with `find` caught it one pass later.

(That pass also *claimed* to record the blocked status here and did not: the edit used a
string replace whose anchor had drifted, with no assertion on the result, so it silently
did nothing while reporting success. Same class of error — an unchecked operation
reported as done.)

**What landed.** All 21 clips resolve: every `DefineSprite` frame places exactly one
`DefineShape`, giving 109 distinct shapes, generated into `levels/propArt.ts` rather
than hand-listed. Frames that place nothing hold the previous shape — `Skeleton` has 16
frames from 12 placements. The shapes went into the **curated sync set**, not
`assets-authored/`: they are extracted art, and `assets-authored/` is for assets we
made. They load as `prop-<shapeId>`.

**The neutrality assertion did its job.** `the art cannot move a prop` passed unchanged
across the swap — the derived positions for seed 610309764 are identical and the
survivors are still an unmoved subset. Nothing reached past the collision pass. It was
written before the art existed precisely so the swap would be guarded rather than
reviewed, and it is the first thing in this port pinned ahead of the change it protects.

**`RedBloodCell` still disagrees with itself**, as predicted: the clip has one frame
where `addBackgroundObject` declares three. The extraction did not reconcile them and
must not. Now asserted against the generated map as well as the hand-read table, which
is the independent check that the table was read correctly.

**What real art does not close:** the visual-fidelity gap. Having the original shapes is
not having confirmed the result, and nobody can compare against a running SWF. That
entry stands.

#### The first bug found by looking, in a subsystem that was fully green

The props were rendered and looked wrong in three ways: they drifted over the terrain as
the camera moved, they overlapped constantly, and they read as roughly twice the size and
twice the number. **Three symptoms, four causes, and the suite was green throughout.**

- **Drift — an invented parallax.** The ground tile position was offset by
  `scrollX * 0.06` as a depth cue. `createBackground` puts the ground tiles *and* every
  prop in the same `bg` container (`:1145`, `:3551`), so nothing in the original moves at
  a different rate. Props were correct; the ground was wrong. Removed.
- **Size — a flat rasterisation.** Every prop SVG was rasterised at 96x96. They range
  from **10.8 to 107 units wide** and are not square, so a rock authored at 13.95x12.95
  drew at nearly seven times its size with its aspect destroyed. Now rasterised at 3x each
  shape's own authored size and drawn at that size.
- **Size again — the raw scale draw.** `scale` is never used raw: `:3529` onward maps it
  per type through eleven different affine transforms, most landing *near one* rather than
  near zero (`Rock` 0.60-1.10, `Dirt` 1.20-1.40, `Seastuff` 0.20-0.325). The port applied
  the 0-1 draw directly, flattening all eleven. `FuturisticLines` is `4 + scale * 0` — a
  constant 4, with the draw consumed and discarded, the same dead arithmetic as the Laser
  Cannon's spread.
- **Overlap — a collision pass reading invented numbers.** `:2617` takes the radius off
  the *rendered* sprite. The port computed it from a hand-invented `PLACEHOLDER_SIZE`
  table and the raw scale, so it ran and under-removed. Both operands now come from the
  art and the mapped scale.

**Density is the one that is not a bug.** The port's world-1 rooms are 800x600 where the
extraction says 640x400, so tiles go from 3x2=6 to 4x3=12 and `amount` doubles with them.
That is the room-standardisation divergence already recorded under *Deliberate content
divergences*, with a consequence nobody had seen until the props were drawn. Halving it
would mean either unwinding that decision or diverging from `createBackground`'s own
arithmetic — a design call, not a correction.

**Why this belongs next to the seam finding.** Every one of these is a rendering-layer
fault in a subsystem whose *maths* is pinned to a hand-derived stream and whose unit tests
number in the dozens. The layout was correct the whole time and stayed correct through the
fix — the neutrality assertion passed unchanged before and after, which is how we know
this was the right layer. What no test could see was what any human saw in seconds. The
seam survey found eight subsystems pinned at the unit and unpinned at the seam; this is
the same lesson arriving from the other direction, and it is the argument for looking at
the running game as a routine step rather than an occasional one.

**The visual-fidelity entry above is now half false and stays.** Nobody can compare
against a running SWF — that is unchanged. But the port itself can be looked at, and the
first time anyone did, it produced four findings.

### The third direction: unpinned numbers (T34, 4 August 2026)

The same lesson again, and the most uncomfortable version. **T34 changed every entity's
collision radius — up to 2.85x, across 112 consumers — and the full suite stayed green.**
2445 tests, and not one of them pinned a value.

The seam survey found subsystems pinned at the unit and unpinned at the seam. The visual
survey found subsystems pinned in maths and unpinned in rendering. This is the third:
**pinned in behaviour and unpinned in magnitude.** A rule can be correct, tested, reached,
and rendering correctly while operating on a number nobody ever checked — which is how
`26`, `46` and `58` survived from placeholder art to the present.

**The mechanism worth carrying, because it generalises past this project:** a test that
copies a constant out of the code it is testing cannot detect a wrong constant.
`tankMovement.test.ts` asserted the hull's per-frame turn was at most `10` — a literal
copied from `TANK_ROT_SPEED_MAX`, which was itself wrong against `Tank.as:25`'s 20. The
test passed for exactly as long as the bug existed and would have failed the moment
anyone fixed it. It now reads the constant, and a separate assertion pins the constant
against the AS3 value. **The assertion has to come from the source, not from the code.**

A citation is not a check either. All three wrong constants carried correct-looking
references to the AS3 lines that contradict them.

**And inert exports can hide correct values, not just absent subsystems.**
`TANK_RADIUS = 14` was in the tree, correctly ported, correctly cited, covered by its own
test — and reached by nothing, while production used a locally derived 29. This is the
`PM_PRNG` shape at value scale: the right answer present and unwired. When the knip
canary reports an unused export, "ported but not yet needed" is one reading; "the correct
value, sitting beside the wrong one in use" is another, and nothing distinguishes them
without looking.

## Frame-order and timing divergences

Added with the ground-hazard weapons (T1–T6, `5b009e0`..`31602ab` — 8 commits of the
85 between `origin/main` and `31602ab`). Distinct from the viewport section above:
nothing here depends on screen size. These are places where the AS3's *ordering within
a frame* is either not reproduced, or not knowable from the extraction.

### A3. Audio toggles appear on the main menu as well as in Options

`ScreenOptions.as` is the AS3's single home for every preference; this port also
keeps the sound and music toggles on the main menu, where they have been since
before an Options screen existed.

**Kept deliberately.** They are the only audio control a player has *during* a
session — the AS3's answer is to pause and open Options, which this port has no
pause menu for yet. Removing a working affordance to match a layout would cost
the player something real and gain nothing.

It is the same component in both places (`AudioToggles`), emitting the same
`ui:set-audio` to the same store, so the two cannot disagree about state. A
reader comparing screens will see one extra control on the menu; this is why.

### A5. The `Objective` panel sits above the HUD band, where the AS3 sits inside it

**A divergence forced by a layout difference, not a correction.** The AS3's
placement is faithful and unusable here, and the reason is worth stating
precisely because the obvious reading of it is wrong.

**What the AS3 does.** The stage is 640x480: play area 0..400, interface strip
400..480 (`PartInterface.as:232`, `bg.y = 400`). `PartTutorial.as:341` places
`Objective` at `480 - height - 8` = **408** — deliberately *inside* the
interface strip. It does not collide with the weapon widgets because it clears
them **on x**: the panel spans 194..354 and the weapon cluster starts at
`bgWeapon.x = 388` (`:234`), with `bgWeapon2.x = 474` (`:237`).

**Why the port cannot do the same.** This port's HUD is a full-width DOM row —
health left, ammo centre, audio and menu right — so **there is no x at which a
bottom-anchored panel clears it**. Reproducing `:341` put the panel on top of
the weapon readout at every viewport size: at the desktop floor the panel spans
328..392 against a HUD band starting at 320, and at a portrait phone 1368..1432
against 1360. Both ends, not one.

**What the port does.** Reserves `HUD_BAND` = 80 units at the bottom and seats
the panel above it — `viewportHeight - 80 - height - 8`.

**The 80 is derived, not chosen:** `480 - 400`, exactly how much of its screen
the original reserved for interface. So the port keeps "at the bottom of the
play area, clear of the interface", which is what `:341` *means* in a layout
where the strip exists, and drops the literal y, which is what it *says*.

**Note this is the opposite treatment to the rest of this section.** Elsewhere a
frozen AS3 screen constant is replaced by the live value and the rule is
preserved exactly. Here the rule itself cannot survive, because the constraint
it relied on — a HUD that occupies only part of the width — is not a property of
this port. Recorded rather than argued at the call site, per the standing rule.

Pinned in `tutorialArt.test.ts` at **both** extremes of `logicalHeight`
(400 and 1440), against the counterpart rule that the other eleven panels stay
at the literal `(16, 16)` and do not move with the viewport at all. The
clearance is asserted as a property (`y + height <= viewport - HUD_BAND`), so it
survives a change to any of the three constants; restoring the faithful
`viewportHeight - height - 8` fails it.

### A7. The achievement toast sits below the HUD row, and survives the results overlay

Two small departures at one site, both consequences of this port's HUD being a
different shape from the AS3's. Landed T79 with the toast queue.

**What the AS3 does.** `PartAchievements.showAchievementFromQueue` (`:112-132`)
shows **one** toast at a time, spliced off `achievementArrayQueue` (`:116-117`)
and only when nothing is currently showing (`:265`). It is placed at
`theXPos = 640 - achievementImage.width - 16`, `theYPos = 16` (`:125-126`) — top
right, 16px in — and pushes the `Achievement` sound as it appears (`:120`).
`PartAchievements` is added to `ScreenGame` (`ScreenGame.as:387-388`) and
`ScreenUpgrades` (`:637-638`), and **not** to `ScreenStatus`.

**Departure 1 — the y.** A faithful `y = 16` puts the toast through this port's
wave counter, which sits top-right; the AS3's own interface is a bottom strip,
so its top-right corner is empty. The toast is therefore placed below the top
HUD row. **Same class as A5**: a faithful coordinate against a HUD that is not
the original's.

**Departure 2 — it shows over the results overlay.** The original changes screen
at level end (`Main.changeScreen = "Status"`), so its toasts cannot appear
there. This port draws the results as an overlay above a paused gameplay scene —
the structural difference already recorded around A0 — so the queue keeps
draining underneath it. Accepted rather than suppressed: suppressing would need
the queue to survive a screen that does not exist here, and with one toast in
the top-right corner it obscures nothing.

**Why this is recorded rather than "fixed".** Both are the port's HUD shape
asserting itself, not choices about behaviour. The rules that *are* behaviour —
one at a time, queued, sounding on show — are ported exactly.

**Driven.** The T74 repro (six achievements on one clear) now renders one toast
top-right with the results panel fully legible, and the sound fires six times,
once per promotion.

### A64. Delete works, and the test that should have proved it did not exist

Checked after `A63`, because the two share a mechanism: the menu deletes
through its own `SaveStores` and then republishes the list, and `A63` had just
made republishing call `reloadAll()`.

**No code change was needed. Delete was already correct**, on all four counts
that are separable here:

    after playing     Slot 1  World 1  Level 2 | 20/Aug/26/16:46
      stored keys     CircularTankSave1
    after delete      Slot 1  New game
      stored keys     (none)
    after reload      Slot 1  New game
    picked slot 1     in a level, wave 1, "Kill 10 Enemies"

The row clears without a reload, the backend key is gone, it stays gone across
a reload, slots 2 and 3 are untouched, and picking the emptied slot starts a
**fresh** game rather than resurrecting the old one — which was the real
worry, since `getPlayerProfile` caches a store per slot and a stale copy could
have written the save back. `selectSlot` builds a new `createPlayerProfile` and
overwrites the registry, so it cannot.

#### The interaction that could have broken it, now pinned

`A63`'s `reload()` **flushes before it re-reads**, so a pending write is
persisted rather than dropped. Run straight after a deletion, that is one small
mistake away from writing the save back: if `clear()` left the store dirty, or
left its data in memory, the flush would undo the delete silently.

It does not — `clear()` empties `data`, sets `dirty = false` **and** removes
the backend key. But nothing held that, and the two halves were written a task
apart. There is a test now for exactly the order `MainMenuScene` uses:
`clear()` then `reloadAll()`, asserted against a *fresh* store so it is the
disk being checked rather than the instance that did the clearing.

**`deleteSlot` had no test at all.** It is one line, which is presumably why —
but it is the only destructive control reachable in two clicks from the title
screen, and "the wrong slot was deleted" is the failure `slotSummary.test.ts`
exists to guard against. It has two now, both driven through the summary the
screen actually renders rather than through the store.

#### The storage probe found nothing and said so quietly

The first driven run printed `stored keys: (none)` at every stage — including
immediately after playing, when a save demonstrably existed, because the row
beside it read `World 1 Level 2`.

The filter was `/slot/i`; the real keys are `CircularTankSave1..3`, verbatim
from `SaveManager.as`. So the assertion built on that probe — "the backend no
longer holds the key" — was guarded on the probe having found something, never
fired, and the run printed **DELETE WORKS** anyway.

Third time in four tasks (`A60`, `A62`, here). The pattern is always a check
whose precondition silently fails, and the fix is always the same shape:
**assert the precondition**. The probe now names the keys exactly and fails if
it cannot see the save it is about to watch being deleted.

The verdict did not change — the reload check covers persistence by a different
route, and it was real. But it was right by luck rather than by evidence.

### A63. The menu showed the saves as they were at page load

Create a save, return to the menu, and the slot still read **New game** until
the page was reloaded. Nothing was wrong with the writing — an F5 showed the
save, which is what made the report so precise.

#### Two stores over one key, and neither knew

`SaveStore` loads in its constructor — `this.data = SaveStore.load(name,
backend)` — and answers every read from that copy until something writes. That
is the AS3's `SharedObject` shape and it is correct for a single owner.

There are two owners:

- `getPlayerProfile` builds `new SaveStore(saveSlotStoreName(slot), ...)` and
  caches it in the game registry. **Gameplay writes through this one.**
- `MainMenuScene` holds `private readonly saveStores = new SaveStores()` to
  list all three slots. **The menu reads through that one.**

A field initialiser runs when the instance is constructed, and **Phaser
constructs a scene once and reuses it across every `scene.start`**. So the
menu's stores were built at boot and re-read nothing, ever. `create()` did
call `publishSlots()` on every return — the plumbing was fine and the data
behind it was three months stale by the standards of a single session.

**This is not a React reactivity bug**, which is where the report reasonably
pointed. The store, the bridge and the selector all worked: `save:slots` fired
on every menu entry and Zustand re-rendered. It published the same wrong
numbers each time.

#### The fix, and why it flushes first

`SaveStore.reload()` re-reads from the backend, and `SaveStores.reloadAll()`
does it for every cached store. `publishSlots()` calls it before summarising,
so the list is always what is actually on disk regardless of which instance
wrote it.

**`reload()` flushes before re-reading rather than discarding.** The menu is
not read-only — deleting a slot writes through it — and a refresh that dropped
a pending write would turn a display bug into a data-loss one. A test pins that
directly, including that the write reached the backend rather than merely
surviving in memory.

The reproduction is a unit test too: two `SaveStore`s over one `MemoryBackend`,
where the second cannot see the first's write until it reloads. That is the
whole bug in six lines, with no Phaser and no browser.

#### A failed build served the old bundle, and nearly cost the diagnosis

The first driven run reported **"the bug is NOT fixed"**. It was wrong.

`npm run build` is typecheck-then-build, and the typecheck failed — my new
tests called `store.get(key)` where the signature is `get(key, fallback)`.
Vitest does not typecheck, so all 21 tests passed and only `tsc` objected.
`dist/` was therefore never rewritten, and `vite preview` cheerfully served the
**previous** bundle: the harness measured T210's code and correctly found the
bug still there.

This is `CLAUDE.md`'s *"build clean is not the app loads"* running backwards —
a build that **failed** silently served stale bytes, and the failure scrolled
past above the harness's own output. The tell was in the log the whole time:
a `tsc` error line printed immediately before `at boot:`.

**Check the build succeeded before believing a driven result**, and do not let
a harness's output begin where the build's output ends. The accidental value is
a genuine before/after on one harness: the same flow, stale bundle showing
`New game` and the fixed one showing `World 1 Level 2`.

#### Driven

The reported flow exactly, in a fresh browser context so slot 1 really starts
empty — a leftover save would have made the "before" reading pass for the wrong
reason:

    at boot                     Slot 1  New game
    play, level ends, shield home
    without a reload            Slot 1  World 1  Level 2 | 20/Aug/26/16:37
    after a reload              Slot 1  World 1  Level 2 | 20/Aug/26/16:37

The last line is the counterpart that matters: it proves the menu was showing
what is on disk rather than something it had invented, and the harness never
reloads before that final check — a reload is the thing that used to be needed.

### A62. The shop prices in dollars, and the coin glyph was never in the face

The buy button drew its price as `◉ 1,600` while the balance directly above it
read `$5,000`. One screen, two currencies.

**The glyph had a second problem worth recording.** `.shop-buy__price` is set
in `--font-display`, which is `SWFMainFont` — 581 glyphs, and U+25C9 is not
among them. The disc was being drawn by whatever fallback the browser reached
for, so it was neither the game's typeface nor reliably the same shape across
machines. Nothing reported this: a fallback glyph renders, it just is not
yours. Same family as `A55`'s font, found the same way — by asking what the
face actually contains rather than what the string looks like.

Everything the screen says about money now says `$`: the price, the buy
button's accessible name, the balance's accessible name, and the one line of
prose about withheld upgrades.

**The accessible names were worse than the visible text and are fixed too.**
The balance announced `5000 coins` — the wrong currency *and* an ungrouped
figure, where the screen showed `$5,000`. It reads `Balance: $5,000` now, so
what is heard matches what is drawn.

#### Green, and which green

The price is `#7dff8a`. `.gloss-pill.shop-buy` is a hard split — green above
the midline for the verb, near-black below for the price — so green on the
lower half reads well and echoes the half above it.

**It is deliberately the shop balance's green, not the HUD's `#4ade6a`.** The

#### Driven, all 28 of them

Every tile is clicked and its price read, rather than sampling the first:

    tiles 28   priced 28   longest "$2,000" fits true
    colour rgb(125, 255, 138)   coin-glyph false   coins-word false

`fits` compares `scrollWidth` against the rendered box, so a price clipped by
its half of the pill would fail rather than merely looking short. The glyph and
the word are asserted absent across the **whole screen**, not just the price

### A61. The unlock reveal stops floating over the results

The reveal rendered on top of the results panel, overlapping it heavily.

**T206 caused it, and the mechanism is worth recording.** The reveal was
absolutely positioned at `inset: 12% auto auto 50%`, and its comment said why:
*"Sits ABOVE the results panel, not over it... Found by looking at the frame
rather than by reasoning about the layout."* That 12% was measured against the
panel as it stood. T206 then grew the panel — a stats grid with its own
padding, three medal sockets, and the four buttons restacked onto two rows —
and nothing moved the reveal.

So a correct, frame-verified constant became wrong because its *neighbour*
changed. It is the same class as `A56`'s `HUD_BOTTOM_CLEARANCE_CSS`: a number
tuned against something that later moved, with a comment that stayed accurate
about its own derivation and silent about its dependency.

#### Option B, and why not the blocking modal

Both were offered. Stacking was taken because it makes overlap **impossible by
construction**, where the alternative — hiding the results until Continue is
pressed — would have reversed the T44 divergence this port deliberately chose:
the AS3 put the exits on the results page only so reveals could not be skipped,
and this port shows the results *underneath* and lets the pop-up be dismissed.
Turning the reveal into a blocking modal would undo that on the way to fixing a
layout bug, which is a lot of behaviour to change for a geometry problem.

**Re-tuning the percentage was the third option and the wrong one.** The
panel's height depends on the outcome — how many medals, whether a next level
is offered, how long the enemy's description runs — so no constant clears it in
every case. That is what "by construction" buys.

`.level-outcome` is a flex column with a gap now; the reveal is a normal child
and needs no positioning of its own. It is also **first in the DOM**, which is
both the visual order and the right reading order: it is the thing demanding
attention, so a screen reader should reach it before the score.

Two details the column needed:

- **`overflow-y: auto`.** The pair genuinely exceeds a short viewport —
  measured scrolling by 13px at 1024x600 — and `justify-content: center` only
  centres while there is room. Without it the top of the reveal would be cut
  off with no way to reach it.
- **`flex: none` on the children.** A flex item's default `min-height: auto`
  lets it shrink below its content when the column overflows, which would clip
  the buttons instead of scrolling to them.

The reveal is smaller as well: `min(20rem, 76vw)` against the panel's
`min(26rem, 86vw)`, with tighter padding. It is an interruption rather than the
screen's subject, and it now shares the viewport with the results instead of
covering them.

#### Driven

Six viewports, 1024x600 to 3840x2160, with both panels open:

    reveal 320x330 to 320x371   panel 416x260 to 416x356
    gap 12 to 19px   intersects false   above true   smaller true

`intersects` is a real rectangle test — the overlap of the two boxes on both
axes — rather than a comparison of two coordinates, so a partial corner overlap
would fail it too. The harness also **fails loudly when no reveal opens** and
says so, instead of skipping the geometry checks and printing OK: that is
exactly what it did in `A60`, and the fix is worth more than the finding was.

### A60. The results lose their banner, and the unlock reveal gains a portrait

Four removals and two fixes, all on the end-of-level flow.

#### Three things came off the results panel

**The VICTORY / DEFEAT banner.** `ScreenStatus.as:446-457` heads the results
with `TitleVictory` or `TitleDefeat` art. Removed by request — the medals, the

**The red `UNLOCKED: ...` line.** It existed as the record that survived the

#### The reveal was centred by a property that cannot centre boxes

description has `max-width: 30ch`, the button has its own width, and the new

The overlay announced a discovery and showed no picture of what was discovered.

### A59. The crest becomes the way home

`IconShield` sat at the title bar's left on every screen inside the game,

### A58. The results screen: real medals, a stats grid, and one primary action

The last of the three heavy-bordered cards, after the pause panel (`A52`) and

Three things beyond the surface, and each was a real defect rather than a
restyle.

#### The medals were text stars in the danger red

`★★☆` in `--accent`, which is `#cc0000`. Two things wrong: the AS3 picks the
medal icon from the level's **mode** (`ScreenLevelSelect.as:874` builds it
before `:898` sets the tier frame, so a Flag level earns flags and a Boss level

**The mode had to be added to `level:ended`**, which had no field for it. The

do. `tabular-nums` on the values for the same reason.

Next level, Replay, Level select and Menu were all the same `.hud__button`, on

The primary spans the full row and the three secondaries sit under it in equal

`.hud__button` is now used only by this screen, since `T194` took the HUD's

Five viewports, 1024x600 to 3840x2160, by playing a level to its end rather

### A55. The body font never loaded, on every screen, since the extraction

A defect scan over level select and upgrades found the layout clean at four
viewports — no overflow, no clipping, no zero-size elements, no broken images,
no undersized controls. It found this instead, in the console, at every
viewport and on every screen:

    Failed to decode downloaded font: 49_Main_font2_Arial.ttf
    OTS parsing error: cmap: Out of order end range (65535 <= 65535)
    [fonts] "SWFMainFont2" did not resolve to a distinct face
            (loaded=false, distinct=false). Rendering in a fallback.

**`--font-body` has never rendered.** One of the two extracted faces, on every
screen in the game, since the assets were first synced.

#### Why it went unnoticed

Nothing broke. Text laid out, wrapped and measured; it was simply set in
`system-ui` instead of the face it was supposed to be. The only signal was a
`console.warn` from `fontLoader.ts`'s own self-test — which was working
perfectly, said exactly what was wrong, and had been saying it into an empty
room.

That self-test is the mechanism `A-guarantees` asks for, and it still was not
enough: **a mechanism nobody reads is not much better than a comment.** What
found it was a scan that treated console output as a first-class result rather
than as noise.

#### The defect, and the fix

The format-4 `cmap` subtable ends with **two** segments whose `endCode` is
`0xFFFF`. The spec requires strictly increasing end codes and one terminal
`0xFFFF` segment, so OTS rejects the font whole.

The repair is a recompile: decoding the table and writing it back rebuilds the
segments correctly — 34 malformed segments become 131 valid ones, strictly
increasing, with **all 2730 codepoints preserved**.

One subtlety cost a pass. `TTFont(src).save(dst)` **does not fix it**:
fontTools copies a table through untouched if nothing forced it to decompile,
so the bad bytes survive a round trip that looks like a rewrite. The table has
to be *read* before it will be rebuilt. A save that appears to recompile and
does not is the same shape as every other instrument failure in this file.

#### Where it lives, and why the name is unchanged

`assets-authored/fonts/49_Main_font2_Arial.ttf`, with the **same filename** as
the extracted original. `assets:sync` copies `SWFimported/` first and
`assets-authored/` second, so the authored file wins by arriving last, and the
sync prints `note ... replaces the extracted file` for every such case.

Keeping the name means the `@font-face` rule, the asset registry and the "never
rename an extracted file" rule are all untouched. `SWFimported/` stays pristine,
as the pre-commit hook requires.

`fontIntegrity.test.ts` pins both TTFs' end codes as strictly increasing and
terminating at `0xFFFF`, and asserts a format-4 subtable was actually found —
an empty match set would pass the loop in silence. Its counterpart asserts the
**extracted** file is still broken and that the shipped bytes differ from it, so
the test says "the repair is in place" rather than "nothing is wrong", and
cannot become a tautology if the export is ever fixed upstream.

### A54. Exit to Menu moves into the options panel, and only there

The action already existed — the dock's bottom-right **Main menu** button,
`ButtonMenu`, which every screen with a bar carries. On the options screen it
reads as disconnected from the settings beside it, so it now sits in the panel
directly above **Reset options**, and the dock drops its copy *on that screen*.

#### Per-screen, not global, and that distinction is the whole design

Removing `ButtonMenu` from the dock outright would have stranded every other
screen: it is the only way out of the bar, and Upgrades, Level select, Enemies
and Achievements all rely on it. So `BottomNav` gained `showMenu`, defaulting
to **true**, threaded through `ScreenShell` as `navMenuButton`.

The default matters. The dock is deliberately the same object on all five
screens — `A45` records that it does not even animate between them, because a
navigation bar that redraws on every press reads as a page load. An opt-out
that defaults to "keep it" preserves that; a switch that defaults to "hide it"
would let the bar drift screen by screen.

**One action, one place**, which is the same rule that keeps the auto-pause
checkbox off the pause panel (`PauseOverlay`) and the audio toggles off the
HUD (`A52`). The failure it avoids is a screen showing two controls that do the
same thing, which looks fine and is the thing `A52` was written about.

#### The assertion that catches the interesting failure

**A move that copies looks exactly like a move that works**, until you count.
Every other test here would pass with the button in both places: one finds the
panel's copy, another finds the dock's. So the pinning assertion collects every
button on the screen whose name matches "main menu" or "exit to menu" and
requires the list to be exactly `['Exit to Menu']`.

Its counterpart drives `BottomNav` directly on both settings — default and
`showMenu={false}` — because the claim is about the *default*, and asserting it
through the options screen alone would prove nothing about the other four.

Ordering is asserted with `compareDocumentPosition` rather than by reading
indices out of a list: it states "the exit button comes before the reset
button" directly, and stays true if something is inserted between them.

#### One layout trap, avoided by moving a single declaration

`.options__danger` carried `margin-top: auto`, which is what pinned the reset
block to the bottom of a card taller than its content. The new block sits above
it, so the auto margin moved to `.options__exit`.

**Leaving it on both would have been the defect**, and a quiet one: two auto
margins in a flex column *split* the free space between them, so the gap would
have opened **between the two buttons** rather than above the pair — the exact
opposite of "immediately above". jsdom computes no layout, so no unit test here
could have seen it.

Driven at five viewports, 1024x600 to 3840x2160:

    exit 55px  reset 55px  gap 65px  same-width true  above true
    in-card true  dock-menu 0  scroll 0

Identical height and width at every size, which is the mechanism rather than a
coincidence — the new button carries `gloss-pill options__reset`, the same
sizing class as the button below it, instead of restating its numbers. `gap` is
the caption line that sits between them and scales with the card.

### A53. The shop's blurbs are a hand-authored layer over the generated text

The shop showed `ButtonUpgradeInfo`'s own strings, which run to six lines and
spell out damage multipliers and boss resistances. Condensed to one line each
by request — `Bullets that explode on impact` became `Explodes on impact.`

#### The originals are not edited, and that is the design

`upgradeDescriptionData.ts` is **generated** from `ButtonUpgradeInfo.as` by
`npm run upgrade-descriptions:data`, and its header says so. Rewriting it would
put hand-written copy in a file the next regeneration silently overwrites.

So the AS3 strings stay exactly as extracted and the short forms live in a new
`upgradeBlurbs.ts`. Two things fall out of that which are worth having:

- **The detailed rules are still recoverable.** "A gummy bear does 1x, 3x then
  4x damage and dies on the fourth wall hit" is genuinely useful and genuinely
  not a tile caption. It is one lookup away rather than deleted.
- **The layers can be checked against each other.** A test requires every
  entry in the generated catalog to have a blurb *and* every blurb to
  correspond to an entry, both derived from the catalog rather than from a
  copied count. A regenerated table that gains a thirteenth primary fails there
  instead of quietly falling back to a bare weapon name in the UI.

A further test asserts the generated strings are still long — a longest above
200 characters, and at least one still carrying the AS3's multi-line shape. If
someone "tidies" by condensing the generated file instead, that is the
assertion that notices.

The brevity itself is measured rather than described: every blurb must be
strictly shorter than the string it replaces, **per entry** rather than in
total, so one enormous original cannot mask a blurb left long. The worst
compression ratio is required to be under two thirds.

#### A budget asserted, then disproved by measuring it

`BLURB_MAX_LENGTH` started at 42, with a docstring saying it "keeps every blurb
to one line" in the shop's detail window.

**That was written down, not checked, and it was wrong.** `shopblurb.mjs` drove
all 28 tiles at five viewports and found the longest blurb — `A beam that burns
through everything.`, 36 characters — wrapping to **two lines everywhere**:
28px of text in a 14px line box at 1024x600, and the same ratio up to
3840x2160. Every viewport failed together rather than only the small one,
because the detail column's width is a share of the viewport, so its wrap point
is roughly constant in *characters*.

The budget is 26 now, which is what the column actually holds, and the copy was
rewritten to fit it. Re-driven: the tallest blurb is exactly one line box at
every viewport (14/14, 19/19, 24/24). The claim is driven rather than asserted,
which is the whole difference between this pass and the first one.

#### Two instrument faults, both mine, both silent

Recorded because each produced a confident wrong answer about a page that was
fine.

- **`querySelector('.a, .b')` returns the first match in *document* order**,
  not the first selector's match. `'.shop-detail__blurb, .shop-detail p'`
  picked up a price paragraph, so the harness reported the longest blurb as
  `"$0"`. The fallback was there to be tolerant and made the query ambiguous
  instead.
- **`line-height` computes to the keyword `normal`**, which `parseFloat` turns
  into `NaN`. Every comparison against it was false, so all five viewports
  failed on a page where nothing was wrong. `NaN` in a measurement propagates
  as a *failure*, which at least fails loudly — the same bug in the other
  direction would have passed everything.

Both were caught only because the printed value was implausible (`"$0"` is not
a blurb; `NaN` is not a length). **A harness should print the value it is
judging, not just its verdict** — the same lesson as `A47`'s white money, and
the third time in this file.

The first run also failed for a third reason that was not a fault at all: the
main menu has no bottom dock, so `getByRole('button', {name: /upgrades/i})`
timed out. A probe of the menu's buttons showed only the slot rows, Play and
the audio toggles. The harness now takes the route a player takes — Play into a
level, pause, Quit Level, then Upgrades from the dock on level select.

### A52. The combat HUD loses its audio toggles, and the pause panel goes flat

#### There is now no way to mute during a level

`PartInterface.as` carries `bToggleSound` and `bToggleMusic` in the in-game
HUD, and this port did too. Removed by request, and the consequence is stated
plainly rather than softened: **a level has no audio control at all.** Both
toggles and both volume sliders live on the options screen, which is reachable
from the main menu and not from gameplay.

The AS3 also puts the toggles in the **pause panel** (`:426-476`), which is
where they would go if that turns out to matter. They were not added there in
this pass, because the same request asked for the panel to be minimal and its
own brief listed only Resume and Quit.

**This invalidated a documented justification, which is the part worth
recording.** `PauseOverlay`'s docstring explained the panel's missing toggles
as "a second copy would be two sets of the same control on screen at once" —
sound reasoning that depended entirely on the HUD copy existing. Removing the
HUD copy left a comment arguing for the right outcome from a premise that had
become false. The same applied to a test named
`does not duplicate the HUD audio toggles`: **its assertion still passes and
its rule is gone.** Both were rewritten rather than left, and the test now
carries a counterpart pinning the exact three actions, so it says "these three
and nothing else" instead of "two strings are absent" — which any panel
satisfies.

That is the second time in this file a *correct* assertion has been found
sitting on a dead reason. It is harder to spot than a failing test, because
nothing goes red.

#### The panel was a card with a 3px border; it is a surface now

It used `var(--panel)`, a **3px** `--panel-border` frame, and three identical
steel pill buttons. Three faults, all the same mistake — decoration standing in
for hierarchy:

- a 3px border reads as a frame around a widget rather than as a surface, and
  does badly what a change of tone and one soft shadow do well;
- three equally weighted buttons are a list, not a menu. The player is nearly
  always here to carry on, so **Resume** now carries the emphasis and the other
  two recede;
- the title was the largest thing on screen, spending the panel's emphasis on a
  word nobody needs to read twice. It is now a quiet eyebrow plus a title
  sized just above the buttons.

Background is `--hud-plate`, the same flat translucent grey as the minimap
ground and every HUD readout, so pausing reveals a surface the player already
recognises. The AS3's 75% black scrim (`:430`) is kept — it is darker than the
results overlay's 62% deliberately, because results are a screen you read and
pause is a screen that says the game has stopped.

**`--hud-plate` resolves because the panel is rendered *inside* `.hud`**, where
the property is declared, not beside it. A test asserts both the declaration
site and that the `var()` fallback is the same literal, so a future move out of
that subtree degrades instead of turning the panel transparent — a missing
custom property fails silently.

#### Two things caught while building it

**`--primary` does not exist.** The first draft wrote
`background: var(--primary, #3d8fd0)`, which would have taken the fallback
forever — the `var()` form of a dead reference, and invisible because it
renders exactly as intended. The real accent token is `--accent`, and it is
red: right for danger, wrong for the button that carries on playing. Resume is
**inverted** instead — near-white on the dark plate — which also keeps the
panel monochrome. Checking that every custom property a new rule names is
actually declared is cheap and was not being done.

**Focus and hover were the same declaration.** The old rule merged them into
one `filter: brightness()`, so a keyboard user could not tell which button was
focused while the pointer sat over a different one. The panel opens with focus
on Resume, so that distinction is the whole of its keyboard story; focus now
draws an outline and hover only changes the fill.

#### Driven

Six viewports from 800x400 to 3840x2160, opened through the **pause button a
player would use** rather than by setting the store:

    offset 0,0   border 0px   bg rgba(38, 40, 44, 0.72)
    3 actions, shortest 44px   audio controls 0   focus "Resume"   scroll 0

`offset` is the panel's left gap minus its right gap, so `0,0` is centred on
both axes rather than merely "inside". The background and border are read as
**computed** values — a stylesheet saying `border: none` proves the declaration
exists, not that it won. The 44px floor is the one measure here deliberately
not fluid: everything else scales in `vh`, and a touch target is a floor.

### A51. The minimap twitched because it was a world object, not because of rounding

The dots were un-rounded in `A50` and the panel still twitched. The rounding
was never the cause, and the real one is a frame-ordering bug worth recording
in full because nothing in this repo's own code looks wrong.

**Two causes, compounding.**

1. `drawMinimap` runs in `Scene.update`. `Camera.preRender` — which runs the
   follow lerp, applies `roundPixels`, and recomputes `worldView` — is called
   from `CameraManager.render` (`CameraManager.js:603`), **after** update. So
   the panel, anchored to `camera.worldView`, was positioned every frame from
   the *previous* frame's camera.
2. `camera.startFollow(this.player, true, 0.12, 0.12)` — the second argument is
   `roundPixels` — and `Camera.js:558` **floors** the scroll. With a 0.12 lerp
   the per-frame scroll delta is not smooth; it jumps between whole integers.

Together, the panel's on-screen offset each frame was
`(scroll[n-1] - scroll[n]) * zoom`: whole-pixel displacement in a pattern that
changes with the tank's speed. Which is a twitch.

**Why un-rounding the dots could not have helped.** The dots are drawn in the
panel's local space. What was moving was the panel underneath them, so every
dot moved together, by the same amount, however precisely each was placed
within it. A50 fixed a real quantisation and left the visible symptom intact —
a good reminder that a plausible cause that is genuinely a defect will still
not fix a symptom it does not cause.

#### The fix, and the transform that sank the first attempt

The panel is screen furniture, so it is now in screen space:
`setScrollFactor(0)` on the `Graphics` **and on its mask**, which must match or
it would clip a rectangle of the world instead of the panel. Position comes
from `minimapScreenAnchor`, which reads the camera's size and zoom and **never
touches the scroll** — so the frame ordering stops mattering rather than being
timed around.

T146 tried exactly this and the panel rendered mid-arena at double size, which
is why the anchor's arithmetic is now pinned rather than commented. A
scroll-factor-zero object is placed in camera-pixel space with the zoom applied
**about the camera's centre**: a point at `x` renders at
`(x - width / 2) * zoom + width / 2`. That was measured at the time — at zoom 2
with `camera.width` 1280, 552 landed at 464 — so the anchor inverts it, solving
for the coordinate that renders where the panel should be.

The tests drive the *rendered* position through that transform rather than
comparing against the function's internals, at zoom 1, 2 and 0.5. At zoom 1 the
inversion is the identity, which is worth knowing: the room-fill zoom is a
prototype enabled on a subset of levels, so most levels exercise the trivial
case and only those exercise the interesting one.

`minimapAnchor` and its five world-space tests were deleted rather than left
beside the replacement.

#### Two reverts and a colour

**Every enemy is red again.** The per-family palette from `A50` was authored,
not ported, and it is reverted to `:675`'s single `beginFill(16711680)`. The
`BESTIARY`-derived coverage test went with it. The assertion that replaces
them is driven against its counterpart on the same plan — the *ground* is a
different colour — so "everything is one colour" cannot pass it.

**The ground is `--hud-plate`.** `:657` is an opaque `6710886`, chosen when the
panel sat on solid chrome below the camera; here it floats over a live arena
and an opaque grey block reads as a hole in the world. It is now the same
colour and alpha as every DOM readout, `rgb(38 40 44 / 72%)`.

**The two values are checked against each other, not both copied by hand.** The
test parses `--hud-plate` out of `global.css` and asserts the plan's ground
fill matches it. A colour duplicated across a stylesheet and a TypeScript
constant is exactly the kind of pair that drifts silently — and this file
already records a case where one did.

That divergence also broke a neighbouring assertion honestly: a blanket "every
fill except the viewport is opaque" was accurate for `:657` and `:672` and is
now false. It was narrowed to exclude the ground **by name**, with the reason,
rather than loosened — excluding it silently would have let a *dot* go
translucent unnoticed.

### A50. The minimap: round dots, coloured by family, and why it would not move

Four changes, three of them divergences from `PartInterface.drawMinimap`.

#### The panel would not move, and the margin was never the reason

T197 moved `MINIMAP_MARGIN` from 8 to 2 and the panel visibly stayed put. That
was reported back as "he didn't move it", and it was correct.

`GameplayScene.drawMinimap` adds `HUD_BOTTOM_CLEARANCE_CSS` to `inset.bottom`,
and that constant was **96** — measured, carefully and with a comment saying
so, against `.hud__row--bottom`: a full-width HUD row carrying the Menu button
and the audio toggles, reported at `top` 89 CSS px above the canvas bottom at
1280x800.

**T194 deleted that row.** The bottom edge is now `.hud__bottom`, a
`1fr auto 1fr` grid with the hotbar in the middle track and **nothing at all in
the right one**, which is where the panel sits. So a 6-unit margin change was
being made against a 96px reservation for furniture that no longer existed.
The clearance is now 8.

**This is the failure mode of a well-documented constant.** The comment named
its method, its measurement and its viewport, all accurately — and every one of
those facts was about a DOM element that had since been removed. A citation
records where a number came from; it cannot notice when its subject is deleted.
The tell available at the time was that `.hud__row--bottom` appears nowhere in
the stylesheet any more, and nothing connected the two.

Driven at five viewports: **0 HUD elements overlap the bottom-right corner
region** the panel occupies. The panel itself is Phaser-drawn and not in the
DOM, so what is measured is that nothing is in its way; the anchor arithmetic
is pinned separately as a pure function, including that only a real safe-area
inset may push it off the corner and that a negative inset is ignored.

#### The dots are circles, which forced the clipping to change

`:678`/`:682` draw every marker with `drawRect`, so the AS3's dots are squares.
They are circles now — at 4px a square reads as a pixel artefact rather than a
marker, and the tank, the flag and the enemies are all round objects.

**That is not a cosmetic swap, because it broke the clipping.** Every fill used
to be clipped arithmetically by `clampToPanel`, dots included, and a test
asserted exactly that. Clipping a dot's bounding box moves its **centre**, so a
dot at the room's edge slid inward rather than being cut off — it reported the
enemy somewhere it was not. That was invisible while dots were squares drawn
from their top-left corner and became a real positional error the moment they
were drawn from their centre.

So dots are now **culled**, not clipped, and the overhang is cut by a geometry
mask on the `Graphics`. That is what the AS3 does — `minimap.mask =
minimapMask` (`:286`) — rather than something this port invented to solve its
own problem. The rectangles (ground, viewport) are still clipped arithmetically.

The old test was **replaced, not repaired**, with a note saying which: it
described the code accurately at the time and restoring it would reintroduce
the defect. Its replacement asserts the rectangles are still clipped *and* that
a dot's centre equals its projected position, which is the rule that matters.

#### Colour by behaviour family — authored, not ported

`:675` is `beginFill(16711680)` for every enemy. There is no per-type colour in
the AS3 to port, and none in this game either: enemies are drawn from SVG
shapes and are never tinted, so there is no "the enemy's colour" to read off
anything. The palette is therefore **authored**, and that makes the grouping
the only defensible part of it.

Five families rather than twenty hues — bulk, fast, evasive, ranged, support.
Twenty colours on a 4px dot is twenty colours nobody can distinguish; five is a
distinction a player can act on at a glance. A boss keeps the AS3 red whatever
its type, since it is already marked by being twice the size and is the one dot
that must never be mistaken for anything else. An unclassified type falls back
to the same red rather than vanishing.

**The coverage guarantee is mechanised against `BESTIARY`**, not a copied count
of 20. `EnemyTypeName` is a type and cannot be enumerated at runtime, but
`BESTIARY` is the same twenty ids as a value — so a type added to the game
fails the test until it is given a family. A `toHaveLength(20)` would only fail
when someone edits the palette, which is the one moment they are already
thinking about it. The test also asserts every family is used, since an unused
one is a colour nobody ever sees.

#### The dots move sub-pixel now

`:678`/`:682` wrap each finished coordinate in `Math.round`, and that was
ported faithfully. It is what made the dots crawl: an 80px panel over a
2000-unit room is 25 world units per pixel, so a dot holds still through 25
units of real movement and then jumps a whole pixel.

`marker` no longer rounds. `fillCircle` antialiases, so a fractional position
renders as smooth movement rather than a blurred square. **The rect fills still
round** — a half-pixel rectangle edge is a blurred line, not a smoother one —
and a test pins both halves of that split so neither drifts into the other.

Note the update rate was never the problem: `drawMinimap` is called every frame
and ungated, exactly as `PartInterface.update` has it. The suggestion to raise
the sampling frequency would have found nothing to raise.

### A49. The objective reads as progress, and the live enemy count is gone

The HUD said `17 left`, and on Flag and Boss levels `4 on screen`. Both are
replaced by one line that reads `3/20 killed`, or `3/20 collected` on a Flag
level.

**A countdown cannot recover the total, which is the part a player needs.**
"17 left" says nothing about whether that is most of the level or the last of
it. So `wave:changed` carries `enemiesKilled` **and** `enemiesTotal` rather
than a single remaining figure, and the same for flags.

**The live population figure was worse than uninformative.** It reported
`this.enemies.length` — the enemies currently on screen — which goes *up* when
the level spawns, moves every second or two, and supports no decision a player
makes. It was there because Flag and Boss levels were treated as having no
finite total.

**Boss levels do have one.** `waveState.ts:140` seeds `enemiesLeft` from
`spec.totalEnemies` for a Boss level exactly as for an arena level, and
`isWaveComplete` reads it down to zero. Only Flag levels are genuinely
open-ended in enemies, and they are measured in flags because that is what ends
them (`flagsLeft <= 0`). So the `indefinite` branch narrowed from
`mode === 'Flag' || mode === 'Boss'` to `mode === 'Flag'`, and Boss levels now
report real progress.

`killed` is derived by subtraction from the same three-places accounting the
scene already keeps — announced, pending, alive — rather than counted into a
separate tally. A parallel counter is a fourth number to keep in step, which is
exactly the shape of the `removeEnemy` idempotence bug recorded in this file.

`FlagCounter` was deleted rather than left unrendered: it was a second widget
making the same claim in the opposite direction ("7 flags left").

#### Two removals

**The diagnostics panel is gone**, not merely hidden — `DiagnosticsPanel.tsx`
deleted, its ~2.3KB of CSS removed with the `.pill` classes only it used, its
entry struck from the `DEV_AIDS` inventory, and the stale prose in
`viewport.ts` that referred to it in the present tense corrected. It was
already behind `import.meta.env.DEV` and so never shipped; it was removed
because it is visible in every development session, which is where it was in
the way.

Its removal emptied the `data-silent` exemption list in `buttonSounds.test.ts`
to `[]`. **That assertion now also passes when the scan finds no files at
all**, so a file-count counterpart was added beside it. An empty expected value
is the classic vacuous check.

**The minimap margin went 8 to 2.** The safe-area inset is added on top of it
in `minimapAnchor`, so a notched phone still keeps the map clear of the rounded
corner.

### A48. The health bar is a pill, and its colour is computed, not painted

Three changes, one of which is a change in kind rather than degree.

**Money went back to the top-left**, health stayed bottom-left. They were a
pair in `A47`; they are now one readout per corner. The money is a figure
checked between fights, the health bar is read mid-fight.

**The bar is a pill** — `border-radius: 999px`, not `50%`. A percentage radius
is a share of each axis and would track the box into an ellipse as the bar
resizes; a large length clamps to half the *shorter* side, which is what makes
the ends semicircular at every size. Note this beats the shared
`.hud-stat, .hud-health, .hud-reload` radius **on source order, not
specificity** — both are one class. Moving the rule up the file would silently
restore the old corners, so a test pins the ordering.

#### The colour stopped being a gradient, and that is the substance

The fill painted `linear-gradient(90deg, red, amber 45%, green)` sized to the
bar's full width. The colour at any point was therefore a property of **where
you looked along the bar**, not of how much health was left — a full bar
carried its own red end at all times, and the request was "green at 100,
grading to red as HP drops". Those are different things.

So the ramp moved out of CSS into `src/game/ui/healthColour.ts`, which returns
**one flat colour for the whole fill** from the fraction remaining. Same three
colours at the same three positions as the gradient it replaced, so the colour
shown at a given health level is the colour the old bar showed at that point
along its length.

Three stops rather than a `color-mix()` of two: a straight red-to-green mix
passes through a muddy olive at the midpoint, where the amber stop keeps it
legible. It is also testable without a browser, which a `color-mix()` in a
stylesheet is not.

**"Gradual" is pinned as two separate properties**, because either alone is
satisfiable by something wrong:

- **Strict monotonicity** across 101 samples — `redness` (red minus green)
  must fall at every single step. A stepped ramp holds one colour across a
  band, which shows up here as two adjacent samples failing to differ. Note
  neither channel is monotonic on its own; red runs 180 up to 232 and back down
  to 74, so asserting on one channel would fail a perfectly good ramp.
- **A bounded step** — no single percentage point may move any channel by more
  than 5 units. Monotonicity alone permits a ramp that sits still and then
  leaps. The bound is derived rather than guessed: the steepest segment covers
  143 units of green over 45 points, so ~3.18 per point.

#### The harness that could not be written twice

The wiring claim — that the computed colour reaches the pixel — needed a
browser, and **two drafts of the driver were built on handles that do not
exist**: `window.__gameStore`, then `window.__GAME_EVENTS__`. This build
exposes only `__PHASER_GAME__`, `__arena`, `__soundQueue` and
`__tutorialPanel`, and the last three are DEV-only, so under `vite preview`
there is no handle to the store at all. Either draft would have set nothing,
read the same colour five times, and reported a flat ramp.

The fix was to stop looking for a driver and check what the DOM already
publishes. The bar carries its own health in `aria-valuenow`/`aria-valuemax`,
so the claim becomes a **pairing**: the fill's computed `background-color` must
equal the interpolation of that same fraction, recomputed in the harness from
the AS3-era stops rather than imported from the module under test — importing
it would make the check agree with the code by construction.

Sampled over 20s per viewport while the tank took real damage:

    9 distinct health values, 0 mismatches
    100/100 -> rgb(74,222,106)   95/100 -> rgb(88,218,102)
     90/100 -> rgb(103,214,97)   85/100 -> rgb(117,210,93)

and `radius 999px` on bars of 18, 20 and 26px, `fill-image none` everywhere.

**The generalisable part**: the claim divided where the evidence divides. The
ramp function is provable offline and is proved there exhaustively; only the
wiring needs a browser, and the browser check is a *pairing* between two things
the page publishes rather than a value the harness had to inject. Reaching for
an injection point that does not exist cost two drafts.

### A47. The HUD is flat grey, and the money is a green dollar figure

T194 built the HUD as glass, matching every menu screen in this project. That
was rejected for the HUD specifically, and the reasoning is worth keeping
because it is a real distinction rather than a change of mind: **the menus are
the only thing on screen and can afford decoration; the HUD sits on top of a
fight, where every rim, shadow and gradient is a second edge competing with the
arena.** So: `border: none`, `box-shadow: none`, `background-image: none`, one
`--hud-plate` grey at 72% alpha, and a small radius.

The translucency is for legibility over nine world themes, not for depth. One
token means "make the HUD darker over a bright world" is a one-line change
rather than five.

Health and money moved from the top-left to the **bottom-left**. The top-left
corner now holds nothing at all, which is the most open the arena has been.

Money reads `$1,500` — green, comma-grouped by `Functions.formatNumber` rather
than `toLocaleString`, which yields `1 500` in fr-FR. The `$` is written into
the text node rather than added by a `::before`, so a screen reader reads it
with the figure instead of skipping it as decoration. The coin glyph and the
"coins" label are gone; the sign carries both.

**What stayed, and why.** The red-amber-green health ramp. It is the one thing
in the HUD carrying information rather than style — a bar readable in
peripheral vision — and flattening it to grey would cost the reason the bar
exists. Its lit top edge was pure glass and is gone. The `backdrop-filter`
decision from `A46` is untouched and still pinned.

#### The measurement, and the bug it caught

Driven at six viewports in a live level, 1024x480 to 3840x2160:

    hotbar-skew 0px   drift-at-7-digits 0px   glassy-panels 0   scroll 0

`glassy-panels` reads **computed** values, not the stylesheet — a `border: none`
in the source proves the declaration exists, never that it won. All four panels
came back `0px` border, `none` shadow, `none` background-image.

`hotbar-skew` is the load-bearing one. The bottom row is `1fr auto 1fr` rather
than a flex row, so the two side tracks are equal by definition and the hotbar
is centred on the **arena** rather than on the space the health cluster leaves
over. The harness proves that by rewriting the money to `$9,999,999` and
re-reading: **0px drift**. Under a flex row it would have shifted by half the
growth, and the two constructions are indistinguishable at `$0` — which is what
any screenshot of a fresh level would have shown.

**The first run printed `money $0 rgb(255, 255, 255)` beside an `OK`.** The
money was white. `.hud-money__value` and `.hud-stat__value` are both (0,1,0)
and the money rule sits earlier in the file, so source order handed it to the
base class. This is the **sixth** equal-specificity override in this stylesheet
to lose to its own base, and the fix is the same as the pause button's two
lines above it: state it at two classes.

Two things about how it was found, both worth more than the bug:

- **The instrument printed the wrong value and still said OK**, because the
  colour was in the output line and not in the predicate. A value that is only
  printed is not checked. The predicate now includes it.
- **The regression test asserts the selector's shape, not the colour.** A test
  reading "the money is green" is exactly what a CSS-only scan would have
  passed while the rendered figure was white — the property was present, it
  just lost. `expect(cssCode).toMatch(/\.hud-stat__value\.hud-money__value/)`
  cannot pass that way, and it carries a counterpart asserting the base rule it
  has to outrank still sets a colour, so it retires honestly if that changes.

### A46. The HUD is three corner clusters, and it deliberately has no blur

Two full-width rows became three clusters: health and coins top-left, wave,
flags, audio and pause top-right, the weapon hotbar centred along the bottom.
The rows put furniture along the top and bottom **edges**, which is where
enemies enter, and the HUD read as a frame around the game rather than as
instruments beside it. Nothing crosses the middle now.

`.hud` is a 3x3 grid whose outer columns are `auto` and whose middle is
`minmax(0, 1fr)`, so a cluster cannot drift inward however wide its content
grows. The hotbar spans all three columns and centres itself, so it is centred
on the **arena** rather than on whatever the left cluster happens to measure.

**Driven at six viewports**, 1024x480 through 3840x2160, in a live level
(`hudfit.mjs`): five panels present at every size, **zero** intruding on the
middle 44% x 44%, zero escaping the HUD box, zero overlapping each other, and
no document scroll. Padding rises 8px to 16px across that range and stops,
which is the `clamp(0.5rem, 1.4vh, 1rem)` cap doing its job.

#### No `backdrop-filter`, which is what the request asked for

The request was explicit: "subtle `backdrop-filter` transparency". It is not
there, and this is the entry that says so.

`D-FPS` measured **52 fps lost** to a `backdrop-filter` over this same Phaser
canvas on a *menu* screen, where the canvas is idle. The HUD sits over that
canvas while the game is running, so every frame invalidates the blur's whole
source region. The reasoning says that is strictly worse than the case already
measured at 52 fps.

**It is reasoning, because the measurement could not be made.** A paired
harness was written to answer it in the place that matters, and both instrument
configurations failed:

    default headless      shipped 30 30 30 30 30   blurred 30 30 30 30 30
    unpinned + SwiftShader  shipped 3333 1 1 1 2500   blurred 2500 0 1 1 1

The first is headless Chromium pinning `requestAnimationFrame` at 30, so both
arms read the display loop rather than the game. The second unpins the frame
rate but falls back to software GL, where the median is 1 fps and the worst
frame is 1.4-2.6 seconds. Neither can see a compositor cost. **Reported as
inconclusive rather than as "the blur is free"** — a flat reading from a
saturated instrument is this project's most expensive recurring failure, and
"0 fps difference" is exactly the clean, decisive, wrong number that pattern
produces.

So the glass reading is built the way `.bottom-nav` builds it: a lit top rim,
a dark vertical ramp and a drop shadow. The panels end up opaque enough that a
blur behind them would be paying for pixels nobody can see. `Hud.test.tsx`
pins the absence — every rule whose selector mentions a `hud` class is scanned
for `backdrop-filter`, with the counterpart assertion that the property is
still present elsewhere in the sheet, so the test cannot pass by matching
nothing.

**What would settle it** is a frame profile on real hardware with a real GPU,
which is the user's machine and not this harness. If it turns out cheap there,
the blur is one declaration on the shared surface.

#### Two things found on the way in

- **`.glass-tile` does not exist.** It was named in an earlier audit note as a
  primitive to extract and never was; `grep` finds it 0 times in `global.css`.
  The real shared primitives are `.gloss-pill` and the per-screen tile recipes.
  The note was a plan being read back as a fact.
- **A pause button is a divergence, and it is one this entry is claiming.**
  The AS3 has no pause button either — `PartGameArea.as:2682` triggers on
  `Main.keyP || Main.keyEsc` plus an auto-pause on focus loss, and the four
  `ButtonPause*` classes are the buttons *inside* the panel. The port matched
  that faithfully, so pause was keyboard-only via `usePauseControl` and the
  overlay was unreachable on a touch device. The request placed a pause control
  top-right, so one now exists and replaces the `Menu` button that sat there.
  It emits the same `ui:pause` the keys do, so there is one path, not two.
  Its icon is drawn from borders rather than set as a glyph: `SWFMainFont`
  carries 581 glyphs with no guarantee of either symbol, and a missing-glyph
  box in the corner of a live fight is not recoverable.

The health bar's colour ramp is sized to the **bar**, not to the fill
(`background-size` fixed to the bar's width). Without that a bar at 20% shows a
squeezed copy of the whole red-amber-green ramp and is green at its right edge,
reading as healthy at the moment it is not.

### A45. Screens pull into focus — opacity and blur, nothing moves

Every screen is a sibling in `App.tsx` that returns `null` unless it is the
active one, so a navigation **unmounts** one subtree and **mounts** another. No
moment exists where both are present, which rules out a true crossfade and
makes a mount animation exact — the browser starts it when the element appears,
so it cannot desynchronise. What sells it as a transition rather than a pop is
that the Phaser canvas and the wallpaper persist, so content resolves into a
scene that was already there.

**170ms**, `opacity 0 -> 1` with `blur(2px) -> blur(0)`, on a front-loaded
`cubic-bezier(0.16, 1, 0.3, 1)`, on each screen's bar and body. **No
`transform` anywhere.** T191 rose 10px and scaled from 0.985 and was rejected
as too heavy; the movement was what read as heavy, not the duration.

The radius has come down twice — 8px, 4px, now 2px — and the duration once,
220ms to 170ms. Each time the complaint was that the effect read as *harsh*,
which is a look decision rather than a performance one. The curve is
front-loaded so the screen is sharp for most of the animation and the tail is
only the last of the fade.

The dock does not animate — it is the same object on all five screens, and a
navigation bar that blurs out and back each time you press it reads as a page
load. The menu's wallpaper fades without blurring: it is full-bleed, and a blur
softens an element's own edges into transparency, which would halo the canvas
around all four sides for the animation's length.

#### `backwards`, and it now matters for a second property

The `from` state must apply before the first frame paints or the screen flashes
sharp and then blurs. `backwards` and `both` both do that; `both` also holds
the `to` state forever.

T191 measured what that costs with a transform: `getComputedStyle().transform`
read `matrix(1, 0, 0, 1, 0, 0)` on every screen after the animation finished,
because a *held* `transform: none` is not `none`. **Swapping the property for
`filter` changes nothing** — a held `blur(0)` is not `filter: none` either, and
a filter makes its element the containing block for fixed descendants exactly
as a transform does. It is the fill mode that is the bug, not the property.
`transition.mjs` now reads the computed `filter` after the animation and gets
`none` on all four screens.

#### The blur costs one frame, and the first measurement of that was wrong

Recorded because the mistake is the instructive part.

`D-FPS` is the standing warning — a `backdrop-filter` over this same live
canvas cost 52 fps — so the blur was measured rather than assumed. The first
attempt ran all the animated navigations, then all the unanimated ones, and
read **33ms against a 17ms baseline**. Then the same baseline came back
**17/33/33/17** on the next run: the machine's load had moved between the two
blocks, and part of what had been attributed to the blur was that.

Re-measured by **alternating the two conditions on the same screen** — the
shop, 28 tiles, the heaviest — over seven pairs at 1920x1080, worst frame per
navigation:

    blur off   17 17 17 17 17 17 17    median 17ms
    blur on    50 33 33 33 33 33 50    median 33ms

So the blur costs **one to two dropped frames** at the start of a navigation,
reproducibly. Accepted rather than unnoticed: one or two frames out of the ~10
in a 170ms transition, at a moment when the content is deliberately blurred.
`prefers-reduced-motion` removes it entirely.

**Re-measured at 2px/170ms, it did not come out cheaper**, and that is recorded
rather than tidied away: `off 17ms / on 50ms median (33 33 33)` against the
4px/220ms `off 17ms / on 33ms median (50 50)`. Both land on the same two
values in different proportions and seven pairs cannot separate them. There is
also a real reason a lighter blur might not be cheaper — the curve is
front-loaded, so most of the delta happens in the first two or three frames and
a shorter duration concentrates the same work further. Less total work, more
work per frame.

**The lesson is the sampling design, not the number.** A clean, decisive number
from a noisy instrument is this project's most expensive recurring mistake, and
block-then-block sampling is how load drift gets read as a result. Paired
alternation costs nothing extra and cannot.

### A44. The level detail panel draws the same medals, several times larger

The tile's three medals repeated in the window at panel scale, each in a dark
inset socket so an unearned slot reads as empty rather than as a smudge, and so
the row keeps its width whatever has been earned.

**One component at two sizes, and the tier colour belongs to neither.** `Medals`
takes a `block` — `level-grid` or `levels` — and the three tiers are
`.medal--gold|silver|bronze`, shared. Two size rules over one colour rule is
what stops a panel medal and a tile medal ending up different golds, which is
precisely how the three glass tile surfaces drifted apart (`A38`).

**The shape is the level's mode**, not a star. `:874` builds the icon from the
mode before `:898` sets its tier frame, so a Flag level earns flags and a Boss
level earns skulls — the shape says what the level is and the colour says how
well it went. The panel asks the same question the tile does; a test compares
the two rendered glyphs rather than trusting it.

The row is always three sockets. A panel that grew as the selection moved would
change height under the pointer, and this screen's whole layout guarantee is
that it never scrolls.

#### The glow on the tile medals had never rendered

`.level-grid__medal--gold` and its two siblings carried `text-shadow`, which
paints nothing here: `LevelModeIcon` renders an `<svg>` and the glyph is a
filled path, not text. Three declarations, shipped since T173, doing nothing.
They are `filter: drop-shadow` now, which follows the shape's alpha — so the
tiles gain the glow they were supposed to have, as a side effect of moving the
colours somewhere shared.

#### The panel was clipping its own contents, and no harness had ever asked

The important part of this pass.

`fitlevels.mjs` measured the grid against its plate, the cells' ratio, the
body's scroll and sibling overlap — but never whether a *panel* holds what is
inside it. That check is the one T179 added to the bestiary's harness and T187
to the options one; this is **the third harness to need it**, and it found
`.levels__detail` cutting its own enemy roster by **67px at 1024x480, 119px at
1280x540 and 61px at 1280x600** on the first run.

Invisible by construction: the panel is `overflow: hidden`, so nothing
overflowed the body, nothing scrolled, and every other number in the harness
was green. It was clean from 1366x768 up, which is the usual shape — the
viewports anyone develops on said the layout was correct.

**How much of it predates this pass is not established**, and the honest reason
is that the panel has never been asked. The medal row certainly contributed;
the roster was already what was being cut. Both are fixed by the same
correction the other two screens needed — `--pane` capped by height as well as
width, `min(clamp(15rem, 26cqw, 34rem), 62cqh)`, which does not bind from
1366x768 up where the panel already fitted.

That makes three screens whose windows were sized by width alone while their
contents scale in both. **The pattern is now worth stating as a rule rather
than rediscovering**: if every size inside a box is a multiple of one lever,
that lever needs a height term, because the box's height is not a multiple of
it.

#### PLAY LEVEL sits above the medals — T189, then T190

Recorded as a pair because the first move was wrong and the record should say
so rather than read as though the second was the plan all along.

**T189** anchored the button to the panel's floor with `margin-top: auto`, on
a misread request. **T190** undid both halves: the button is directly under the
level's name and mode, with the medals below it, and the anchor is gone. The
order is the level's identity, the action, then what is known about it — the
medals read as this level's record rather than as one more thing to get past
before the button.

**Both halves had to go, and leaving either would have been worse than
neither.** The DOM order without removing the anchor puts the button back below
the medals on any viewport with spare height, which is every one from 1366x768
up; removing the anchor without the reorder leaves it under them at the bottom
of the read. The test pins the order as a *relative* one — the button is above
the medals — rather than as a child index, so inserting a row between them
fails and appending one at the end does not.

Neither move changed the geometry: measured before and after both times, all
eight viewports byte-identical with `clipped[]` everywhere. `margin-top: auto`
takes only what is spare and collapses to zero when there is none, which is why
T189 cost nothing on the short viewports where this panel was clipping until
the fix above — and why removing it costs nothing either.

**Measured** at 1024x480 through 3840x2160: 45 cells, ratio 1, no panel
clipping its own contents, no grid spill, no overlap, `scrollHeight ===
clientHeight`, no horizontal overflow.

### A43. Options is two glass cards, and it omits two of the AS3's controls

The last screen. Two cards centred — five gameplay preferences on the left,
sound and the reset on the right — built to the same rules as the other five.

#### Four of the AS3's eight controls are not here, for four different reasons

Worth separating, because "not ported" covers very different things:

- **Graphics quality** (`ButtonOptionGraphics.as:93-101`) sets `stage.quality`,
  Flash's vector rasterisation setting. This port rasterises SVG at load and
  renders through WebGL; there is no runtime equivalent, so the control would
  change nothing. **Not applicable**, recorded in `gameplayOptions.ts`.
- **Difficulty** is genuinely on the AS3's options screen and is deliberately
  only on level select here, where it sits beside the medals it decides and the
  progress slot it writes to. **A divergence**, and the reason is that two
  places to set one value is how they drift.
- **Save conversion** migrates between local and Kongregate online slots — the
  third-party surface is out of scope.
- **`windowUL`** is `A11`; the key is still read and written so an existing
  player's value survives, and only the row is gone.

Both omissions the maintainer asked for are pinned by test, because the failure
mode is a **re-addition** by someone completing the AS3's list, which nothing
else in the suite would object to. The difficulty check looks for
`.difficulty__button` as well as the three labels, so a copy-paste of level
select's control fails rather than quietly giving the value two homes.

#### Reset is preferences, not progress — and that is the AS3's own line

The user asked for a "clear save data" button. `ButtonResetOptions` →
`SaveManager.resetOptions()` (`:1142-1147`) is `optionsSave.clear()` followed by
`initAndLoadOptions(true)`: it resets **settings**. `gameSave` is untouched, and
deleting a slot is a different control that this port already has, on the save
picker, ported from `ButtonGameSave:453` with its own two-step confirm.

So the screen gets the button the original has, labelled for what it does, and
`optionsService.test.ts` drives the separation rather than asserting it — it
writes two save slots, resets, and requires both to survive. That is the claim
that would quietly stop being true the day someone reached for a convenient
`localStorage.clear()`.

**It resets audio too**, because `:1144` clears the whole store and this port
keeps `soundOn`/`musicOn`/`soundVol`/`musicVol` in it. Resetting the checkboxes
and leaving the volumes would be a *narrower* reset than the original's.

One bug found while testing it: the reset published audio through
`publishAudioOptions`, which reads the live `SoundManager` and **returns early
when there is not one**. It now emits the values it just committed, so the
sliders cannot sit at stale numbers in any context without a manager.

#### The audio switches here are not `AudioToggles`

`AudioToggles` draws `ButtonToggleSound`/`ButtonToggleMusic` and lives in the
HUD and the main menu — the places the AS3 puts them (`PartInterface`), where
the picture is the label. This screen uses the same switch its five preference
rows use, so seven controls of the same kind look like it.

**That is presentation, not a second implementation**: both emit
`ui:set-audio`, both read `audioOptions` from the store, and neither holds
state. There is no rule here to keep in two places.

#### The card was sized by width alone — T179's defect, caught before shipping

Everything in a card is a multiple of `--card`, so the taller column's content
runs about 1.16 times it. A width-only clamp gave a 343px card needing 397px of
height inside a 314px box at 1024x480, and `overflow: hidden` meant it **clipped
in silence**: no scrollbar, no body overflow, nothing a page-level check could
see. 83px over at 1024x480 and 1280x600, and nothing from 1366x768 up.

Identical in shape to the bestiary's window (`A37`), and the difference is that
this time the harness had the per-box clipping check **from the start** — the
one T179 added after finding it the hard way. It reported `clipped[card0+83]`
on the first run. That is what a trap being written down is for.

**Measured** at 1024x480 through 3840x2160: two cards, seven switches, two
sliders, one reset, no card clipping its own contents, no overlap between rows
or between the cards, `scrollHeight === clientHeight`, and no horizontal
overflow.

### A42. The bottom bar grows on a large screen, and 40px became its floor

`A41` established that the six bar clips are pure vector and that 40px is the
size they were exported at. T185 used that as a *ceiling* — the art was never
scaled up. On a 2560x1440 monitor that leaves a 40px bar on a very large
screen, which is a small target and hard to read.

So 40px is the **floor** now. Growing vector art costs nothing, which is the
whole point of having checked: `height: min(clamp(40px, 6vh, 80px), 6vw)`, two
constraints binding at opposite ends —

- `clamp(40px, 6vh, 80px)` is what the window's *height* can afford: native at
  1024x480, 46px at 1366x768, 65px at 1080p, and the 80px ceiling from about
  1340px tall.
- `6vw` is what its *width* can afford. The row needs roughly 14.1
  button-heights across, which is what keeps two 5:1 tabs and four icons inside
  a 360px phone.

`min()` takes whichever is scarcer, so one rule covers a 4K desktop and a
phone. Measured: the art runs 108x22 at 360x640 up to **400x80 at 2560x1440**,
never spilling its button and never overlapping a neighbour.

The bar is also lifted off the bottom edge, by padding rather than margin — the
plate still reaches the screen edge, so there is no strip of wallpaper under a
floating bar and `--safe-bottom` still works on a phone with a home indicator.

#### The lift cost a layout 4px, and the first fix landed on the boundary

Worth recording as an instance of a rule this document already states: **the
bar is the `auto` track under five screens' `1fr` bodies, so anything added to
it is taken from all of them.**

The dock went from 58px to 128px at 2K. Four of the five screens absorbed it.
The shop did not, at exactly one viewport — 1280x540, the widest and shortest
measured, where the catalogue is already tightest: `scrollHeight 379` against
`clientHeight 375`.

The fix is that the lift is a share of the window's height rather than a flat
value, so it yields on a cramped window. **The first attempt at it did not
work, and how it failed is the useful part**: at `1.7vh`/`1.3vh` the dock came
to 58.2px against the 58px it had been, and the shop still failed by a
sub-pixel. A fix that lands on the boundary is not a fix, it is the same bug
rounded differently. At `1.5vh`/`1.1vh` the dock is **56px there — 2px better
than before this pass** — so the shop has more room than it started with rather
than exactly as much.

**Measured** after the change, all four screens re-run: shop, bestiary,
achievements and level select fit at every viewport, and the dock fits from
360x640 to 3840x2160 with no art outside its button, no art overlap, no
clipping and no document scroll.

### A41. The bottom bar keeps its extracted art; only its sizing was wrong

T183 replaced the bar's six `Button*` clips with CSS pills and T184 turned them
into six competing styles. Both are **reverted** — the maintainer wanted the
ported art kept and its layout fixed, not the art replaced. This entry records
what was actually wrong, because the answer turned out not to be what T183
claimed.

#### The upscale argument was wrong for this bar

T183 justified dropping the art as "40-unit exports drawn at whatever height
the viewport gives, the same upscale problem `A40` found". Two things are wrong
with that:

- **The art was never upscaled.** `.nav-button` was `height: 2.5rem`, which is
  40px at the default root size — *exactly* the height these clips were
  exported at. Measured at all eight viewports from 360x640 to 3840x2160, the
  drawn boxes were 200x40 and 41x40 every time. There was no scaling at all.
- **These clips could not pixelate anyway.** All six are pure vector: every
  shape in `ButtonUpgrades`, `ButtonLevelSelect`, `ButtonAchievements`,
  `ButtonEnemies`, `ButtonOptions` and `ButtonMenu` was checked for an embedded
  `<image>` and none has one.

**That last check is worth keeping, because the opposite case is real.** Some
JPEXS exports *are* raster payloads wrapped in SVG — `910.svg` carries a
base64 PNG with `image-rendering: optimizeSpeed; image-rendering: pixelated`
baked in. Those genuinely cannot be scaled up. So "it is an SVG" is not the
answer to "will this pixelate"; **"does this SVG contain an `<image>`" is.**

`A40`'s shop plate was a separate case and its fix stands on its own ground: a
flat disc is cheaper and sharper as a CSS circle regardless.

#### The defect that was actually there

`.nav-button--wide` carried `max-width: 40vw`, added so two 200-wide tabs plus
four icons would fit a narrow phone. It caps the **button**; the `.chrome-art`
inside takes its width from the clip's aspect ratio and `width: auto`, so the
picture ignored it. Measured at 360x640: art 200px wide inside a 144px control
— **56px hanging over the neighbour**, and six art-on-art overlaps across the
row. At 414x896 it was 34px.

The button rectangles stayed perfectly clean throughout, which is why no
harness caught it: this is the third instance of one shape in this project,
after the shop's widget overlap (T168) and the bestiary's panel clipping
(T179). **The container being fine says nothing about what is inside it.**

The fix scales the shared height instead of capping a width —
`height: min(2.5rem, 6vw)`. It only ever takes the art *down*: the row needs
about 14.1 button-heights of width, so from roughly 670px up it gets the native
40px, and below that the whole row scales together. `flex-wrap` is kept as a
safety net rather than as the plan.

**Measured** at 360x640 through 3840x2160: no art outside its button, no art
overlapping another, no clipping, no document scroll in either axis, exactly
one tab current. From 768px up the bar is **identical to before this pass** —
200x40 and 41x40 on one line in a 58px dock — which is the point: the fix
touches only the widths that were broken.

#### The probe counted the stack as a collision

Worth recording because it produced a flat, plausible, wrong number.

The first art-overlap check compared every `.nav-button .chrome-art` node and
reported **15 overlaps at every viewport, including 3840x2160** where nothing
can possibly collide. 15 is C(3,2) x 5: each clickable button stacks three
faces — rest, hover, pressed — which are *supposed* to sit on top of each other,
because that is how `.chrome-stack` makes hover and press CSS instead of state.

A number identical at every input is the tell this project keeps relearning:
**when a check returns the same answer for every case, suspect the check.** The
corrected probe takes one face per button, and then reads 0 everywhere except
the two narrow viewports, where the real spill was.

### A40. The shop's backing disc is CSS, and the layout gets its cap back

Four polish items, two of which are worth more than polish.

#### The backing disc was a 30x30 shape drawn at up to 176px

Every tile draws a plain dark disc behind its glyph. It is a **single path of
radius 15 in a 30x30 export** — and this shop now runs tiles from 42px to
176px. At the top end that is a six-times upscale of an antialiased edge, which
reads as a ragged circle behind a crisp glyph, and it is worse on a high-DPI
display, not better, because the glyph gets sharper while the disc does not.

`.upgrade-icon__plate` draws it in CSS now. **The gradient stops are the SVG's
own, not a guess**: `596.svg` fills its path with a linear gradient whose
matrix rotates it bottom-to-top — `#000000` at offset 0.380, `#333333` at
0.694, `#666666` at 1.0, padded black below 0.380. Read from the bottom up that
is black for the lower 38% greying to `#666` at the top, which is why a *linear*
ramp on a circle reads as a lit sphere and why this is not a radial gradient.
The CSS inverts the offsets because `180deg` runs top-to-bottom.

**The rule for which layers to drop is positional and derived.** The plate is
layer 0 of a drawn frame — not a list of ids. Collected across every rest frame
of every clip that yields four shapes today: `596` on 54 frames, `601` on 24
(the equipped red disc, already dropped by `A32`), and one each for
`EnemyAbsorb` and GummyBear, **whose plates are their own shapes**. A
hand-written `[596, 601]` would have left a pixelated disc on exactly those two
tiles and nowhere else, which is the kind of gap nobody finds by looking.

What the rule assumes is that layer 0 is never *content*, and that is driven
rather than asserted: `tileHighlight.test.ts` reads the exported SVGs and
requires every shape in the set to be a single-path 30x30 disc. A glyph is four
paths of real colours and fails it immediately. `tileGlyphLayers` also refuses
to return an empty list — if a regenerated clip ever put its glyph at layer 0,
the tile falls back to drawing the original art, so the failure is a visible
duplicate disc rather than a blank tile.

#### The cap, argued three ways

`max-width` on `.shop` has now been added, removed and added again, so the
reasoning is recorded rather than the conclusion:

- **T167 added `1800px`** to close a void between two columns pinned to
  opposite edges.
- **T169 removed it.** The cap was itself the next complaint — black pillars
  down both sides of a 2K display — and three columns spread with
  `space-between` uses the width rather than refusing it.
- **T182 adds `1900px`.** Spreading three columns does not close the void on a
  really wide screen, it *relocates* it: at 2560x1440 the columns come to about
  1900px of content in 2531px of room, so `space-between` pours 630px into the
  two interior gaps and the catalogue and the window end up at opposite edges
  again.

**1900 is the measured natural width of the three columns at full size**, which
is what makes it defensible rather than a taste value: below it nothing changes
at all, and above it the slack moves from between the columns to outside them.
The 1200–1400 that was suggested would also have shrunk the catalogue — the
grid track loses about 500px, taking tiles from 155px to roughly 95 — which
solves the spacing by making the thing being spaced smaller.

Measured before and after at 2560x1440: side margins 16px -> 330px, **tile size
unchanged at 155px**. At 3840x2160 the tile goes 176px -> 163px, which is the
whole cost.

The pillars are back on 4K, and that is the trade that was asked for. Both ends
of it are in the stylesheet comment so the next pass round this loop does not
re-derive one half of it.

#### Two smaller things

**The money top-up is gone** — the button, `UpgradesScene.grantMoney` and the
`ui:dev-grant-money` event, three `DEV-AID` tags in three files. The inventory
in `devAids.test.ts` drops 36 -> 33. Removed at request rather than because it
was broken: a dev affordance behind `import.meta.env.DEV` still appears in
every development session, which is where it was unwanted.

**EQUIP / SLOT 1 / SLOT 2 are on `.gloss-pill`.** They were a flat 7%-white
rectangle, which read as a form control on a screen of glass and metal. The
equipped state is **red, because the tile says equipped in red** —
`.shop-tile--equipped` is the AS3's own red ring in CSS (`A32`), and a green or
gold button here would give one state two colours on one screen. It overrides
the pill through two classes (`.gloss-pill.shop-row__slot--on`), because both
are (0,1,0) and this project has shipped five bugs settled by source order.

### A39. The shop has no hover panel at all, and its blurb moved into the window

**This reverses half of `A38`, one task later, and the reason is specific
enough to be worth keeping.**

`A38` moved the shop's 28 tiles from `PartInfoText`'s fixed corner to the
pointer-following card, on the argument that a corner panel is unreadable
across a grid. That argument was right about the corner and wrong about the
remedy: a card that follows the pointer **covers the grid**, and the shop's
grid is the densest in the game — 28 tiles in three labelled groups, swept
precisely to compare one weapon against another. The card sat on top of the
comparison it was meant to help.

So the rule is sharper than "corner panels lose to grids":

- **A corner panel fails on a grid** because it is nowhere near the thing under
  the pointer. That is `A36` and it still stands for the achievements board.
- **A cursor card fails on a *dense* grid** because it occludes the neighbours,
  which on a comparison grid are the whole point. Level select (45 tiles laid
  out as a map you read one cell of), the bestiary (20 tiles) and the
  achievements board (36 badges you inspect one at a time) all keep theirs; the
  shop does not.

The distinction is **what the grid is for**, not how many cells it has.

**The strings had to go somewhere.** `UPGRADE_DESCRIPTIONS` is 28 generated,
tested strings whose only consumer was that panel; removing the panel without
rehousing them would have left them rendering nowhere — the "ported but not
wired" state this document tracks separately, arrived at by deletion. They are
now `.shop-detail__blurb` in the detail window, which is where a description
belongs once a window addresses a selection. `infoTextSites.ts` keeps the row
`no-consumer` and says *as a tooltip*, not *unported*.

#### The white ring was never "as in the original"

The selected tile's CSS carried the comment *"a bright white ring, as in the
original"*. That justification is false, and it is the reason the colour looked
settled when it was not.

The AS3 does have selected frames — `ButtonWeapon.as:145-161` picks frame 3, 6
or 9 by owned/equipped state. **This port has never drawn them.**
`UPGRADE_TILE_REST_FRAME` is `{ owned: 1, equipped: 4, notOwnedWeapon: 7 }` —
the *resting* frames — so hover and selection on this screen have always been
entirely CSS, and the white ring was a port invention wearing a fidelity
justification.

Changing it therefore costs no fidelity at all. It is now the bestiary's blue
ring and bloom, declaration for declaration, which is what was asked for by
name. The four-selector group is kept so the selection still out-specifies
`--affordable`, `--locked` and `--equipped` rather than depending on source
order.

`glassSurfaces.test.ts` now compares the two screens' `:hover`, `:active` and
`--on` blocks as strings, so "exactly the same" is a mechanism rather than an
intention. The world card is deliberately outside that comparison — it is a
wide card with a terrain strip and no selected state, so it shares the surface
and not the states, and the test says so where someone would otherwise "fix"
its absence.

### A38. The shop's tiles raise the cursor card, and the last hover-jump is gone

A backport, not a new design: five screens were built after the shop and the
patterns improved along the way. What actually changed is smaller than the
brief implied, and the difference is worth recording.

**Two of the five asks were already true.** The catalogue has selected on
`onClick` with `aria-pressed` since T166 — the detail window has never followed
the pointer — and the tiles have carried `aspect-ratio: 1` with
`max-width: var(--tile)` since T168, measured square. What made the shop *look*
like it updated on hover is the third ask: it was the last grid still opening a
`PartInfoText` panel, and that panel is pinned to a **fixed corner**.

**So the divergence is the corner, and it is the same one `A36` records.**
`ButtonUpgradeInfo.as:163` asks for `showLeft: false, showTop: true`, which
this port transcribed correctly and has now stopped using: across 28 tiles the
panel is nowhere near the tile under the pointer. The 28 strings still render —
`UPGRADE_DESCRIPTIONS` is generated from that same AS3 source — laid out in the
card rather than styled as character ranges in a corner panel.
`infoTextSites.ts` moves the row to `no-consumer` with the reason, which takes
the table to 7 wired and 9 no-consumer. **Two of those nine left `wired` for a
view decision rather than for unbuilt work**, and the module docstring now says
so, because a falling count that means "polished" reads exactly like one that
means "regressed".

#### The hover jump, and the three drifted copies

The tile lifted 1px on hover — `transform: translateY(-1px)` — and it was the
last one in the game. Beyond the twitch a dense grid gets from it, this one
also nudged `.shop-tile__level` a pixel off the art it labels, since the badge
is positioned against the tile.

Removing it found the more interesting problem. `.shop-tile`,
`.bestiary-tile` and `.world-grid__cell` are **the same object written three
times**, one screen at a time across five tasks, and they had drifted: the
steel ramp was 26/20/42 on the shop, 24/20/42 on the bestiary and 26/22/42 on
the world card. No screen shows two of them at once, so nothing could reveal
it, and the shop's surface was additionally still on the first iteration — a
flat white-to-black gradient with one inset line — which reads as a darker,
flatter object beside the two built after it.

All three are now the bestiary's values, and `glassSurfaces.test.ts` drives
them against each other: same ramp, same top rim, no `transform` in any hover
rule, and no `transform` left in any transition. **The last one matters most** —
leaving `transform` in the transition list is how the property comes back,
because a later edit adds it to a hover rule and it eases in, looking
deliberate.

`.gloss-pill` is what this should eventually be: one class carrying the surface
and nothing else. That refactor touches three screens already signed off, so it
is not done here — but the *mechanism* is, because "keep these in step" in a
comment is a hope, and this document has a section on the difference.

**Measured** at 1024x480 through 3840x2160: 28 tiles, **worst-of-28 ratio
exactly 1.000** at every viewport, no scroll, no overlap between tiles and the
aside widgets, and — with the check T179 added — no panel clipping its own
contents. The ratio is the worst tile rather than the first, because
`aspect-ratio` losing to content is a per-tile failure and reading tile zero
would miss it.

### A37. The bestiary is a roster and a window, and all twenty enemies show

`ScreenEnemies` is a grid on the left and `bgWindow` on the right, with one
enemy selected into it. This port had a **vertical list**, one row per enemy
with that enemy's stats, description and badges inline — a different screen
wearing the same title. T179 rebuilt it to the original's arrangement: tiles
five to a row (`addEnemyButtons`, `:277-303`), a window carrying the name, the
description, the two selector rows and the four stat lines (`:544-611`), and a
selection connecting them.

**Click selects, hover does not** — `A8`, applied here for the same reason it
was applied to level select: a window that changes as the pointer crosses the
grid cannot be read, because reading it means moving the pointer off the thing
you are pointing at. Hover raises the shared `CursorTip` card instead.

#### All twenty show, and this is *not* a divergence

Worth stating precisely, because it looks like one.

The original's grid is 5x3 with a `More Enemies` button under it. Both come
from the same condition: `addEnemyButtons` sets `hideAmount = 5` when
`!Main.extraStuff` (`:283-286`), and `:254` adds `ButtonMoreEnemies` under the
same `if`. `Main.extraStuff` is set by an **Armor Games or Kongregate purchase
check** (`Main.as:380`, `:414`) — so the 5x3 grid and the upsell are the state
of a build that has not been paid for.

This port shows 5x4 and no button, which is the `extraStuff = true` branch of
the same source. Both storefronts are on the "will never be ported" list, so
there is no third state to be in. Adding the button would mean adding a control
with nowhere to go, which is the call `A35` already made for `More Worlds`.

#### A locked tile now draws no art at all

The AS3's frame 4 is plate + overlay + a `?` glyph. The tile draws its own
plate and overlay in CSS now, so drawing the frame as well would be a picture
of a tile inside a tile; the mark is set in type instead.

The side effect is the useful part: **an unmet enemy contributes no shape id to
the document.** This screen's whole reason for existing as a separate component
is that it must not be able to answer "what is enemy X" for an X the player has
not met, and it is now one step further from being able to — there is no art in
the DOM to inspect, rather than the right art. `BestiaryScreen.test.tsx`
asserts that directly, with a known tile beside it as the counterpart.

#### The selectors moved from `.chrome-tab` to `.difficulty__button`

T159 put them on `.chrome-tab` rather than a near-copy of it. T179 moves them to
the pill the rest of this UI uses for "exactly one of these is chosen". **What
was being pinned is unchanged** — a shared primitive rather than a fork, and
`aria-pressed` rather than `aria-current`, because these filter a table and do
not navigate. Only the identity of the primitive moved, and the tier row is the
same pill in a four-column container rather than a second set of rules.

#### The window was sized by width alone

Recorded because the failure mode is silent and the rule that produced it looks
right.

`--pane` was `clamp(14rem, 30cqw, 30rem)`. Everything inside the window is a
multiple of it, so the window's *content* runs about 1.28 times `--pane` tall —
and at 1024x480 that is a 303px pane needing 389px inside a 315px box. The
panel is `overflow: hidden`, so it **clipped in silence**: no scrollbar, no
overflow on the body, nothing the fit harness's `scrollHeight` check could see.

Measured: 74px over at 1024x480, 69px at 1280x600, and **zero from 1366x768
up**, which is exactly why a width-only clamp looked correct — every viewport
anyone would develop on was fine. The fix caps it by the height too
(`min(clamp(...), 70cqh)`), which does not bind at all above 1366x768.

The general form, and it is the third time this shape has appeared: **a
container's own overflow is not the body's overflow.** T168 was a widget drawn
over the tiles while `scrollWidth` and `scrollHeight` were both clean; this is
a panel clipping its contents while the same two are clean. A fit harness has
to ask each box whether it holds its own content, not only whether the page
scrolls.

**Measured** at 1024x480 through 3840x2160: 20 tiles, ratio exactly 1.000, a
5x4 grid every time, no tile outside the plate, no tile intersecting another or
the window, `scrollHeight === clientHeight`, and no clipping inside the window.

#### T178b — the badge gets its picture, its card and its size

Three follow-ups, and two are divergences.

**The badge draws the clip's own art.** `Achievement<id>` is a 52-unit backing

can see how big a layer is and not where it sits. Centring is right for the
disc and the ring by construction — they are concentric — and matches every
icon checked by eye. An off-centre icon in the original would render centred
here and **nothing would flag it**; recovering the offsets means extending
`gen-sprite-shapes.mjs` to keep the translation half of the matrix.

**Divergence 2 — the hover readout is a cursor tooltip, not `PartInfoText`.**

#### The grid was never irregular

Recorded because the wrong version was believed for three months and reached
four files.

`achievementListing.test.ts` carried `it('has an irregular grid, …')`, which
said `MaxedPrimary1` sat 16 units off the row step. Measured, all 36
placements are a **regular 6x6 lattice**: x 55..355 step 60, y 120..400 step
56, every point filled, none doubled. `MaxedPrimary1` is at (55, 176), exactly
on it.

The original defect was real — the first screen derived a row by dividing y by
40, two entries rounded into one cell and one vanished — but the cause was the
**assumed step**, not the data. The test asserted `(y - 120) % 40 !== 0` for
some entry, which is true of a *regular* 56-step lattice, so it passed
comfortably while describing something that does not exist. From there the
claim reached `AchievementsScreen.tsx`, the stylesheet and this document.

The tell, and it is the one this project keeps rediscovering: **the assertion's
expected value came from the code it was testing** — the wrong constant 40 —
rather than from the data. What replaces it pins the lattice itself, with the
40-step failure kept beside it as the counterpart that explains why the
placement is read directly instead of bucketed.

#### The percentage that resolved against the wrong box

Worth its own note, because the first diagnosis was wrong and the way it was
wrong is reusable.

`.achievements__cell` carried `padding: 6%`, written as "6% of the disc".
**Percentage padding resolves against the containing block's inline size**, not
the element's own — so at 1920x1080 it was 6% of the 1425px grid, 85.5px a
side. That is 171px of padding inside a 105px disc: the content box floors at
zero and the border box grows to fit the padding. The badge measured 173px, six
rows of them overlapped vertically, and the last row hung 45px off the plate.

The first fix blamed a container-unit cycle — `--disc` is `min(13cqh, 13cqw)`
and the cell was its own `container-type: inline-size` — removed it, rebuilt,
and **every measured number came back byte-identical**. That is the useful
part: *a fix that moves no number did not touch the cause.* The second pass
asked the browser instead of the stylesheet, and `left` answered it —
`calc(var(--disc) / 2 + ...)` computed to 52.4px, exactly half of a perfectly
valid 104.83px `--disc`.

So: **when a length is wrong, check what its percentages resolve against before
theorising about how it was computed.** Every length on the cell is now a share
of `--disc`, and `AchievementsScreen.test.tsx` holds that shape — with
`border-radius: 50%` asserted alongside, so the rule reads as "no percentage
that resolves against the parent" rather than "no `%` at all".

### D-TIP. The cursor tooltip's three flicker causes, and the corner flash

Level select's hover readout follows the pointer. Four defects went into
getting that right, and none of them is visible in the CSS.

**Three separate causes of violent twitching**, of which the obvious one was
the least important:

1. **It was in flow.** Before it had any CSS it was an ordinary `<div>` inside
   `.levels` — a two-column grid gaining and losing an item on every hover,
   which is a full reflow of both columns each time the pointer crosses a tile.
2. **`pointer-events: none`.** The card is drawn a few pixels from the cursor,
   so without it the pointer lands on the tooltip rather than the tile: the
   tile's `mouseleave` fires, the card unmounts, the pointer is over the tile
   again, `mouseenter` fires — a loop as fast as the browser can dispatch.
3. **The portal.** `.screen-shell__body` sets `container-type: size`, which
   implies `contain: layout` — and a layout-contained element becomes the
   containing block for its *fixed* descendants as well as clipping them. A
   `position: fixed` tooltip rendered in place would be positioned against that
   box and cropped near every screen edge.

**And a one-frame flash in the top-left corner.** `useEffect` runs *after* the
browser paints, so the card was painted once with no `transform` before the
effect moved it. `useLayoutEffect` runs before that paint. The second half —
`visibility: hidden` until a `--placed` class is added — covers what a layout
effect cannot: a hover raised with no pointer position ever recorded, which is
what a touch tap or a programmatic focus produces.

`visibility` and not `display`, because the component measures its own box to
choose which side of the cursor to sit on, and a `display: none` box has no
dimensions to measure.

**Driven, not asserted.** A rAF recorder sampled the tooltip's `visibility` and
`transform` on every frame across a hover: 76 frames, **zero** visible at the
origin, and the first visible frame already carrying a real `translate3d`. A
one-frame flash is invisible to a screenshot and to any check that samples
"afterwards", by which time it has already moved.

### D-FPS. `backdrop-filter` over a live canvas cost 52 fps

Level select ran at **8 fps** on a 2560x1440 display. Found by isolation rather
than by reading: sample `requestAnimationFrame` deltas on the real screen, then
disable one suspect at a time and re-sample.

```
baseline (as shipped)            8 fps median    7 worst
no backdrop-filter anywhere     60 fps median   30 worst
no tile box-shadow               7 fps median    7 worst
no tile gradients                7 fps median    6 worst
no panel shadows                 8 fps median    7 worst
no tile at all                   8 fps median    7 worst
no canvas                       60 fps median   60 worst
```

**The tiles were innocent** — hiding all 45 changed nothing, and so did
stripping their shadows and gradients. The cost was `backdrop-filter` on the
panels: Phaser repaints its backdrop every frame, so the browser re-blurred the
whole viewport 60 times a second. The two 60-fps rows are the same finding from
both ends.

**And the blur was buying nothing.** `.screen-shell` paints `--bg`, which is
`#000` and opaque, so the blurred backdrop is a flat colour — blurring a flat
colour returns the same flat colour. Removed from all six in-game panels.
`.menu-card` keeps its blur: there is a real picture behind that one, and the
main menu was measured separately at 60 fps.

**The general rule, worth carrying:** `backdrop-filter` over anything that
repaints is a per-frame full-area cost, and over an opaque backdrop it is a
per-frame cost for no pixels at all. Neither is visible in the CSS.

A second cost went with it: `previewForLevel` was being computed for **all 45
tiles on every render**, because each cell built its own tooltip request. Only
the hovered tile needs one now.

  between a 76px grid and the window. The slack belongs outside the pair.

(`:570-579`): a labelled socket holding the equipped weapon's own art, with
`bWeaponSwitch` between them drawn as a red diamond. **The diamond is
decorative** — the original's button swaps the two slots and nothing in
`ShopCatalogue` carries a swap. The weapon's name is kept `.visually-hidden`,
since the original shows only the picture and a screen reader would otherwise
get two wells called "Slot 1" and "Slot 2" with no way to tell them apart.

**T168 fixed an overlap the fit runs could not see, and that is the lesson
worth keeping.** The slot widget was drawing on top of the weapon tiles while
every number in the harness was green — because a grid overflowing its own
*grid column* does not overflow the body. The layout is centred at a max-width
inside a much wider body, so `scrollWidth` had 380px of margin to absorb it and
reported nothing. **Container overflow and sibling overlap are different
questions, and the harness was only asking the first.** It now also tests
rectangle intersection between every tile and the aside widgets.

The cause was two columns sized against each other: the grids took their
content width and the aside took the remainder, so a grid wider than its share
simply drew over its neighbour. Both halves of the fix are needed — an explicit
`--aside` track the grid cannot eat, and `repeat(6, minmax(0, var(--tile)))` so
the tracks give way instead of overflowing. Anything computed from `--tile`
then overstates the box it lands in, so the tile is an inline-size container
and its badge and icon are shares of the real width.

The first fit run found the other real defect. The overflow was **exactly 60px
at every viewport size** — a number that does not move while the tiles scale by 2x is
not coming from the tiles. It was the DEV grant button, a sibling of `.shop`,
which claimed `height: 100%` of a body it did not solely occupy. The body is a
`grid-template-rows: minmax(0, 1fr) auto` now.

### A19. A marker's appear threshold is the collision radius, not the art's half-width

`PartGameArea.as:4761` decides `outsideWindow` with `theEnemy.width / 2` — the
*display object's* half-width, the clip's rendered bounding box. This port feeds
`outsideWindow` the enemy's `radius`, which is its **collision** radius.

In the AS3 the two are near enough the same thing, since an enemy is a circle
drawn at its own size. Here they are separate quantities and have been since
T34, which changed every collision radius by up to 2.85x and left the art sized
independently — the same split T85 made explicit for projectiles, where the
drawn size stopped being derived from `bulletRadius`.

**The consequence is bounded and one-sided**: a marker appears or clears a few
world units early or late, per enemy type, at the exact moment the enemy's box
crosses the camera edge. It cannot make a marker point the wrong way, appear for
an on-screen enemy, or persist for a dead one — the flags are recomputed from
live positions every frame.

Left as the collision radius deliberately. It is the quantity the rest of this
port means by "how big is this enemy", it is the one already threaded through
`Subject`, and reaching for the art size would mean the marker rule consulted a
different notion of size from every other rule around it — a second definition
being the thing T34 was cleaning up.

### A17. The minimap anchors to the live camera view, not to `(560, 400)`

of a **640x480 stage whose bottom 80px sat below the 640x400 camera**, a
dedicated HUD band. This port has no band: the camera fills the screen and the

bottom-right instead, re-placed every frame by `drawMinimap`.

**Three knock-on effects, all accepted:**

  or home bar.
- **A clearance for the DOM HUD's bottom row**, stated in CSS pixels (96) and
  converted at the draw. The AS3 needs no equivalent — its HUD was *below* the

- **The viewport rectangle is computed from the live camera**, not the AS3's

at 552 lands at `(552 - 640) * 2 + 640 = 464`. World-unit anchoring needs no

### A12. Enemies turn twice as fast as the original

**A tuning decision by the user, 13 August 2026 — and the scoping pass found no
bug.** Recorded because it looks exactly like one being fixed.

**What the AS3 does.** Four steps per frame: turn toward the goal capped at
`rotSpeedMax` (`:4696-4714`), accelerate along the **new** facing by `accSpeed`
(`:5056`), clamp the speed (`:5098`), integrate (`:5374`). **There is no
friction on a live enemy anywhere in the loop** — the only velocity reduction,
`:5106-5112`, applies to *frozen* enemies. Momentum is shed solely by the speed
clamp, which scales both components and so preserves direction.

**What the port did.** Exactly that, with correct frame scaling, and stat rows
matching the source: `enemyBasicStats` is `[5, 10, 50, 1.5, 0.2, 1, ...]` and
the port's Basic row reads `moveSpeedMax 1.5, accSpeed 0.2, rotSpeedMax 1`.
Nothing was broken.

**Why it played badly anyway.** `rotSpeedMax = 1` is one degree per *frame* —
30 degrees a second. Measured on the shipped module, a Basic enemy at full speed
with the tank 300 units behind it took **176 frames (5.9s)** to come about.
Against a moving player that is never: the enemy sails past and cannot correct,
which reads as ice-skating and makes them trivial to dodge.

**What this port does.** `ENEMY_TURN_MULTIPLIER = 2`, applied in
`resolveEnemyStats` on top of the difficulty's own rotation ladder:

| | AS3 | port | reversal before | after |
|---|---|---|---|---|
| Basic | 1 deg/f | 2 deg/f | 176f (5.9s) | **88f (2.9s)** |
| Fast | 2 deg/f | 4 deg/f | 88f (2.9s) | **44f (1.5s)** |

**Why the turn rate and not friction.** Acceleration is not the limiter — at
`accSpeed 0.2` toward `moveSpeedMax 1.5` an enemy reaches top speed in 7.5
frames, about 23x faster than it can turn. Adding damping would invent a force
the original does not have and make enemies sluggish rather than accurate.

**Why x2.** The conservative option of three measured; x3 (2.0s) and x6 (1.0s)
were rejected as too far from the original's feel. Global rather than per-type,
so every class keeps its relative agility and Flag and Defense still get enemies
that commit to a path.

**What is kept.** The stat table is untouched — it is generated from the AS3 and
checked by `data:check`, and `enemyStats.test.ts` pins the rows at the source
values so a future pass cannot "fix" this by editing the data. Reverting is one
constant: `ENEMY_TURN_MULTIPLIER = 1`.

**What is lost.** Enemies converge more tightly than the original's, so crowds
form closer to the tank. Three AS3 behaviours that make the original *worse* at
tracking remain unported and would each partly undo this if added later:
`slowDown` (`:4613-4640`, periodically halves `rotSpeedMax`), `speedSubtracting`
(cuts the speed cap), and the `angleOffset` swerve (`:5223-5265`, steers up to
75 degrees away from neighbours). Whoever ports them should re-measure this
number rather than assume it still fits.

### A11. Per-level upgrade limits are not enforced, and no longer shown

**A game-design decision by the user, 13 August 2026** — not a porting gap, and
not deferred work. Balance will be handled by other means than hard caps.

**What the AS3 does.** Every level row carries a cap in `levelDataModel` column
7, range 1..10 (`ScreenGame.as:365` reads it into `selectedUpgradeLimit`). At
level start `:578-580` walks the player's upgrade levels and **strips the
excess** into `ScreenUpgrades.levelsArrayRemoved` — a temporary downgrade for
the duration of the level, restored afterwards, announced by an "Upgrade Limit"
notice in `WindowOk`. `ButtonLevelGuideInfo.as:77-106` prints the number in the
level guide's info panel, and `ButtonNextLevel.as:335` in the next-level
preview.

**What this port does.** Nothing enforces the cap — that was already true, and
it is now true **by decision** rather than by omission. The display is gone too:
`levelPreview.ts` no longer emits the `Upgrade Limit` row, so the panel prints
five lines where the AS3 prints six.

**Why the display went with the mechanic.** A number that constrains nothing is
worse than no number: it tells the player their upgrades will be clipped on this
level, and they will not be. The two halves are one decision.

**What is kept.** `LevelSpec.upgradeLimit` still carries the extracted value for
all 405 levels. Dropping a column whose meaning is known is the failure
`CLAUDE.md` records for `enemyModel[1]`, so the datum stays and
`levelPreview.test.ts` pins that it is still there, still 1..10, and still
unread by the panel.

**What is lost.** Levels the original made harder by clipping upgrades are
easier here, and the effect is largest late — a fully upgraded tank entering a
limit-1 level. This is the intended change, not a side effect.

**The "Info window" option went with it (T137).** `optionWindowULOn` is **not**
an upper-left info panel, which is what this port's comment and its options row
both claimed — **"UL" is Upgrade Limit**. It gates the warning window itself:
`ScreenLevelSelect.as:1001` scans the equipped loadout against the level's cap
when the flag is on, `:1024` raises the window, and `ButtonNextLevel.as:123` and
`:147` do the same from the results screen. The window's "don't show this
message again" checkbox writes this flag and nothing else.

With the cap gone the toggle governed a warning about a rule that no longer
exists, so the options row is removed rather than left inert. **The key is still
read and written**, so an existing player's stored value round-trips instead of
being dropped on their next save — reinstating the mechanic needs no data
migration, just the row back and `:578-580`.

**Reverting.** Restore the summary row in `levelPreview.ts`, the options row in
`OptionsScreen.tsx`, and implement the `:578-580` strip/restore against
`upgradeState`. The value is already extracted, so nothing needs re-deriving
from the SWF.

### A10. The muzzle flare sits at the equipped weapon's barrel tip; the AS3 uses a flat 10

**Decided by the user, and rewritten once.** The first version of this entry
recorded a different change and was wrong; what it got wrong is kept below,
because the mistake is more instructive than the fix.

**What the AS3 does.** `PartGameArea.as:3962` spawns the flare at
`tank.x + cos(angle) * 10`, `tank.y + sin(angle) * 10` — a flat 10 units from
the tank's centre, along the round's bearing, for every weapon.

**What this port does.** `muzzleFlareOffset(weapon)` returns that weapon's own
`barrelReach`, derived from the turret shape's authored bounds: **10.5** for
eleven of the twelve turrets, **11.3** for the Gummy Bear, **17.9** for the
Magic Cannon. Nothing else about the flare changes — it still spawns along the
round's bearing, still carries `startAngle: rotation`, still has `distance: 0`
and `randAngle: 0`, and the Shotgun's one-flare-per-volley rule at `:3964` is
untouched.

**How small this divergence actually is.** Half a unit, for almost every weapon.
`Tank.as:63` adds the turret at (0,0) so the shape's registration point is the
tank's centre, and the barrel tip is whatever the art extends past it — which is
10.5 nearly everywhere. **The AS3's flat 10 was very nearly the barrel tip
already**, which is presumably why it could be a constant at all. The value of
reading it per weapon is the two turrets that differ and any future weapon that
does.

**What was actually broken, and it was not this number.** Flash anchors a clip
at its **registration point**; Phaser anchors a sprite at its centre by default.
Shapes 1108/1114/1119 — the three flares' first frames — have their registration
at local x = 0, *the flare's flat base*. Drawn centred, half of every flare sat
behind the muzzle inside the tank. That is the "buried in the hull" the flare
was reported for, and it is fixed by `PARTICLE_ANCHORS`, not by moving the
spawn point. Position and anchor are separate quantities and only one of them
was ever wrong.

**The wrong first version, kept as the lesson.** T120 recorded A10 as moving the
flare to the *hull* edge — `TANK_SIZES.body / 2 + 1.5`, 16 units — reasoning
that a flare at 10 looks buried because the hull's radius is 14.5. The reasoning
was sound and the conclusion was wrong, because the measurement underneath it
was never taken: **every one of these barrels ends at 10.5**, so 16 floated the
flare 5.5 units clear of the gun. It fixed the symptom's *description* ("looks
like it comes from the middle") by breaking the thing the description was about.
The tell was available and ignored — the entry asserted the barrel "does not
protrude past the body" without ever asking where the barrel *does* end.

**Driven**, at two turret angles on two weapons with different barrels:

| Weapon | Turret | Flare offset | Distance | Flare rotation | Anchor x |
|---|---|---|---|---|---|
| Cannon | 0 deg | (10.5, 0) | **10.5** | 0 deg | 0 |
| Cannon | -121 deg | (-5.3, -9.0) | **10.4** | -121 deg | 0 |
| Gummy Bear Cannon | 0 deg | (11.3, 0.1) | **11.3** | 0 deg | 0 |
| Gummy Bear Cannon | -117 deg | (-5.2, -10.0) | **11.3** | -117 deg | 0 |

The two weapons disagree on distance by exactly the difference between their
barrels, which is what separates a per-weapon read from a constant that happens
to suit the Cannon.

**What is lost.** Half a unit of fidelity against the original on most weapons,
0.8 on the Gummy Bear. Nothing depends on the position — the flare is
decorative, spawns no collider and carries no damage. Reverting is one function
body: `return AS3_MUZZLE_FLARE_OFFSET`.

**A related non-divergence.** The turret is now drawn at its authored size with
its registration point as origin, replacing a fixed 21x21 square centred on the
texture. That is not a divergence but a **fidelity fix** — five of the twelve
turrets are not square and were being stretched, and the Magic Cannon was also
pivoting 4.7 units from its real hinge. It is recorded here only because it
arrived with this change; see "A registration point is not a centre".

### A9. A boss row in a roster preview draws boss art; the AS3 draws the ordinary enemy

**Decided as an improvement, and recorded because it looks exactly like a bug.**

**What the AS3 does.** `PartInfoText.as:249` strips the trailing level character
off the enemy name — `"BasicB"` becomes `"Basic"` — and `:271` then builds
`new (getDefinitionByName("Enemy" + enemyType))`. So the `AllEnemiesInLevel`
panel draws **`EnemyBasic`** for a boss row: the ordinary enemy's art, at the
ordinary enemy's size. `ImageEnemy.as:57-145` is a twenty-branch cascade with no
boss branch at all, so the level-select roster does the same.

**What this port does.** `levelPreview.ts` passes `isBoss` to `enemyShape`, so a
boss row resolves to `EnemyBasicBoss` — a different, larger clip. Every roster
surface inherits it: the next-level preview, the level guide's info tooltip, and
the level-grid hover.

**Why it is kept.** A roster's job is to say what is coming. A Boss level whose
boss row is drawn identically to its ordinary rows, distinguished only by the
word `BOSS` underneath, buries the one fact the preview exists to convey. The
port's rows are ~22px and render at a fixed size, so the boss clip costs nothing
in layout — only the artwork differs.

**Why this entry exists at all.** The divergence was introduced *by accident* in
T101 and found in T104's scoping, and the shape it presents is dangerous: a
reader who follows `:249` will see a level character being stripped, look at
`enemyShape(enemy.type, isBoss)`, and conclude the strip was forgotten. It was
not — it was found, checked against both AS3 sites, and kept deliberately.
`levelPreview.test.ts` carries the same warning at the assertion, because that
is where someone would stand while "fixing" it.

**What is lost:** nothing a player would notice, and one point of fidelity a
reviewer comparing screenshots would. Revisiting means changing one argument
(`enemyShape(enemy.type, false)`) and the pin beside it.

### A8 (original text). Level select starts a level on click; the AS3 selects one first

**Decided, not owed.** `LevelGuide`'s push into the level select
(`selectFromLevelGuide`, `ScreenLevelSelect.as:584-596`, and its latch
`canSelectFromLevelGuide` at `:73`, `:364`, `:592`, `ButtonLevel.as:93`,
`ButtonWorldSelect.as:70`) is **deliberately not reproduced**, and the reason is
that the mechanism it serves does not exist here by choice.

**What the AS3 does.** Its level select is four steps: pick a world, see the
grid, **select** a level — `selectedLevel` is persistent selection state, drawn
as a highlight — then press Play. `selectFromLevelGuide` pre-*highlights* the
guide's level once per visit, so a player who set the guide in the shop can go
straight to Play. The latch makes it once-per-visit and lets any manual click
take precedence.

**What this port does.** Three steps: world picker, grid, and a cell click that
emits `ui:start-game` immediately. There is no `selectedLevel` on
`LevelSelectScene`, no highlight, and no Play button on the grid.

**Why that is the decision and not the gap.** Click-to-start is the port's
interaction model, chosen and built. Porting `selectFromLevelGuide` would not
fill a hole in it — it would require **adding a selection step that contradicts
it**: a highlight state, a confirm control, and a second way to start a level
alongside the one that exists. That is a UX change to a settled screen wearing a
port's clothes, and it would make the screen worse to use in order to make an
unused pointer visible.

The latch is decided out with it. `canSelectFromLevelGuide` is a one-shot guard
*for* that function; with no pre-select it would be a mechanism with no rule
behind it — the shape `KNIP.md` and the source-shape tests are this project's
cautionary tales for.

**What is lost, stated.** Setting the guide in the shop and then opening level
select does not pre-point the grid at that level; the player clicks the level
they want, which is one action either way. The guide still does its actual job
— saying which level is next, and previewing its roster and upgrade limit while
you spend money.

**Two fragments would become portable if the interaction model ever changes**,
recorded so they are not re-derived: opening the grid on the guide's world
(`SaveManager.as:1463`) and writing a manual pick back into the guide when
auto-select is off (`ScreenLevelSelect.as:988`, `:1326`). Neither is worth
building alone today — the first is moot while the port opens on a picker, and
the second writes to something nothing then reads.

**The generalisable half** is in "A feature's coupling can be unportable because
the *other* screen diverged", above: scoping asked what `LevelGuide` reads and
writes and got right answers, but not whether the thing it writes *to* still
exists in the same shape here.

### A6. The medal reveal lags the display but not the unlock gates

**A deliberate split, and the reason is a defect the faithful version would
introduce in this port specifically.**

**What the AS3 does.** `worldsValuesVisibleArrays` is a session-only clone of
the earned table (`ScreenLevelSelect.as:37`, re-cloned at `SaveManager.as:656`
and `:1453`, never serialised). `ScreenStatus.as:356` snapshots it *before*
`:357-359` raises the earned slot, so the pair differs by exactly the result
just played, and `progressLevelButtons` (`:518-545`) animates that away at one
medal per **seven** frames (`:1378`, `:1371`).

**The original reads the visible table in its unlock rules too** — `:841` for
levels, `:1518` for worlds. So in the AS3 a level opens when its reveal
finishes.

**Why this port does not.** `GameplayScene.ts:980` handles `ui:start-game` with
**no unlock check at all**; only `LevelSelectScene` gates (`:136`, `:156`). The
results screen's Next-level button therefore starts whatever it is handed. Put
the gate on a lagging table and the two routes disagree: Next works, level
select refuses the same level, and only until someone watches an animation.
**Intermittent, save-dependent, and invisible to every existing test.**

**So the port splits them.** `levelUnlockStates` takes a separate `display`
view (defaulting to the gate view, so callers without a reveal are unchanged);
only `value` reads it. `cleared` and `unlocked` stay on the earned table.

**What this costs:** for the length of one reveal, a level shows fewer medals
than it has while already being playable. In the original it would also have
been unplayable for that second. Nobody can tell the difference without trying
to enter a level mid-animation, and the alternative is a progression bug.

**Pinned before it was built.** `levelUnlock.test.ts` carries three assertions
written in T75, one commit *ahead* of this change, including one that states
the two routes must agree. `progressReveal.test.ts` then pins the split
directly: the same earned table passed as gate and a lagging one as display
must differ **only** on the level just cleared.

**Driven** — `npm run look -- --unlock`: `0★ → 1★@243ms → 2★@473ms → 3★@710ms`
against an expected 233ms stride, one `Unlock` on the latch rather than one per
medal, and level 1-2 selectable throughout.

### A4. The tutorial panel's jitter re-rolls at 30 Hz, not per browser frame

`PartTutorial.as:457` picks a fresh angle every frame and offsets the panel by
`(1 - alpha) * 10`, but only while a tween runs (`:454`) — so it exists during
the one-second fade in and out, not on a settled panel.

**The amplitude was never wrong; the cadence was.** The AS3 ran at 30 fps and
this port updates at 60, so a per-frame re-roll produced twice as many angle
changes over the same fade and read as roughly twice as busy. Reported by the
user as "it shakes too much", and it is a **frame-rate correction rather than a
taste change**: `jitterOffset` now accumulates AS3 frames and re-rolls on whole
ones, so the offset range is unchanged and the rate matches the original.

Worth carrying: any per-frame random in a presentation layer inherits this. The
amplitude ports directly and the *rate* does not.

### A2. The results screen opens on the score, not the reveal — deliberate

**A divergence requested by the user, not a fix.** Recorded so nobody restores
the original ordering thinking it was a bug.

**What the AS3 does.** `ScreenStatus` builds one page stack —
`pagesArray = ["Standard", ...achievements, ...enemies]` (`:226`, `:408`,
`:427`) — and opens on the **last** page (`pageCurrent = pagesTotal`, `:431`).
The exits live on the Standard page only (`:939-960`), so a reveal cannot be
skipped, only walked back past. Its exits are **Play Again** and **Next Level**
(suppressed on the final level of the final world, or a medal-less defeat).
There is **no menu button and no level chooser** on that screen at all.

**What this port does now.** Opens on the results. The reveals are a pop-up
above the panel, dismissed with Continue, and a `Unlocked: …` line on the
results records what they said so the information survives dismissal — in the
original it could not be missed, because it was a page you walked through. A
**Level select** button is added beside Next Level and Replay.

**Why.** The original's order is coherent for a game where the reveal *is* the
reward. This port surfaces the score as primary feedback instead. It also
misread as a bug twice during development: a first clear shows "NEW ENEMY"
where a score is expected, and it cost two harness misdiagnoses.

**What did not change.** The reveal content, its order, and the page stack
itself are untouched — `buildStatusPages` is unchanged and still returns
results → achievements → enemies. Only where the reveal appears in the sequence
moved. `initialPageIndex` is kept as a named function rather than inlining `0`,
so the divergence has one place to be read and reverted, and
`statusPages.test.ts` asserts the new rule **against** the AS3's, so restoring
the original ordering fails loudly rather than silently.

**Found by looking.** The first attempt centred the pop-up, which covered the
title and the stats — defeating the entire reason for the change. The frame
said so; no test could have.

### B1. `:7083` does not fire — resolved by testimony, unconfirmed by measurement

`:7083` would destroy any ice patch the laser beam crosses. **The port no longer feeds
it a beam**, so the laser leaves ice trails alone.

**Status: resolved, and the manner matters.** The port was wired *reachable* on a static
reading of the source. It was unwired on the **player's direct recollection of playing
the original**, where lasers do not destroy ice patches.

That is real evidence, and better than anything derivable from this repository — nobody
can read Flash's playhead timing out of an extraction. **It is not a measurement.** A
future reader must not upgrade it to one: no log was taken, no frame was inspected, and
the experiment below has still never been run.

**The reading that put a beam there, recorded because it will be rediscovered.**

Against it: `handleGround` only ever sees beams spawned on an earlier frame (A1), and

the game and **moved no test whatsoever** — 2275 passing before and after. `sweepHazards`

**A1 is dormant while this stands.** It described the patch sweep and the freeze gate

## A pooled game object outlives the scene that built it (T149)

**The fifth member of the wiring family, and the first whose broken thing is a
field's *lifetime* rather than a value.** The rule was right, the arguments were
right, the call site was right, and it still could not work twice.

T148's enemy markers keep a pool — `this.enemyMarkers`, grown `while (length <
wanted.length)` and hidden rather than destroyed when the count drops, which is
what the AS3's `markerEnemyArray` does (`:495-515`). Three facts combine:

1. `GameplayScene` restarts itself — `:1175` for retry and Reset Level, `:1205`
   for Next level — and Phaser **reuses the scene instance**, so `create` runs
   again on the same object and a field initialiser does not.
2. `DisplayList.shutdown` calls `destroy(true)` on every object it holds, so the
   restart destroys the pooled images.
3. `GameObject.destroy` ends with `this.scene = undefined`, and `setTexture`
   reads `this.scene.sys.textures`.

So the second run found a pool long enough, created nothing, and threw on the
first frame with an off-screen enemy. **Every level after the first**, on a
subsystem whose 29 tests were green and stayed green.

**What made it invisible is worth more than the fix.** No test in this project
can construct the situation: `src/test/sceneHarness.ts` records that a real
scene will not boot under jsdom, `npm run smoke` stops at the menu, and a unit
test over `offScreenMarkers.ts` is testing the one part that was never wrong.
The suite's blind spot here is not a missing assertion — it is a lifetime that
no instrument in the repo can observe.

**The fix is positional, and deliberately so.** The reset went into `create`
beside `flagMarkerSprite`, not into the `init` reset block seven hundred lines
up that clears `flagMarker`, `bombMarkers`, `particleSprites` and
`coinSprites`. That block is a convention — a list somebody has to remember to
extend — and the evidence that it fails is that `enemyMarkers` was the one field
of seven missing from it. Beside the sprite, the next marker added inherits a
per-run rebuild by construction. `this.minimap` never had this bug for exactly
that reason.

**The generalisation, for anything added to a scene from now on:** a field
holding a game object is safe if `create` reassigns it and unsafe otherwise, and
"unsafe" means a crash on the second run, not a leak. Lazily-populated
collections are the risk; a sprite built in `create` is not.

## A setting can be complete in every respect except mattering (T140)

**Reported as "crosshair OFF by default doesn't work".** Two hypotheses came
with the report, and the answer was neither: **the option had no reader.**

`GameplayScene` drew the reticle with `setVisible(true)` — a literal where the
preference belonged — and `readGameplayOptions(...).crosshair` appeared nowhere
in `src/`. Everything *around* the option was correct and tested: the AS3 key
name, the first-run default, the read path that distinguishes a stored `false`
from an absent key, the options-screen row, the write-and-republish service, and
seven tests over all of it, added the day before in T135.

**Why the two obvious hypotheses were both wrong, and worth recording:**

- *"A stale profile stores `true` and overrides the new default."* Plausible,
  and a real effect — the store is only initiated when a player toggles
  something, and `writeGameplayOptions` writes all six keys at once, so anyone
  who ever touched the options screen before T135 has `optionCrosshairOn: true`
  stored, and it correctly wins. But it cannot explain this symptom, because no
  value of the key changed anything.
- *"The render path misreads the boolean."* There was no read to misread.

**The general shape.** A preference has two halves — storage and effect — and
this project's tests were entirely on the first. `autoPause` sat in the same
state until T127 gave it the pause latch. `windowUL` sits in it now, on purpose
(`A11`). The tell is a setting whose whole test file talks about reading and
writing.

**The mechanism, since a sentence here would just be another unenforced
guarantee.** `optionConsumers.test.ts` sweeps `src/` for a property read of each
option on one of the two channels that carry them —
`readGameplayOptions(...).<key>` and the store mirror `gameplayOptions.<key>` —
and requires every declared key to have one, with `windowUL` exempted *and its
exemption asserted*, so gaining a reader fails the test rather than passing it
quietly. It proves a spelling, is labelled as proving a spelling, and is driven:
over the pre-fix source it reports **0** readers for `crosshair` and 1 after.

Its own first run is the reason the file also carries an instrument check — the
argument regex was `[^)]*`, which stops at the inner bracket of
`readGameplayOptions(getOptionsStore(this))`, so the sweep found nothing and
reported *every* option unread. A clean, decisive, wrong answer, in the file
written to catch clean decisive wrong answers.

**Also ported while here** — `PartInterface.as:428` reverts to
`MouseCursor.AUTO` on pause and `:799-802` restores the custom cursor on unpause
*if the option is on*. The port pauses the scene, so without this the sprite
froze in place over the pause panel.

## A survey pass got three things wrong, and the corrections matter more than it did

A call-graph survey reported that **enemies never shoot**, that **defeat is therefore
unreachable**, and that **nothing is saved**. The player, who runs this build, says all
three are wrong. They are, and the way each went wrong is the reusable part.

**"Enemies never shoot" — a truncated grep read as a whole result.** The search was
`grep -rn "enemyBullet\|EnemyBullet" src/game/ | head -4`, and the first four hits were
all `difficultyMultipliers.ts` because `config/` sorts before `scenes/`. Enemy firing is
fully ported and wired: `enemies/enemyFiring.ts` with its own tests,
`advanceEnemyBullets` called at `GameplayScene.ts:2770`, bullets classed
`EnemyBulletBasic` / `EnemyBulletTrap`. **`head` is not a filter, it is a truncation**,
and reading one as the other produced a confident absence claim about a subsystem with
its own test file.

**"Defeat is unreachable" — deduced from the above, and contradicted by this document.**
The *Doc contradictions* section already recorded that `GameplayScene.ts:548-551`'s
"losing is arithmetically impossible until shooting enemies are ported" is a **stale
comment**, and that `:1315` applies enemy bullet damage to the tank. The survey
contradicted a correct record that was already written down, in the same file it was
writing to. The same pass also observed contact damage dropping the tank to 65/100, which
makes defeat reachable regardless of bullets.

**"Nothing is saved" — settled: it saves. The claim was wrong, and so was a second one
drawn from the same read.**

Driven end to end: win a level, **wait past the hand-over delay**, reload.
`CircularTankSave1` is written, survives the reload, and the menu comes back reading
**"Continue — Level 2"**. Both claims below were produced by one premature dump —
storage read at the instant the last enemy died, while `outcome.finished` was still
counting down the post-win timer that gates `bankLevelOutcome`. Two seconds later the
write is there.

- ~~Nothing is saved.~~ It saves.
- ~~There is no route from a win to the next level.~~ There is: the menu's **Continue**
  button, which that check never got far enough to see.

**The third purely-timing failure of seven.** A sub-frame tap, a screenshot taken after
a radial burst had left the frame, and now a storage read taken before the thing that
writes it had run. All three shared a shape: *a fixed delay chosen without reference to
what the game was actually waiting on.* `npm run look` now captures a burst rather than a
single frame, and its `--save` mode reports storage at three points rather than one.

The original diagnosis is kept below, because the reasoning it used was sound and the
conclusion still wrong — which is the useful part.

**"Nothing is saved" — an instrument reporting a clean negative, for the fifth time.**
`localStorage` read empty after a win. The mechanism is right — `SaveStore` writes
`saveString` to `window.localStorage`, and `levelBanking.ts:167` calls `profile.save()`.
The most likely artefact is that the level was never properly exited: the only route out
is a `Menu` button that **`diagnostics` overlaps**, and the harness needed `force: true`
to click it, so the click may have landed on the wrong control. Not diagnosed further,
because the player reports saving works and that outranks the instrument.

**`enemyBulletSpeed` has a consumer.** The survey called it "a tuned stat for a system
that does not exist", drawing a parallel to `LevelSpec.seed` before D1. That parallel
dissolves entirely — enemy firing exists, so the stat is read.

**The pattern, now at five instances.** A CRLF-poisoned file list, a drifted string
replace, a sub-frame key tap, an unowned weapon, and now a truncated grep. Every one
produced a clean, decisive, wrong result from a tool that reported success. **A survey
built from searches is evidence about the searches.** Where a claim matters, drive it and
watch it, or read the code path end to end — and check whether this document already
answers it before asserting the opposite.

## How to read a DefineSprite's frames — method, not incident

**A frame is the accumulated display list, not the shapes placed on that frame.** Flash
keeps objects across frames: a `PlaceObject2` without `HasCharacter` is a *move* of
whatever already sits at that depth, and a frame that replaces one of two layers changes
only that layer. The first parser used for `propArt` and `particleArt` recorded "shapes
placed on this frame", which is a different thing and is wrong.

**It was latent in two subsystems before anything showed it.** Props and particles each
replace a single shape per frame, so "placed" and "displayed" happen to coincide there,
and both tables are correct. `ItemMoney` is the first clip whose frames layer a shared
body under a changing numeral, and the wrong model produced a coin ladder with a
4.2-unit Money5 against a 7-unit Money1.

**The tell was monotonicity.** A derived table that is not ordered the way the source
obviously intends is a *parser* question before it is a *data* question. Coin values
ascend, so their discs cannot shrink; enemy tiers ascend, so bosses cannot be smaller
than their base form. Whenever an extracted table has an obvious intended order, assert
it — `money.test.ts` and `enemyArt.test.ts` both do, and in the coin case that assertion
is the one that would have caught the parser rather than the data.

**The correct method**, for any future extraction:

1. Track `depth -> characterId`. Apply `PlaceObject2`/`PlaceObject3` (set when
   `HasCharacter`, otherwise leave the depth alone) and `RemoveObject`/`RemoveObject2`.
2. Snapshot the whole depth map at each `ShowFrame`.
3. Flatten nested sprites to `DefineShape` ids afterwards, not during.

`propArt` and `particleArt` were re-checked against the corrected parser and are
unaffected. **One latent finding survives**: `TankBody` frame 2 is `[4, 3]`, not `[4]` —
Tower mode adds a shape *over* the frame-1 body rather than replacing it. Nothing reads
it today because the port has no Tower-mode body switch; the warning is written at
`entities/tankArt.ts` beside `TANK_BODY_FRAMES`, which is where whoever wires one will
be standing.

## A valid value in the wrong place is invisible to every check but a frame

T99 wired the hover panel (`PartInfoText.as`) and shipped three defects that
typecheck, lint, 2795 tests and a production build all passed. Each was a
**well-formed value that was the wrong one**, which is the shape no type system
and no unit test can see. All three were found in the first four frames of
`npm run look -- --tooltips`, and they are worth listing together because the
family is what matters, not the instances.

| Defect | What it looked like to the tools | What it looked like in a frame |
|---|---|---|
| `\n` never unescaped out of the AS3 literal (`gen-upgrade-descriptions.mjs` handled `\'` only) | A valid `string`. The generator's `--check` was green — it compared its own output to itself | `...towards the crosshair.\nThe ice grenade explodes...` with a visible backslash |
| Panel size estimated (`6.6` px/char, `17` px/line, transcribed from Flash's Arial 14) rather than measured | Arithmetic that agrees with itself; `placeInfoText`'s 13 tests all green, because they are given the size | Panel rendered 76 and 94 tall against an assumed 66, so every up-opening corner sat 10–28px too low and covered the cursor |
| `showTop: false` where `ButtonUpgradeInfo.as:163` passes `bottom = true` | Two valid booleans | The panel opened upward, over the row *above* the one it described |

Three separate lessons, in decreasing order of how well this project already
knew them:

1. **The citation drifted before the value did.** The wrong `showTop` was
   cited to `ButtonUpgradeInfo.as:56` — a description string, not the
   `changeText` call at `:163`. The eye lands on the text because the text is
   what you are looking for; the arguments are four lines away and named
   `right`/`bottom` against parameters named `left`/`top` (`:168`). **A
   citation to the wrong line is worse than none**, because it stops the next
   reader checking. This is the T34 finding — "a citation is not a check" —
   arriving from the other direction: there the line was right and the constant
   wrong, here the constant was wrong *and so was the line*.

   The fix is a mechanism, not more care: `src/game/ui/infoTextSites.ts` holds
   all 20 call sites, and `infoTextSites.test.ts` **parses the arguments back
   out of `SWFimported/scripts/*.as`**, resolving locals through their
   assignments. The screens call `siteCorner(...)` rather than restating
   booleans. A wrong corner now needs two edits that disagree.

2. **A generator's `--check` proves determinism, not correctness.** `--check`
   re-runs the extraction and diffs; a wrong extraction is stably wrong and
   passes forever. It is a staleness guard and was read as a correctness one.
   Where the extracted value is *displayed*, the check that matters is a frame.

3. **An estimate of something the platform can measure is a
   constant-that-became-a-variable.** Line height was fixed in Flash and is a
   function of the stylesheet here; porting `17` carried the arithmetic and
   dropped the meaning, exactly as `cameraWidth` did. The panel now reads its
   own box back after layout. **The tell is a magic number describing something
   the runtime already knows.**

## A feature's coupling can be unportable because the *other* screen diverged

T102 ported the level guide in five passes. Four landed. The fifth —
`selectFromLevelGuide` (`ScreenLevelSelect.as:584-596`), the half that pushes
the guide's choice into the level select — **has no counterpart in this port**,
and the reason is not in `LevelGuide.as` at all.

The AS3's level select is a four-step flow: pick a world, see its grid, **select
a level**, press Play. `selectedLevel` is persistent selection state, and
`selectFromLevelGuide` exists to pre-*highlight* it so the player can go
straight to Play.

This port's level select is three steps: world picker, grid, and a cell click
that emits `ui:start-game` **immediately**. There is no `selectedLevel` on the
scene, no highlight, and no Play button on the grid. So there is nothing to
pre-select, and porting the function would mean first building a selection
layer the port deliberately does not have — a UX change to a screen that was
carefully settled, dressed up as a port.

The latch goes with it. `canSelectFromLevelGuide` (`:73`, `:364`, `:592`,
`ButtonLevel.as:93`, `ButtonWorldSelect.as:70`) is a one-shot guard *for*
`selectFromLevelGuide`; with no pre-select there is nothing for it to guard, so
implementing it would be a mechanism with no rule behind it — the shape
`KNIP.md` and the source-shape tests are cautionary tales for.

**The generalisable part.** Scoping asked the right question about `LevelGuide`
— what does it read, what does it write, does it touch the unlock rules — and
got right answers. It did not ask **whether the thing it writes to still
exists in the same shape here**. A coupling is a relationship between two
sides, and this project has now diverged from the original on enough screens
that the far side is a live variable. Where the AS3's `ScreenX` writes into its
`ScreenY`, check `ScreenY`'s port before costing the write.

Recorded rather than built, with the two portable fragments named in
`HANDOFF.md` §5 so a later pass can take them if the level select ever grows a
selection step.

## Dead arithmetic: port the reachable answer, and make the assumption fail loudly

`PartInfoText.getEnemyAmountArray` (`:94-147`) is the most intricate thing in
the next-level preview: it raises a level's enemy total by the difficulty's
`multiplierAmount`, then hands the *extra* enemies out one at a time to
whichever type currently sits furthest below its original share.

It cannot run. `DifficultyMultipliers.as:6` and `:8` set
`multiplierAmountMedium` and `multiplierAmountHard` to **1**, so the loop bound
`enemyModelCurrent[0] - normalEnemyAmount` is exactly zero on all 405 levels at
every difficulty, and all three difficulties yield the raw per-type counts.
This is the Laser Cannon's `spread = 0` again — "a line of dead arithmetic was
recorded as a blocker" — one level up: fifteen lines this time, and the
temptation is to port them for fidelity's sake.

T101 did not, and the reasoning generalises: **porting code the original never
executes ships arithmetic that cannot be checked against anything.** There is
no observation, in the original or the port, that would reveal a mistake in it.
A faithful-looking transcription of an unreachable branch is a guess wearing a
citation.

What was done instead has two halves, and the second is what makes it
defensible rather than lazy:

1. `enemyAmounts` returns the raw counts — exactly what the original produces.
2. It **throws** if `amount !== 1`, naming the unported branch and its AS3
   lines. A test drives that by temporarily setting the multiplier to 1.5 and
   asserting the throw, then restoring it.

So the assumption is not a comment that rots; it is a check that fires the
moment it stops holding. `countdownPanel.objectiveText` makes the *opposite*
call on the same constant — it applies the multiplier, saying "the multiplier
is the rule, and 1 is data" — and both are right. **The dividing line is
whether the rule is cheap and verifiable at any value.** One `round(total * m)`
is correct however `m` moves; a fifteen-line redistribution is only correct if
someone can observe it.

## A caveat that reads as diligence, and was never checked (T111)

The volume slider ↔ mute coupling sat open from T83 to T111 on a stated blocker
that was **false about the AS3**, and the shape of the error is worth more than
the feature.

The note said adopting the AS3 rule *"would do it from the HUD and main menu,
where `AudioToggles` renders with no slider visible — the original always
reconciled with the slider on screen."* That describes `ScreenOptions.as:233-256`
accurately, and it is the only file the T83 pass read. **`ButtonToggleSound.as:43-52`
is a standalone toggle with no slider anywhere, and it applies the same coupling**
— flip `soundOn`, then write `soundVol = 1` on / `0` off. So the port's HUD and
main-menu toggles have a direct AS3 counterpart, and the objection to porting the
rule was an artefact of not looking for one.

**The tell is the shape of the claim, not its content.** *"The original always
reconciled with the slider on screen"* is a **universal statement about the whole
original**, derived from a **single file**. It is the "say by what method" rule
in a new place: the sweeps that rule was written for are name- and pattern-based
greps, and this was a prose assertion with no sweep behind it at all. One
`grep -rn 'soundOn *='` over `SWFimported/scripts/` returns eight sites and
settles it in a second.

It also cost more than an ordinary stale note would, because it was *reasonable*.
It named a real asymmetry (toggles without sliders), gave a plausible consequence
(a chosen volume discarded from a surface that cannot show it), and concluded
with restraint. A caveat that argues for caution and cites a line number reads as
careful work, so nobody re-derived it for four passes.

**Ask of any "we cannot do X because the original does Y" note: which files were
read to establish Y, and does the claim quantify over more than those?**

## A synced asset is not a loaded asset, and the gap renders silently (T108)

**The T106 boss life indicator shipped drawing Phaser's `__MISSING` texture for two
days** — a 32x32 black square with `rgb(0,255,0)` lines — and it was reported as "a black
background with green lines under the boss". The geometry was never wrong.

**The cause is one missing line, and the shape of it is the finding.** Getting extracted
art on screen takes **two** independent registrations:

1. `scripts/sync-assets.mjs` copies the SVG into `src/assets/` — T106 did this
   (`:213`, `'1199.svg'`).
2. `src/assets/manifest.ts` declares it in `UNIT_SHAPES` so `PreloadScene` loads it as a
   texture — **T106 did not**. `manifest.ts` is not among the seven files that commit
   touched.

`GameplayScene` then asked for `unit-1199`, and `TextureManager.js:1301` returns
`__MISSING` for any key it does not hold. **No error, no warning, no failed load** — the
image draws, at the right position, size and depth, masked by a correct wedge. `npm run
look` reported `no page errors` on the broken build.

**Why every existing guard missed it, which is the reusable part:**

- **All 17 T106 unit tests passed against the broken build** (driven in a throwaway
  worktree, not assumed: 2 fail / 18 pass once the new assertion is added). Every one of
  them is about *angles and sizes*. A pure geometry module cannot see which texture its
  angles reveal, and `bossLifeIndicator.ts` was deliberately pure.
- **`projectileArt.test.ts:80` is exactly this check and had been since T84** — it even
  names the symptom in its own docstring, *"the game would draw a green 'missing texture'
  box"*. It covers `PROJECTILE_ART` only. The boss disc is constructed directly by the
  scene, so it fell outside the mechanism's reach. **The guarantee existed; its reach did
  not include the new site** — the same shape as trap 9 and the `KNIP.md` entry.
- **A frame is the only instrument that sees it**, and one was never taken on this
  subsystem after it landed. T106's own driven run logged five correct HP/degree pairs
  and captured five frames; the numbers were right and nobody opened the images.

**The fix is `manifest.ts` plus a pin.** `RED_CIRCLE_SHAPE` moved from a private const in
`GameplayScene` into `bossLifeIndicator.ts` **so that a test can assert it against the
manifest without booting a scene** — the id was untestable where it was, which is why it
was unpinned. `bossLifeIndicator.test.ts` now drives the key against `UNIT_SHAPES`, with
the negative (`unit-999999`) on the identical set so the lookup cannot pass vacuously.

**Before adding any scene-constructed texture, check both registrations.** A name-based
grep for the shape id finds the `sync-assets.mjs` line and stops there, which is what
makes this look done.

### `e.type` on an `Enemy` is `"Container"`, not a species

Found while instrumenting the fix, and the same family. The `__arena` debug projection
gained `type: e.type` to report which boss was being sampled; it logged
`Container hp 450/750` for every enemy in the game. `Enemy extends
Phaser.GameObjects.Container` (`Enemy.ts:158`), so `type` is Phaser's own GameObject tag
and the species is `enemyType` (`:159`).

**A plausible string is worse than an obviously broken one** — this is the fallback trap
(`(640, 400)` as a tank position) arriving through inheritance rather than through a
default. The projection now uses `enemyType` with the reason stated at the site.

## A screenshot cannot tell a missing layer from a deliberate blank

The bestiary's resistance badges (T100) are three stacked SVGs per frame: a
coloured disc, the damage-type glyph, and a ring. **If the middle layer fails to
resolve, the badge still renders — as a clean empty disc, which is precisely
what the frame-1 "none" badge is supposed to look like.** So the failure mode
and a correct, meaningful state are pixel-similar, and eyeballing the frame
cannot separate them.

`npm run look -- --resistances` therefore counts `naturalWidth > 0` per layer and
prints `[3/3 layers]` beside each badge, rather than relying on the picture. That
is the same move as `--tooltips` measuring the panel box instead of asserting the
node exists, and it generalises: **when a subsystem's broken state resembles one
of its valid states, the driven check has to measure the mechanism, not the
result.**

The related trap, caught in the same pass: a fresh profile knows exactly one
enemy, `Basic`, and `Basic` has **no** strengths and no weaknesses. A run without
`?known=all` photographs two "none" badges, reports "every badge layer resolved",
and is completely truthful while covering none of the 16 typed badges. That is
the T99 achievement-note gap again — *the default profile is not a
representative sample* — and here it was cheap enough to fix with a dev aid
rather than record as a limitation.

**T101 hit the identical trap a third time, from a different direction.** The
next-level preview's first driven run cleared 1-1 and hovered the button: six
correct summary lines, two enemy rows, "every image resolved". It also drew
**zero badges**, because 1-2's roster is `Basic` and `Fast` and neither has a
single resistance. The run was accurate and covered nothing. The fix was to
drive a second scenario — jump to 1-12, clear it, preview 1-13, which is the
earliest roster carrying any — and that immediately found a real defect the
first run could not have: every badge announced itself as `aria-label="None"`.

Three passes, three instances, one shape: **the state a fresh run lands in is
chosen by the save file, not by what needs testing.** Before reading a driven
result as coverage, ask what the default profile makes *unreachable*, and note
that the answer is invisible in the output — a run that draws nothing and a run
that draws everything correctly both print "no errors".

## The reachable surface of a ported subsystem is not its AS3 call count

`PartInfoText` has **20** `changeText` call sites, and step 1 was scoped as
"14 core + 2 rich text". Both counts are right about the AS3. **Two** have a
live consumer in this port.

The other twelve plain-text sites divide cleanly, and the division is the useful
part:

- **Four are faithful and pointless here.** `ButtonAchievements`, `ButtonEnemies`,
  `ButtonMenu` and `ButtonOptions` each show a tooltip containing the button's
  own name — because in the AS3 those buttons are *icons*. This port renders
  them as text buttons captioned with that same word, so porting the tooltip
  would put "Options" in a panel under a button labelled "Options". Recorded as
  `status: 'redundant'` rather than wired.
- **Five have no consumer**: the Credits screen is unported, and `ButtonSaveInfo`
  / `ButtonConvertSave` explain Armor Games online saves, which this port does
  not have.
- **Three are deferred** to the Level Guide, which does not exist yet.

None of this is visible from a call-site count, and a pass that took the count at
face value would have produced four tooltips that repeat a visible label and five
that attach to nothing. The counts belong to the source; **what is reachable
belongs to the port, and only the port can be asked.**

This is the same correction as "27 tutorial classes were 26 stubs and one real
class" and "187 sound sites were 12 rules" — the third time an AS3 count has
overstated the work by roughly an order of magnitude in the same direction.

**T100 made it the fourth, and added a sharper version.** Step 2 was scoped as
"wire `addStrengthsAndWeaknessIcons`, 2 live sites on the Enemies screen". Three
of those four terms were wrong: the screen is the *Bestiary* (`EnemiesScreen.tsx`
is a port-progress dev board with no AS3 counterpart), the badges there are a
**different class** from the one `addStrengthsAndWeaknessIcons` draws
(`IconStrongWeak` 1033 against `IconStrongWeak2` 1018, differing on 6 of 16
glyphs), and `addStrengthsAndWeaknessIcons` itself has **no** live consumer —
its caller chain ends at `ImageEnemy`, which appears only on the level-select
enemy roster (`ScreenLevelSelect.as:1128`), unported.

The sharper lesson is the second one. **Two AS3 classes with near-identical
names, near-identical frame layouts and a shared purpose were not
interchangeable**, and nothing but reading both `[Embed]` lines and every
construction site would have shown it. A name-based reading — which is what a
queue entry is — cannot distinguish `IconStrongWeak` from `IconStrongWeak2`, and
picking the wrong one would have produced a screen that looked entirely correct
while drawing the panel's artwork.
`INFO_TEXT_SITES` records the per-row verdict so the next pass inherits the
answer instead of re-deriving it, and its test asserts the table still matches
every call site found by name in `SWFimported/scripts` — a floor, since an
inlined or aliased call would not be counted.

## Unsourced polish — an open category

Invented presentation with no AS3 counterpart, added for feel and never recorded as
added. **It reads as faithful to anyone who did not write it**, which is what makes it a
category rather than a list of small choices.

The category exists because one instance caused a real bug hunt: a `scrollX * 0.06`
parallax on the ground tile made props appear to drift, and the complaint arrived as
"props are broken" while the props were correct and the ground was the invention. A
future session debugging a symptom near any of these should suspect the polish before the
mechanic.

Known instances — **not hunted, so treat this as a floor**:

- **Ground margin dimming.** The out-of-arena border is darkened because "with no border
  art in the extraction, the change in brightness is the only thing marking where the
  arena ends". Self-declared invention, still present.
- **Bullet render inflation.** `setDisplaySize(radius * 4)` — bullets are drawn at four
  times their collision radius so they "read at speed". Also self-declared. See the
  placeholder-art note below for why this one is a trap.
- **Ground parallax.** Removed in `b51c059`. Recorded here because it was invented,
  survived months looking faithful, and cost a diagnosis pass.
- **Prop variant brightness step.** Gone — superseded when real art landed in `c5bd4bf`,
  where the variant frame became an actual sprite frame instead of an opacity cue. Noted
  so a future reader looking for it knows why it is absent rather than assuming it was
  lost.

## Placeholder art is not a bug, and must not be compensated for

Two rows of the first visual survey are **consequences of placeholder art**, recorded so
nobody "fixes" them in the rendering layer:

- **Enemies and the player tank are near-identical bright green.** Both are tinted
  circles; the tank differs only by size and a blue centre. At a glance they are hard to
  tell apart. The fix is enemy art, not a different tint.
- **Bullets are nearly invisible** — radius 2, pale tint, easy to miss entirely in a
  frame while firing.

**Do not make bullets bigger.** They already carry a 4x inflation over their collision
radius (see unsourced polish above), so enlarging them further stacks invented polish on
invented polish — and the second layer hides the first, which is exactly how the parallax
survived. The honest fix is real art; until then the discrepancy between what is drawn
and what collides stays recorded rather than tuned away.

## Two ways this port can be misread, and both bit within one pass

`npm run look` drives the running game; **the two traps in operating it are findings
about the port, not about the tool**, and the next person to conclude "this weapon does
not fire" needs them. Full detail sits next to the command in `CLAUDE.md`:

- **A sub-frame key tap can be lost.** Input flags are read once per frame, so a
  down+up inside ~10 ms is never observed. This is **faithful** — see the entry below.
- **A secondary can fire invisibly.** Mine drops at the tank's own centre, under an
  opaque sprite. A frame taken on the press cannot distinguish "did not fire" from
  "fired underneath".

Both were reported as game findings before being diagnosed as observation artefacts.

## Code that looks wrong, is load-bearing, and invites the tidy-up that breaks it

Three instances found so far, months apart, in unrelated subsystems. Each looks like a
mistake, each is faithful, and **each is tempting to tidy in exactly the way that breaks
it**. A fourth should be recognisable in one line rather than re-derived.

**Broadened 4 August 2026.** The heading was "arithmetic that discards its own result",
which covered three instances that were all literally dead arithmetic. A fourth arrived
that is not arithmetic at all and belongs to the same family, so the category is now the
*hazard* rather than the syntax: **code a careful reader would improve, where the
improvement is the defect.**

### The coin magnet has no range limit, and must not acquire one

`handleMoney` (`:2155`) adds `2.5` toward the tank to every coin's velocity **every
frame, from anywhere on the map**. No proximity check, no acquisition radius. It reads
like a missing guard, and adding one is the obvious tidy-up.

It is load-bearing. `levelDoneFunction` (`:667`) holds the results screen while loose
money is on the floor, and the unlimited magnet is what guarantees every coin eventually
reaches the tank — i.e. that the wait *terminates*. A range-gated magnet looks more
sensible and hangs the results screen permanently on any coin that came to rest out of
reach. The level would simply never hand over, and it would happen only on drops that
scattered far, which is the worst possible failure distribution.

Pinned in `items/money.test.ts` by driving a corner coin 400 frames and requiring it to
arrive, with the reason stated at the assertion.

**The shape (original three):** an expression whose result is discarded, thrown away by a multiply by
zero, or rendered inert by NaN — *while still consuming a random draw or occupying a
branch*. The behaviour is correct as written. The tidy version is correct too, right up
until it changes how many draws were taken or which branch ran.

| Where | The arithmetic | Why it must stay |
|---|---|---|
| **Laser Cannon spread** (`:3938`) | `tower.rotation - spread/2 + random() * spread` with `spread = 0` | Evaluates to the turret rotation exactly. Once recorded as a reason the weapon "needed its own spread rule" — it is a no-op, and reading it as a mechanic cost a scoping pass. |
| **Prop group roll** (`:1370`) | `groupChance *= 1 / ((max - min) / 2)` = `0 * (1/0)` = **NaN** for a ruleless type | The NaN gives the right answer (never clusters) *and* consumes the right draw. Hoisting the roll inside the rule check keeps the behaviour and shifts every prop after the first ruleless one. **Verified: hoisting it fails six tests.** |
| **`FuturisticLines` scale** (`:3529` region) | `4 + scale * 0` | A constant 4. The `scale` draw is taken and thrown away. Simplifying to `4` is correct in isolation and wrong in sequence — the draw is part of the stream. |

**What to do when you meet the fourth.** Do not simplify it. Establish first whether the
discarded expression *consumes* anything — a `nextDouble()`, a branch that advances
state, a side effect in an argument. If it does, the arithmetic is load-bearing despite
producing nothing, and it goes in the table above with a comment at the site saying so.
If it genuinely consumes nothing, it is dead and can go — but say which you established
and how, because the two are indistinguishable by reading the expression alone.

The tell is a term that is provably zero, provably constant, or provably NaN, sitting in
an expression nobody would write that way on purpose. In this source that is a signal it
was left over from something, not that it is inert.

## Faithful, and easy to mistake for a defect

Seven places where the port looks wrong and is not. Each was verified against the AS3
line cited. This section exists because reviewing a faithful port produces false
positives, and the cost of "fixing" one of these is a silent behaviour change.

- **C1. Food rounds bounce off the camera, not the room.** `:1906`. The `roomWidth`
  terms cancel exactly; `cameraPosX` is a negative container offset (`:707`), so the
  pair is the visible window inset by the radius. A round bounces with a thousand units
  of empty room beside it.
- **C2. Lava patches *grow* as they die.** `:7062`, scale `0.75` → `1.25`, and a patch
  drops from its spawn radius of 18 to 15 on its very first tick because `:1800` sets 18
  and `:7065` overwrites it.
- **C3. Ice bites for its full stat; lava for fifteen frames less.** One gate at
  `lifeTime > 15` (`:6200`), and only ice is spawned with `+15` (`:1789`, `:1795`).
- **C4. The Ice Ball deals no contact damage at all.** `explosion = false` (`:4187`)
  keeps it off the automatic blast path and `:5917` names it in the exclusion list of
  the direct-damage path that flag selects. Its hand-queued blast (`:5895`) is its only
  route to an enemy — including the one it just hit.
- **C5. A new Ice Ball throw re-arms every patch on the floor**, including the previous
  throw's. `:6208` compares the enemy's stamp against the scene counter's **live**
  value, and no patch carries an id. Diverges from a per-patch model only when a second
  ball is in flight over the first one's trail, which is why the wrong model survived
  review.
- **C6. Gummy Bear's 4× damage was unreachable for the entire port until `fad4cba`.**
  A bear escalates on bounce — `×3` into stage 2, `×4/3` into stage 3 (`:1951`) — and
  the port culled every bullet at the room edge, so it never bounced. **The weapon ran
  at a quarter of its intended damage, indefinitely, with no test failing and nothing
  visibly broken.** This is the strongest case in the repository for pinning ported
  rules against the source rather than against observed behaviour: no amount of playing
  the port would have revealed it, because the port was self-consistent.
- **C8. Kill Reload does not reload anything.** `:6849`. Every kill takes 2-11 frames
  off the **secondary** cooldown; the primary is untouched. It also does not bank — a
  kill with the secondary already off cooldown is worth nothing — so it shortens a wait
  rather than charging a weapon, which is not what the name promises.
- **C9. A contact suicide pays no money but still buys cooldown.** `:6849` sits outside
  the `noMoney` gate at `:6842`, so the one death that deliberately pays nothing is
  still worth 2-11 frames. Reads like a missing guard; is faithful.
- **C10. A lava-trail kill credits the player.** `:6282` sets the same `dead` flag a
  bullet does, from the ground-contact loop, so an enemy that dies to a patch thrown
  seconds earlier triggers everything a shot would — Kill Reload included. Ice trails
  never do, because they freeze and never damage.
- **C11. A prop that can never cluster still rolls for it.** `:1370` computes
  `groupChance *= 1 / ((max - min) / 2)`, which for a type with no group rule is
  `0 * (1 / 0)` = **NaN** — so `nextDouble() <= NaN` is false and it never clusters, but
  the draw happens. The NaN is load-bearing: it gives the right behaviour *and* consumes
  the right draw. Hoisting the roll inside the rule check keeps the behaviour and shifts
  every position after the first ruleless prop. Verified: hoisting it fails six tests.
- **C12. `RedBloodCell` asks for a frame it does not have.** `addBackgroundObject`
  declares `maxFrames = 3` (`:3596`); symbol 1465 has one frame, and Flash clamps
  `gotoAndStop` past the end. The port keeps 3 in the arithmetic — that is what the draw
  consumes — and clamps only at display. Reconciling the two tables either changes the
  stream or renders a frame that does not exist.
- **C13. Cracks collide with everything, despite a branch that says otherwise.** `:2633`
  excludes `BGObjectCrack` against non-Crack in both directions, and **no class of that
  name exists**. Confirmed two ways rather than on one reading:

  1. *Exhaustive search.* No file, and no `class BGObjectCrack` declaration, anywhere in
     `scripts/`. The three clips are `BGObjectCrackDesert`, `BGObjectCrackBlueDirt` and
     `BGObjectCrackConcrete`, and none of them extends a shared `BGObjectCrack` — each
     extends `MovieClip` directly, so there was no base class to test against either.
     The literal `"[object BGObjectCrack]"` occurs nowhere but `:2633`.
  2. *A control on the same line.* The idiom resolves through
     `Object.prototype.toString`, giving `[object ClassName]`. `BGObjectCrackDesert` and
     `BGObjectFuturisticSquare` are structurally identical — same top-level package, both
     `public dynamic class … extends MovieClip`, neither overriding `toString` — and the
     **FuturisticSquare test on the same line matches**, which is why that exclusion is
     live. So the mechanism works; only the name is wrong.

  The author appears to have meant "any Crack variant" and written a name that never
  existed. Cracks are removed by collision like anything else. Reproduced as written.
- **C14. The game can drop a very fast key tap — and so did the original.** Input is a
  latched flag set on keydown and cleared on keyup, polled once per frame, so a press and
  release that both land between two frames is never observed. That looks like a defect
  and is faithful: `Main.as:711` sets `space = true` on keydown, `:771` clears it on
  keyup, and `PartGameArea.as:3981` polls `if(Main.space)` once per frame inside
  `tankAttack`. Identical structure, identical vulnerability — and at the AS3's 30 fps the
  window is 33 ms, *wider* than the port's. **Not a fidelity bug, and not to be "fixed"
  by latching the event**, which would make the port accept inputs the original refused.
  Established by comparing both handlers, after a 10 ms scripted tap was mistaken for a
  weapon that would not fire.
- **C15. After the countdown, enemies stop appearing off-screen and arrive at the room
  edge instead — on 198 of 405 levels.** Landed T67 with the countdown, and it is the
  most visible behaviour change in the port so far, so it is recorded before anyone
  reports it.

  `:7245` runs the off-camera search only while `countDownDone` is **false**, and
  `:7268` takes the edge branch once it is true. The port never wrote the flag, so the
  search ran on **every** spawn for the whole level. Now it runs for roughly the first
  two seconds and then stops for good.

  **Measured, not estimated** — `npm run look -- --countdown` drives level 1-2 twice on
  one build, `?countdown=0` reproducing the old state:

  | | spawns in a 16s window | off-camera | edge |
  |---|---|---|---|
  | before (flag never written) | 9 | 9 | 0 |
  | after | 8 | 1 | 7 |

  The single off-camera spawn is at `framesLeft=17`, i.e. inside the countdown; every
  later one carries `framesLeft=0` and lands on a room boundary (x=0, x=800 or y=600 in
  an 800x600 room). Over 1-2's full 18 enemies that is ~94% arriving at an edge.

  **Which levels can change, and which cannot:**

  | Mode | Levels | Affected | Why |
  |---|---|---|---|
  | Normal | 90 | 76 | |
  | Flag | 90 | 77 | |
  | Boss | 45 | 45 | non-boss spawns only — `:7245` excludes bosses |
  | Tower | 90 | **0** | all are 640x640, so `roomWidth == cameraWidth` already disqualified them |
  | Defense | 90 | **0** | excluded by mode *and* 640x960 |

  So Tower and Defense are untouched, and the 198 figure is not a viewport artefact —
  it is the room table. Checked by reading the room sizes rather than assuming.

  **Why it reads as a regression and is not:** enemies currently fade in out of view,
  which looks deliberate and good. The original pops them in at the room boundary once
  play starts, and on rooms whose edge the camera can see that means appearing on
  screen. The off-camera search exists precisely for the countdown window, not for the
  level.
- **C7. Fire drain stacks per flame; lava damage does not.** Both in the same file. The
  drain sits in the bullet loop with no dedup (`:7078`), so two flames on one patch
  drain it twice; `onLava` (`:6250`) is deduped per frame. Opposite rules, both faithful.
